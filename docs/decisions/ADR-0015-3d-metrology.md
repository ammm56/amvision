# ADR-0015：3D Metrology 节点包与三维测量边界

## 状态

设计方向已确认，M0 收口，M1–M3.3 共十八节点已按后续授权内部接通，生产仍隐藏。更新日期为 2026-10-24。受控 trimesh PLY / pypcd4 PCD 修复仅本项目使用，不提交上游；M3.3 另行授权的矩形扩展已包含在 trimesh `.2`。实现记录见 [M3.3 实施与验收](../development/3d-metrology-m33-acceptance.md)，最新阻断及修正顺序见 [真实工件审计](../development/3d-metrology-audit-20261024.md)。不将定向算法/链路验证等同于完整现场测量通过。下文决策中的“本轮仅设计”是 M0 时的授权边界，不覆盖后续已授权实施。

2026-10-24 后续修复已完成参数分发、输入错误分类及有限连续边段选择，见[修复与验收](../development/3d-metrology-repair-20261024.md)。目标 ROI 仅保留已有连续顶点，跨排除点/原缺口断开，多段歧义拒绝，不插值 ROI 端点；边界方法升 v2，包版本 `0.1.10`，旧方法资产只读需重建，生产仍不启用。

已确认基准延伸采用显式模式与配方给定最大距离，被测面始终需实测支持；契约设计见修复记录第 5 节。高度算法尚未实施该设计，现有支持域拒绝语义不变，不对缺测的被测表面静默补点或外推。

已确认的方向是：以 **3D Metrology** 提供跨产品、跨行业的三维测量节点，复用现有 Workflow、Core Rule、Preview、Runtime、资源管理和前端主栈。当前工件点云仅是开发验证样本，不构成产品范围或算法默认参数。

详细设计、节点能力清单、样本证据、依赖准备、阶段步骤与验收要求只维护在 [3D Metrology 实施基线](../development/3d-metrology.md)。其中拟定的 payload、节点 ID、参数和接口仍须完成契约门禁，不能作为当前公开运行时能力使用。

## 背景

项目已有二维 OpenCV 算法、测量数值表、限值判断、节点目录和工作流执行能力。三维测量还需要明确点云/深度/高度/轮廓的数据语义、空间坐标与基准、观测覆盖和测量证据，不能通过给二维图片增加第三个坐标字段完成。

已有真实点云探索说明，尺寸结果必须同时说明参考对象、位置、方向、边界和可见范围；同一个工件的投影包络、拟合边间距和特定轴跨度不是同一个量。缺测圆弧可得到很小的拟合残差，但不代表具备足够的测量支持。样本脚本中的固定区域、数量和排序规则也不具备通用产品语义。

## 决策

1. 包显示名称为 `3D Metrology`，拟定包 ID 为 `metrology3d.nodes`，Python 目录为 `custom_nodes/metrology3d_nodes/`。不使用 `pointcloud_nodes`，不建立锂电、某工件、某工位专用包。三维计量是独立技术域，包内按输入、预处理、定位、特征、测量和表面分析分类，不为单一算法再拆包。
2. 采用基础算子、常用测量工具、Workflow/Template 三层。组合工具调用共享算法函数，不嵌套执行节点 handler 或 Workflow。模板保存产品 ROI、特征身份、公差和交付方式；算法层不写产品固定数量或名称。
3. 平台公共层负责版本化数据契约、资源身份和生命周期；节点包负责三维算法。Core 继续负责通用数值表、规则、控制和结果组织，不能反向依赖 3D Metrology。三维数据不能伪装成现有图片 payload。
4. 采集 SDK 属于 Camera provider 或明确的受信任设备扩展；PLC、数据库、HTTP 和文件交付复用现有能力。SPC 属于持久结果统计，不在单次测量节点内建立无界历史缓存。
5. 高度、厚度、距离、尺寸、形状误差都必须有可核对的测量定义。单位转换与刚性定位分开；定位不允许隐式缩放、镜像或非刚性变形吸收尺寸缺陷。基准建立和最佳拟合配准不能混为一种操作。
6. 测量数值、数据质量、几何证据和公差判断分别表达。无效量不能以零代替；必检集合来自冻结配置，不能从本次成功结果推导。通用判断需要显式区分 OK、NG、INVALID，执行异常仍保持任务错误。
7. 每次 Workflow 调用输入完整点云，同时支持文件和同机内存二进制数组，输入载荷最大 1 GB，不是运行内存上限；不做连续实时流和跨机二进制传输。大数组不内联到 JSON/pickle。文件输入复用 ObjectStore/文件快照，同机数组复用 LocalBuffer 分配、guard 与所有权底层，并新增显式版本化的三维类型；当前图片协议不改作点云协议，不创建平行 Broker、数据面降级或隐藏队列。具体布局、释放及预算见实施基线第 10 节；后续 M1 已内部实现，生产启用仍受预算与发行验收约束。
8. Preview 与正式运行继续使用既有 Worker/Workflow Runtime、取消、timeout、整组停止和恢复机制。不新增 Metrology Runtime、每节点进程、独立调度器或默认常驻服务。纯测量 Workflow 不引入模型实例数限制；调用模型时沿用实际 Deployment 容量准入。
9. 前端采用 Vue 3 和共享 Three.js 三维查看组件，复用 Catalog、参数绑定和已有受控编辑扩展。工程师使用现有画布/参数检查区/Preview，现场使用同一发布版本的 App Mode；不新增角色体系、页面设计器或独立 UI 发布。三维显示由显式 cloud-preview 节点接入既有有界观察通道，不让每个算法自动发送全云或各建连接。标注真实端点与显示偏移分离；显示降采样、色标和裁剪不改变测量数据。资源随发行包离线分发。
10. 基础算法优先使用已有 NumPy/SciPy/OpenCV 及经验证的 Open3D 等库，项目完整实现参数、测量语义、质量、追溯和生命周期，不以单工件脚本、CloudCompare CLI 或轻量近似替代正式节点。CPU 作为 Windows/Ubuntu 的基础计算路径，GPU 仅在独立验证后作为明确能力。
11. 工程正确性、真实计量准确度、界面正确性、性能及持续运行验收分别给出证据。拟合小数位、残差、单次点云结果和合成测试不能替代标准件标定与重复性验证，也不构成通用工业认证声明。
12. 生产调用默认不自动保留完整点云，由配方显式选择保存原始或处理后的数据；结果保留数值和有界显示证据。暂存文件不等于持久资产，运行结束须按借用、映射、底层资源的依赖顺序释放。原始数据未保留时不承诺任意原精度复算。最低 RAM、目标并发数和单次时限未确定，不据此填入产品默认值或验收承诺。
13. 保存采用平台无损资产，PLY/PCD/XYZ 为独立、显式交换导出。原始文件保留原字节；内存输入和派生点云保留 dtype、属性、单位、坐标与追溯信息，派生子集保存为独立数据，不持久化运行句柄。**当前样本按 float32 保存和传递，外部文件按声明保留精度，算法按需要局部使用 float64**；不强制整云提升，不按显示小数位数舍入输入。无 dtype 的 XYZ 复用现有字段映射显式声明，不猜测。扩展既有计量资源服务及显式内容版本，不另建资产系统；原有整包 bytes 导入导出不能仅扩大限额承载 1 GB。资源包采用独立、显式配置的大小上限，数值待定；Workflow 输入数据的 1 GB 上限不变。
14. 几何选型保持 **trimesh + Open3D**，**XYZ 复用现有 NumPy**。Open3D 使用上游原版负责点云几何，不承担本方案的严格文件 I/O；PLY 基于 trimesh 5.1.1、PCD 基于 pypcd4 1.5.1 维护受控 Python 修复版本，仅在本项目使用，不要求或安排向原仓库提交。成熟 parser 内补齐头部、完成状态、字段、类型化分块和写出检查；平台不复制解析器，不依赖私有元数据、不运行时 monkey patch、不保留失败换库/编码的降级。LZF 使用上游 wheel，不自建 C/C++ 扩展。修复版必须有独立版本、源码/补丁身份、许可证、wheel hash 和双平台格式/资源回归；后续升级由本项目承担重审责任。trimesh 的几何算法不随 I/O 修复改变，原版已有缺口不能被新版本名掩盖。此前 RPly 薄适配取消，meshio 不引入，plyfile 继续排除，此为发行审查边界而非“GPL 禁止商用”。现有 ASCII PLY 样本必须直接覆盖并保持 float32，不转格式规避。路线和验收见实施基线 11.2.8/15.5；本轮仅设计，不安装、构建或实现。
15. 现有 Workflow App 已有草稿、不可变版本、依赖快照、Runtime 选版与回滚，直接复用，不再实现发布管理。通用三态规则及资源/节点语义变更采用审核重发：仅确受影响的旧发布保留只读历史，审核后创建新 AppVersion；新增不被旧图引用的节点不使无关发布失效。冻结文件指纹与实际执行代码身份需在已有发布/启动边界对应核对。不保留旧算法兼容分支，不根据历史 NG 猜测重写 INVALID，本轮不删除或迁移数据。
16. 实施按测量功能推进：M1 实现点云读写、单位/有效性与查看；M2 实现 ROI/平面/坐标；M3 实现高度、轮廓、尺寸、孔和判定交付。共享三态及结果读取方在 M3 启用新语义前同批升级，不作为所有算法开发的前置重构；资源和发布保护随实际改动同步完成，不拖到最终交付。每阶段都包含对应前端、异常和验证，不先交付空壳节点。

## 与既有决策的关系

[ADR-0010](ADR-0010-workflow-app-entry-multi-input-contract.md) 的普通文件走 ObjectStore、小参数内联、图片专用 Trigger 和无等待队列原则继续有效。本 ADR 规划的是 local-shared-memory 新增类型化点云能力，不是把普通文件塞进图片 BufferRef；ZeroMQ 能力不随之扩大。公开格式、能力声明、App Contract、SDK 和前端需要同批更新，未完成前仍按现有能力拒绝点云。是否修改底层二进制 layout 取决于真实字段变化，不因新增业务类型就建立第二套 ABI。

[ADR-0011](ADR-0011-industrial-vision-node-coverage.md) 中“三维另立里程碑”的约定保持有效，本 ADR 定义该里程碑的边界，不改写二维能力的历史范围。

[节点包分类规则](../architecture/workflows/node-taxonomy.md)要求按稳定技术域和依赖边界组织。3D Metrology 不等于把现有二维 `measurement` 分类另拆一个包；既有二维节点不迁移、不改名，通用规则不复制。

[ADR-0014](ADR-0014-connector-inspection-2d.md) 中的二维连接器 PIN 语义不进入三维公共契约。可以复用平台的数值、资源和编辑基础设施，不能以复用为名引入特定连接器业务依赖。

## 未采用方案

| 方案 | 未采用原因 |
| --- | --- |
| 直接搬入点云探索脚本 | 固定特征数量、ROI、路径及绘图流程不符合节点契约和跨产品要求。 |
| 一个节点完成采集到 PLC 输出 | 隐藏基准、判定和副作用，无法独立审计、调试和复用。 |
| 每个工件或每个尺寸新建节点类型 | 产品配置污染 Catalog，形成重复算法和维护成本。 |
| 复用图片引用承载 XYZ/深度数组 | 图片格式与三维坐标、单位、有效性语义不同，破坏已有数据面边界。 |
| 用预览降采样、填洞或最佳拟合掩盖缺测 | 显示结果不能替代观测证据，可能导致错误放行。 |
| 新建三维服务、队列和进程管理器 | 与现有模块化单体和独立执行器重复。 |
| 以安装 Open3D 代表实现全部计量 | 算法库不负责本项目的计量定义、公差规则、资源管理和业务追溯。 |
| 用残差或合成结果宣称现场精度达标 | 缺少量值溯源、采集误差、重复性和判定规则证据。 |

## 影响

需要新增三维契约与节点包、共享三维显示和测量证据支持，并完善通用规则的三态语义、发布资源冻结和导入导出验证。公开语义变更必须同步版本、消费者、模板、迁移说明和回归，不保留隐藏兼容分支或静默降级。

新增依赖须在 conda 开发环境、同目录 Python、Windows x64 与 WSL Ubuntu x64 中验证，并核对传递依赖、许可证和发行体积。缺少可选 CAD/厂商依赖时，不伪造可执行能力，也不得导致无关节点失效。现有 assembler 只支持 Windows CPU/NVIDIA 两种目标，Ubuntu profile 文件存在不等于离线发行已完成；WSL 源码运行与 Ubuntu bundled 发行分别验收。

本 ADR 不授权安装依赖、启动服务、迁移现有数据或运行性能/长稳测试；这些操作由后续实施任务按阶段开展。详细步骤与完成后的文档归档规则以唯一实施基线为准。
