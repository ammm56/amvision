# NVIDIA 发行性能与异常收尾验证（2026-10-06）

本轮承接 [两轮一小时验收](nvidia-release-followup-20261006.md)，处理显示清理扫描开销、上传失败资源回收，并复核提前退出、内存与延迟的证据。原小时测试和失败记录保留，本轮新增测试不混入原小时计数。

## 修复及边界

### 文件清理扫描

原实现对每个文件创建路径对象、解析深层路径祖先链并计算相对路径，同时在对象键及模式匹配中再次创建路径对象。真实目录剖析中，这部分开销明显高于获取文件身份的系统调用。

现在按目录计算相对路径，直接组合文件键并提取末段文件名。没有加入隐藏执行间隔、扫描缓存、后台清理线程或跳过目录的逻辑。每次节点调用仍完整扫描；最旧文件优先、期限判断、重解析点防护、文件 ID、删除前版本检查及保存竞争保护保持不变。

同一真实目录 4,473 个文件，旧、新扫描交替执行六轮，逐轮比较返回 metadata 完全一致；中位耗时从 548.37 ms 降至 116.38 ms，减少 78.78%。这是同目录对照，不以不同规模目录的结果代替对照。

两条显示 Runtime 各独立执行五次，完整 HTTP 调用中位数约 1.388 / 1.359 秒，范围分别为 1.190–2.507 / 1.227–1.530 秒。上轮额外诊断的两次调用为 7.37 / 8.86 秒；前后不是同一时刻的严格负载对照，扫描部分的独立交替测试提供直接优化证据。真实节点耗时中清理节点已降到约百毫秒量级。

扫描仍为 O(文件数)，本次不能将 4,473 个文件的结果外推为任意百万文件目录也在一秒内。大规模清理应使用显式独立维护 Workflow，由调用方按维护频率触发，不能在普通节点内隐藏定时器。

### Preview 上传失败

确认了一个失败路径缺口：分块/提交错误发送 `protocol.error` 后，上传仍留在连接的 uploads 字典，等待过期或断线回收；连续错误可占满四个上传槽位。

修复为已识别的分块或提交失败后立即归还该 transfer 的临时内存和上传槽位。未知 transfer 不影响其他上传，已提交输入不受迟到分块影响。不修改 Runtime/Trigger 数据面，也不增加业务队列或重试。

单元/API 回归覆盖错误 SHA-256、不完整内容及乱序分块，每类连续五次失败后同一连接成功提交正确输入，并核对失败后 blocks、bytes、pins、reserved_bytes 全部为零。最终组装的真实发行服务另验证同一 WebSocket 连续 15 次错误后第 16 次正常提交成功；随后相同 59,885,622 字节 BMP 的 Base64 工作流预览成功，6 份显示资源全部释放。

修复扫描后的发行包运行 303.047 秒，同时进行 HTTP 治具检测、.NET SDK ZeroMQ/LocalBuffer 塑盒检测、两路显示订阅、五次真实大图 Preview 和状态查询。Preview 测试额外插入 5 秒 Delay，用于验证节点结果提前显示，不能以这部分人为延迟评价常规预览速度。

| --- | ---: | ---: | ---: | ---: | ---: |
| 治具 HTTP Runtime | 85 | 0 | 3.264 秒 | 6.718 秒 | 8.061 秒 |

- 236 次检测全部符合真实数据预期；治具每次 24 个空槽，塑盒每次 80 槽、72 个满槽、8 个问题槽。没有放宽原有业务超时，没有新增等待队列或自动重试。
- 292 次持续状态查询全部就绪；另 1,000 次 .NET 同步状态调用全部就绪，P50 1.715 ms、P99 7.618 ms、最大 324.498 ms。
- 五次 Preview 全部成功，累计释放 30 份显示资源；两个显示订阅分别收到 89、90 帧成功结果，错误帧为零。

- 排空后 LocalBuffer 分配量、活动租约和活动借用全部为零，原生产目录三个 JSONL 哈希未变。
- 结束并行压测后另外串行调用治具、塑盒各六次，仅写隔离验收目录，与上表计数分开。治具约 1.89–2.52 秒，塑盒约 1.65–2.11 秒。并行竞争和前处理/存图是完整延迟的组成部分，不能把整图耗时当作纯模型推理耗时，也不能将不同图的 HTTP/ZeroMQ 数值当作协议对照。

## 内存与提前退出的归因

上轮所谓 CUDA “20 MiB 台阶”实际是 CUDA 模型进程的主机私有内存，不是 GPU 显存分配量。上轮台阶之后约 25 分钟保持平台；本轮重新启动后预热至稳定区间，60–299 秒两模型主机私有内存分别为 1,807.473–1,807.508 MiB、1,806.227–1,806.230 MiB。没有复现修复前逐调用新增线程导致的持续增长。单次分配台阶不能单独认定为泄漏；具体是哪一个库的那次分配，现有报告不能反向还原。

原 TensorRT 探针在 08:29:31 启动，进度停止于约 280 秒；Windows 在 08:34:31.695 记录 `CodexSandboxService.OpenAI.Codex` 的服务启动事件，随后执行工具报告原进程会话不存在。本轮 12:04:59.285 再次记录相同宿主启动事件，正在启动的隔离 Supervisor 整树消失，没有后端异常堆栈。这两组证据支持测试执行宿主生命周期中断的归类；尚无证据把它归因为 CUDA 原生崩溃，也不冒充已获取旧进程的 OS 退出码或故障转储。

此前一次 Base64 失败只保留了外层错误和字符长度，没有底层原因及失败字符串，无法事后严格还原。当前已保留底层原因，上传完整性及失败清理已有自动化和真实协议验证；两轮一小时及本轮大图测试没有再次出现该错误。历史事件保留为证据不足，不能写成已找到精确根因，也不应通过宽松解码或自动重放掩盖它。
