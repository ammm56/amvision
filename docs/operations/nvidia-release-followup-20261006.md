## 已定位与修复

### WebSocket 背压断言

旧 `websockets.legacy` 协议在写入暂停时只允许一个 drain waiter，业务发送和心跳发送并发进入该路径会触发 `waiter is None or waiter.cancelled` 断言。已用隔离协议对象复现，不依赖猜测实际连接。

服务 launcher 和 Windows reload server 默认选择 Uvicorn `wsproto` 后端，依赖固定 `wsproto==1.3.2`，继续关闭 `permessage-deflate`。不选择当前缺少相同写入暂停处理的 SansIO 实现。回归覆盖写入暂停、并发 ping/pong、恢复发送和压缩协商拒绝；业务接口和 JPEG 编码不变。

两轮结束后审计完整 HTTP 日志，又发现 7 次客户端断开时的 ASGI 堆栈：Runtime Preview 的 `finally` 再次关闭已由 wsproto 完成握手的连接，只捕获 `RuntimeError`，遗漏 Starlette 转换后的 `WebSocketDisconnect`。已在 Runtime Preview 和 Preview Session 的清理关闭路径补齐断开异常处理，先释放订阅/任务并保持内存清理执行。新增真实 wsproto 连续 20 次客户端关闭握手回归，订阅全部释放、无 ASGI 错误。此次收尾修复发生在两轮一小时之后，单独验证，不声称长测使用了该最后补丁；原始 7 次错误保留在 `fixed-http-session.log`。

收尾补丁通过 `assemble-release` 重新生成，再更新隔离发行 app。最终 bundled Python 加载发行目录路由重新运行背压及连续 20 次关闭握手验证，通过且无错误日志（`final-release-wsclose.json`）。源码与最终发行文件哈希一致（`final-source-package-hashes.json`）。

### 初始化预算

Bundled Python 冷导入训练框架累计约 20 秒，尚不包含完整 Worker 初始化和并发启动资源竞争。full launcher 每个 worker 的默认初始化预算从 30 秒改为 120 秒；只有收到真实就绪状态才完成启动。默认启动已实测成功。该预算不改变推理或 Workflow 请求超时，不引入请求等待队列。

### 逐次新建推理线程

Deployment 子进程原先每次 `infer` / `infer_batch` 创建新的 `Thread`。使用同一真实分类权重、固定真实图片裁剪和 bundled Python，分别在独立进程执行 200 次推理：

| 设备 | 逐次新线程 | 常驻线程对照 |
| --- | --- | --- |
| CPU | 私有内存约 1.00 GiB → 1.93 GiB，后续持续增长 | 预热后约 1.02 GiB，未出现相同增长 |
| CUDA | 第 20 次以后仍持续增长，GPU allocated/reserved 基本固定；200 次约 95.87 秒 | 第 20–200 次主机内存稳定；200 次约 5.26 秒 |

对照仅用于定位线程生命周期及库资源复用，不等同于完整工作流吞吐或模型准确率验收。它复现了主机侧持续增长与反复线程初始化成本；不能把所有历史 30 秒超时直接归因于同一原因。

修复为部署级常驻推理线程槽：数量等于 `instance_count`；满载立即拒绝，无等待队列、无自动重试；完成后释放请求闭包引用。单图、批次的输入输出、模型预后处理、LocalBuffer 协议不变。新增容量拒绝、线程身份复用、异常回收、请求引用释放及在途停机测试。停机失败时不提前关闭父进程监视或释放在用模型/mmap。

## 续测中的失败与限制

- 第一轮 TensorRT 长测在约 5 分钟后进程退出，未记录正常关闭或异常堆栈；不计作一小时通过，退出原因未确定。
- 该轮一次 Preview 的 Base64 解码失败，尚未稳定复现；已补充不含图片正文的底层错误原因。重启并完成启动后，相同图片连续三次预览成功，完整接收耗时 4.26–4.69 秒，每次六份临时资源释放；三次成功不抹除之前失败。
- 一次探针在 daemon 尚未就绪时调用，返回 mmap 探测失败；后续探针先确认 `/api/v1/system/status` 的 `ready=true`。
- 第二轮 TensorRT 基线期间状态查询、真实调用、目录变化和页面数据流可运行，但发现线程问题后主动停止，保留 `trt-hour-run2/interrupted.json`；不把该未满一小时轮次算作通过。
- 修复前 CUDA 两路各 12 次分段调用成功，但不足以证明此前超时已消失。旧一小时私有内存增长主要位于两个 PyTorch 模型进程，且五分钟分段中持续增长，不能解释为已经达到稳定平台的缓存。

### 延迟与显示链路的限制

完整调用包含大 BMP 传输、传统视觉前处理、分类和图片/结果落盘，不能作为单次模型推理延迟，也不能直接把两个不同工作流的 HTTP 与 ZeroMQ 数值作为协议性能对比。

CUDA 治具首尾十分钟 P50 为 4.825 / 6.301 秒，塑盒为 2.656 / 3.349 秒，存在明显波动；本轮不能证明所有性能指标已达标。机器仍有其他 GPU 应用，未做独占资源对照，不据此断言波动由其他应用造成。

一小时样本结束后另采集节点耗时（`final-node-timings.json`），与正式小时样本分开：

- 两个显示 Runtime 单次完整调用约 7.37 / 8.86 秒。主要耗时在每轮执行的 Storage Retention Cleanup 目录遍历，单节点约 0.59–1.79 秒，随文件积累会增加扫描成本。此次发现的是显示工作流反复扫描的配置/调度性能问题，不能据此把模型调用变慢全部归因于磁盘扫描。
- 治具额外调用约 7.94 秒，其中 Hough 并行段约 3.40 秒，两路分类节点各约 0.65 / 0.54 秒；塑盒额外调用约 4.46 秒，两路分类节点各约 1.53 / 1.49 秒。并行结束节点包含子节点时间，不能将这些耗时重复求和。
- 两次额外检测仅写入隔离验收目录，不计入正式小时的调用量。后续应将保留期清理从高频显示刷新中独立调度，或设计明确的清理执行间隔与有界扫描；保持最旧文件优先、期限边界和目录防护。未在本次长测后临时改动清理语义而跳过重新验收。

## 结论边界

固定线程复用、WebSocket 后端和初始化预算修复已通过针对性测试及真实发行环境验证。两轮各一小时未发生 CUDA 调用超时、WebSocket 断言或共享内存未释放；明确满载仍直接拒绝，没有增加推理队列或自动重试。
