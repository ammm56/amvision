# JSONL 增量记录与汇总规模验证

日期：2026-09-18。

## 结论

现有 Append JSONL 与 File Summary 在提交元数据、汇总检查点有效时，不随历史总行数重新扫描日志。百万条记录测试中，单条追加加增量汇总的 30 次测量最大为 25.683 ms。该结果不代表整个 Workflow、图片读取、模型推理或浏览器显示的耗时，也不是最坏情况的 1 秒保证。

汇总检查点缺失或配置改变，需要分批重新归约全部历史；提交元数据缺失，需要同步校验整个日志。两种恢复均不能保证 1 秒内完成。

## 实现核对

- `backend/service/application/runtime/io/jsonl.py`：正常追加编码一条记录，持久化写意图、日志和提交元数据。读取使用字节游标 seek，不从头跳过历史行。正常读取不持生产日志写锁；恢复元数据时才尝试获取锁。
- `backend/nodes/core_nodes/support/file_summary.py`：检查点包含规则签名、累计结果、最新匹配记录、游标、未完成批次的目标边界和结果修订号。读取检查点并继续归约新增行；无新增内容时不重写检查点。每次另读取首行核对源文件，不归约整段历史。
- `checksum` 校验汇总 body，不是整个 JSONL 的内容校验。managed 模式要求已提交历史内容保持不变；不能按可任意编辑的普通 JSON 文件使用。
- 汇总无效、归约规则/过滤条件改变、源文件代次改变会触发重新计算。`snapshot` 模式的文件身份含长度和修改时间，不适合作为持续追加日志的增量汇总模式。
- 读取预算约束记录处理循环，不是磁盘 IO、文件锁、元数据恢复、持久化写入及整个 Workflow 的硬截止时间。
- `complete=false` / `status=loading` 表示仅处理到当前游标，不能视为最终累计。节点不会自行在后台运行到完成，后续调用继续处理。测试中的连续调用不包含实际工作流刷新间隔。
- `.commit.json` 丢失后的重建在本次规模测试时为 30 秒上限，随后按使用要求调整为 180 秒（3 分钟）；仍遵守更短的节点或 Workflow deadline。恢复持有日志路径写锁；更大日志或较慢磁盘可能超时，其他写入会明确报忙，不排队等待。

## 测试条件

Windows、conda amvision，在仓库 W 盘 `.tmp/jsonl-scale-audit/` 创建隔离日志。使用现场治具日志最后一条的真实字段结构，每行 390 字节，重复生成 10 万、100 万条。图片仅保留路径字段，不读取图片。此测试未向 D 盘生产日志追加数据。

种子文件批量生成后，使用真实 `_rebuild_commit` 校验生成元数据。追加、归约、文件 fsync、原子替换和路径锁均使用现有实现。汇总参数为 managed、max_records=10000、max_bytes=4194304、max_ms=100，归约为三个物料字段 sum 和盘数 count。单进程顺序测量，不包含 Worker 调度、并发压力或磁盘冷缓存保证。每种稳态操作测量 30 次。

| 场景 | 10 万条（39 MB） | 100 万条（390 MB） |
| --- | ---: | ---: |
| 追加单条，中位 / 最大 | 8.195 / 10.386 ms | 8.454 / 9.640 ms |
| 新增一条后汇总，中位 / 最大 | 12.089 / 15.273 ms | 13.089 / 14.790 ms |
| 追加并汇总，含外层路径锁，中位 / 最大 | 21.575 / 26.501 ms | 22.460 / 25.683 ms |
| 无新增时读取汇总，中位 / 最大 | 4.604 / 6.063 ms | 6.411 / 9.201 ms |
| 汇总从零重建总耗时 | 2492.168 ms | 27303.771 ms |
| 汇总重建批次数 | 23 | 237 |
| 单批重建最大耗时 | 115.206 ms | 128.080 ms |
| 提交元数据全量重建 | 1330.783 ms | 14256.623 ms |

所有成功样本都核对累计值、记录数与完成标志；无新增调用还核对检查点修改时间未变化。

## 保留的失败与恢复证据

第一次 10 万条测试在更新汇总时，`atomic_write_bytes` 的 `os.replace` 出现一次 `PermissionError: [WinError 5]`。当时日志已提交至第 100013 条，检查点停在第 100012 条。随后重新调用现有汇总函数，成功补算至 100013 条，累计值严格匹配，没有漏计或重复计数。

第二次使用全新隔离文件完成上述全部测量。第一次失败仍保留，不能因复测成功而宣称问题不存在。具体导致 Windows 拒绝替换的因素尚未定位，不能据此归因于杀毒软件、并发读者或特定修改。未添加自动重试、队列或绕过持久化保证。

回归验证：`python -m pytest tests/test_file_summary.py tests/test_managed_jsonl.py -q --basetemp=.tmp/jsonl-scale-pytest`，32 项通过。

后续恢复上限调整只影响异常扫描路径；使用模拟时钟覆盖 31 秒、179 秒可以恢复，以及 181 秒拒绝发布并保持原日志不变，不以真实等待代替边界验证。调整后同组回归 35 项通过，修改 Python 文件的 Ruff 检查通过。

## 使用与后续边界

- 实时统计保留有效的日志提交元数据与汇总检查点；正常进程重启可从磁盘检查点继续，不必从零累计。
- 如需限制单文件恢复成本，可按统计周期切分日志，并同步配置对应汇总路径与统计范围；不能悄然改变累计产量的含义。
- “每次正常增量调用低于 1 秒”在本次测试有充分余量；“百万条全量重算也低于 1 秒”不满足。数百万条未直接测试，不能仅按行数线性推算作验收。
- Windows 替换文件失败的后续复现与修复见 [Windows 文件替换故障修复](windows-file-replace-audit-20260918.md)。已验证同类句柄冲突并修复，历史单次事件的具体占用进程仍不可追溯。长期并发与现场磁盘性能仍需对应环境验证，本次不构成长时间稳定性验收。
