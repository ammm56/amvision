# NVIDIA 发行与一小时运行验收（2026-10-05）

## 范围与环境

验收目录为 `release/nvidia-acceptance-20261005/full-windows-x64-nvidia/`，使用 HTTP 5610、ZeroMQ 5655–5660，与原开发业务数据隔离。从源码执行 `assemble-release`，沿用已正式发布的 self-contained x64 桌面启动器资产，复制 NVIDIA bundled Python 后执行发行布局校验。完整栈通过随包 Python launcher 启停。

本机 GPU 为 NVIDIA GeForce RTX 3060 Laptop GPU，6 GiB 显存，驱动 595.79。发行校验确认 Python 3.12.13 x64、CUDA 可用、PyTorch CUDA 12.6、TensorRT Python 10.16.1.11 / trtexec 10.16.1 匹配。此结果不替代其他客户机驱动和设备验证。

通过正式 API 导入四个真实 OpenVINO CPU 部署包，重建八个 Runtime 和八个 Trigger。另外用同一批已训练 YOLO11 分类权重建立两个 PyTorch FP32 CUDA 部署，每个保留两个实例及满载立即拒绝策略；将隔离的 3570 治具及塑盒工作流指向 CUDA 部署。原开发应用和配置未作这些替换。

## 验收中发现的问题

两个真实显示应用共用相同生产日志和汇总检查点。持续更新时，File Summary 的 CAS 检查把同规则的另一个读取者先提交缓存视为业务失败，应用模式实际显示“检查点已由另一调用更新”。HTTP 就绪状态仍为正常，说明只测 `/system/status` 不能替代业务结果验收。

修复保持日志为权威数据、检查点为派生缓存：锁争用跳过缓存发布；同规则、同代际的并发缓存提交保留已有缓存，并返回本批已计算的不可变快照。不等待、不重试、不合并或重复累计、不覆盖先提交者的进度。不同规则、不同代际、损坏内容及相同游标但结果不同仍报冲突。相关 JSONL/File Summary 测试 41 项通过，Ruff 通过。源码修复后重新组装，停止验收服务，再使用组装产物更新程序文件。

另有首轮治具调用返回 failed，但旧测试探针未保存完整错误对象，不能据此确定该次根因。已补充探针失败证据记录，保留原失败轮次。之后真实捕获到 Preview 与 Runtime 同时占用两实例时的“推理实例已满载”，这是正常容量拒绝；不能把先前缺少详情的失败追溯性断言为同一原因。

一小时轮次还发现两个独立问题：

- File Summary 一次报告 `file_access_denied`，目标祖先变为 `\\?\W:\$Extend`。隔离文件并发替换实验真实复现 `Path.resolve()` 返回 NTFS `$Deleted` 中旧文件名。原子替换期间普通文件的句柄身份不能作为后续写入目标。源码新增稳定文件位置解析：仅解析父目录并保留文件名，显式符号链接按链接目标解析；节点输入、写锁键、write journal 和文件保存位置统一采用该规则。目录路径及删除保护不改。完整一小时观察结束后才停止进程、重新组装并验证此修复，未把修复前后结果混为一轮。
- 状态接口 503 的明细为塑盒 Runtime 未运行、对应 Trigger 依赖不可用，六个模型部署仍就绪。Runtime 事件记录表明执行响应超时后 worker 被回收，再按期望状态自动恢复；这不是状态接口把正常满载误判为未就绪。仍需区分超时的计算、IPC 和机器资源因素，不能仅扩大超时值掩盖问题。

约第 48 分钟，3570 显示应用的目录监听线程因 `path is on mount '\\\\?\\W:', start on mount 'W:'` 停止；六个模型和八个 Runtime 仍正常，状态接口正确报告该 Trigger 不可用。筛选和构造事件之间重复调用 `Path.resolve()`，原子替换期间路径表示可能变化。修复为解析一次稳定文件位置后再筛选和构造事件，并隔离单条不可解析的变化，防止终止整条监听。此次未在一小时中途重启监听，保留持续故障及页面停留在 16:34:40 的证据。

本机同时运行其他 GPU 程序，显存占用明显波动。验收不结束其他程序，不将共享环境下的全部时延变化直接归因于视觉代码。

## 一小时验证方法

服务全部自动恢复后，正式观察从约 15:46:53 开始，预定持续完整 3,600 秒。此前短测及中断轮次不合并计时。

- .NET SDK 两个长生命周期 client 分别持续同步调用 HTTP Runtime 与 ZeroMQ Trigger；每次使用独立请求标识，不重试失败调用。
- 治具样本期望 24 个空槽；塑盒样本期望 72 个合格槽、8 个问题槽。逐次核对返回字段和请求身份。
- 每十分钟执行一次带 5 秒 Delay 的真实 Preview，检查展示资源确认、断线重连和会话释放；满载拒绝单列。
- 每秒采样状态，每十秒采样进程私有内存、句柄和 LocalBuffer，每三十秒采样 GPU 温度、显存和利用率。
- 持续订阅两个显示 Runtime 的实时结果帧，记录执行状态和错误，不重复保存图片正文。
- 开始与结束记录 JSONL 统计和触发器健康计数；原生产日志以 SHA-256 检查未变化。

测试探针增加 `duration_seconds`、失败响应保留和每 30 次调用的进度文件，仅属于验收程序，未修改 .NET SDK 生产调用协议。`continue_on_workflow_failure` 表示保留失败后发起下一次独立测试调用，最终失败计数不清零，不是自动重试。

## 结果

完整调用窗口为 2026-10-05 15:46:54 至约 16:47，持续 3,604.265 秒，排空及最终快照于 16:47:09 完成。**本轮不通过生产验收**，正常满载拒绝与非预期错误分别统计。

| 链路 | 成功调用 | 中位完整耗时 | P99 完整耗时 | 异常 |
| --- | ---: | ---: | ---: | --- |
| 治具 HTTP Runtime、CUDA FP32 | 481 | 6.817 s | 16.476 s | 2 次推理响应超时；12 次明确满载拒绝 |
| 塑盒 ZeroMQ Trigger、CUDA FP32 | 760 | 4.255 s | 8.908 s | 4 次超时；19 次 failed |

两条流程的业务、ROI 数量和传输路径不同，不能用此表比较 HTTP 与 ZeroMQ 的性能。塑盒旧探针只读取 envelope 内的错误，没有采集 TriggerResult 顶层 Error，19 次 failed 不具备完整错误详情，不将其直接归类为正常满载；后续探针已修正错误采集位置，SDK 生产接口不变。6 次 Preview 中 2 次完成、4 次明确满载，符合两实例立即拒绝策略。

- 481 次治具成功调用增加 481 条日志、11,544 个 OK 物料；760 次塑盒成功调用增加 760 条日志、60,800 个物料，其中 OK 54,720、NG 6,080。与逐次期望值完全一致；原 `D:\摆盘机\记录` 校验文件 SHA-256 未变。
- 935 / 786 帧两路显示订阅无连接观察器错误，4570 显示出现一次前述文件路径异常；3570 显示因监听退出而停止更新。
- 状态定时采样记录 728 次 503，其中后段主要由监听退出持续产生。开始阶段 .NET 同步状态查询 1,000 次均 ready，中位 2.079 ms、P99 7.403 ms；全小时成功 HTTP 样本中位 16 ms、P99 250 ms。短测成功不能替代后续故障证据。
- 排空后 LocalBuffer 活跃租约、已分配容量、活动借用、隔离容量均为 0，容量分配失败计数均为 0。两个 CUDA 部署仍各有两实例就绪且 idle、无 pinned output；未发生模型进程重启。
- 发行栈私有提交内存各十分钟窗口中位值从 20,307.84 MiB 升至 21,650.08 MiB（约 19.83 GiB 至 21.14 GiB），峰值 24,903.64 MiB，存在波动及上升趋势；这既不能证明永久泄漏，也不足以宣布内存长期稳定。SDK 记录的 GC 堆值未执行完整 GC，不作为泄漏结论。
- 官方停止入口成功，所记录的 34 个进程身份全部退出，运行状态文件清理完成。

修复后重新执行 `assemble-release` 并更新隔离包；发行目录校验通过，相关回归 **95 项通过、1 项符号链接权限不足跳过**，.NET 合约程序构建无警告错误并通过合约测试。重启曾因训练 Worker 超过默认 30 秒初始化预算而整栈退出；保留该失败，随后使用已有参数 `--worker-ready-timeout-seconds 120` 重新启动。此参数只改变启动预算，不改变生产调用超时。

## 修复后的独立验证

修复后 CUDA 并发回归持续 61.375 秒，仍发生推理响应超时及后续明确满载拒绝，状态记录 5 次不可用；本次没有并发 Preview，因此不能把全部超时归因于 Preview 竞争。该短测仍不通过。两路显示订阅无观察器错误，未再次出现上述文件路径、缓存提交冲突或目录监听退出；短测结束时目录监听仍 running。停止 CUDA 部署并排空后，LocalBuffer 租约、已分配容量、借用和隔离容量再次归零。

浏览器打开隔离发行包应用模式，目录变化触发后页面更新到 17:09:04，并显示对应图片及生产统计。双击进入大图后，JPEG 图片和左上角数据面板正确显示；本轮没有修改用户开发环境的工作流或保存其页面草稿。

### TensorRT 转换、部署与真实数据

以同一真实 YOLO11 分类权重执行 ONNX 导出、数值校验和 TensorRT FP32 引擎构建，严格模式禁用 TF32。第一次构建因 CUDA 内存分配失败结束，原始失败保留。重新提交的第二次转换任务成功，不将失败轮次覆盖为成功。本阶段停止了本轮 PyTorch CUDA 部署以释放资源，但构建期间机器仍有其他 GPU 应用，未实施干净 GPU 环境对照。

- ONNX 数值验证通过，最大绝对误差约 `7.45e-8`。
- TensorRT runtime smoke 的 finite、allclose、passed 均为 true，最大绝对误差约 `8.94e-8`。这是导出样本的数值一致性检查，不代表完整数据集精度验收。
- 部署两实例均 healthy、warmed，随后通过仓库内 .NET SDK 同步执行 5 次真实治具工作流，全部返回 24 个空槽、OK、无问题槽。
- 完整调用耗时分别为 2.641、2.698、2.086、2.381、2.262 秒，中位 2.381 秒。包括约 60 MB 图片 HTTP 上传、工作流处理和结果保存，不能当作模型独立推理耗时；未达到一秒内的整链路目标。
- TensorRT 仅完成上述短测，未完成独立一小时持续运行。常驻实例保留的 24 字节 pinned output 为健康接口报告的输出缓冲区，不能与 LocalBuffer 未释放租约混淆。

最终快照确认 LocalBuffer 活跃租约、已分配容量、借用、隔离容量全部为 0；再次验证原生产日志 SHA-256 未变化。通过官方停止入口结束最终隔离发行栈，记录的 33 个进程身份全部退出，无残留；原开发服务不在停止范围内。

收尾检查另发现开发 HTTP 5600 无监听、连接被拒绝，5601 前端仍监听；开发热重载进程 32228 及其子进程 25224 仍存活，子进程启动时间为 16:39:09。它们使用 conda 解释器，不属于本次停止的发行栈。未执行重启或终止以覆盖现场，此现象尚无异常堆栈，不能认定与发行栈停止有关，也不能报告开发服务当前健康。
