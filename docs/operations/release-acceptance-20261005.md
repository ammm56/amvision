# 0.1.8 CPU 发行验收（2026-10-05）

## 范围

当前四个真实部署均为 OpenVINO CPU，因此选用 `full-windows-x64-cpu`。验收包位于 `release/acceptance-20261005/full-windows-x64-cpu/`，HTTP 使用 5610，六个 ZeroMQ 入口使用 5655–5660。模型、数据库、监听目录、图片及 JSONL 均隔离于原开发业务目录。该目录包含验收数据，不是空白交付包。

由当前源码发布 self-contained x64 启动器并执行 `assemble-release`，复制既有 CPU Python 到验收目录后校验。全部服务和 Worker 使用验收包自己的 Python 3.12.13；未依赖开发 conda 来运行发行服务。浏览器加载发行静态资源，没有使用 Vite。

## 发现与修复

### 依赖约束与发行校验不一致

现有 CPU Python 安装了 Uvicorn 0.51.0，而 Windows HTTP 接入实现和发行门禁只验证了 0.48.0。两份 requirements 原先没有直接约束 Uvicorn，可能随 FastAPI 的间接依赖升级。

修复：CPU/NVIDIA requirements 统一显式要求 `uvicorn[standard]==0.48.0`；增加组装产物检查。本次仅修正验收副本中的 Python，原 CPU/NVIDIA 包没有改动。修正后 `validate-layout` 通过，`pip check` 无损坏依赖。

### multipart 同步调用阻塞 HTTP 事件循环

第一轮并发实测中，60 次真实调用成功，但 .NET 同步状态探针在保持 3 秒超时的情况下失败。另一条状态采样链路的最慢响应为 3094 ms。直接检查代码发现：`async def invoke_workflow_app_runtime_upload` 在事件循环中调用同步 `invoke_workflow_app_runtime_with_response`，推理的同步 IPC 等待阻塞了 HTTP 处理。

修复：两个 multipart 路由的同步 Runtime 查询、同步调用/提交通过 `run_in_threadpool` 执行。对外同步接口仍等待本次执行完成后直接返回，不增加业务排队、重试或后台任务；Runtime、ZeroMQ、LocalBuffer 和模型计算不变。

新增四个防阻塞用例覆盖同步调用与异步提交、Runtime 查询与执行两个阶段；同一事件循环必须能够解除模拟等待，并且调用不得提前返回。相关 API、状态及防阻塞测试共 39 项通过，发行组装和运行时校验测试共 26 项通过，Ruff 检查通过。

修复后重新执行 `assemble-release` 到 `release/acceptance-20261005/rebuilt/`。验收服务完整停止、核对进程退出后，使用重新组装的 `app/` 程序文件更新验收包；不在发行目录手工编辑源码，保留原验收数据用于前后对照。

## 已完成的链路检查

- 通过正式接口导出四个真实部署包，逐包 `ZipFile.testzip()` 检查 CRC，通过发行端正式导入接口导入。
- 复制八个活动发布的应用/模板，重建八个 Runtime 和八个 Trigger；只重映射部署、Runtime、端口和隔离路径。
- 全部资源达到部署 4/4、Runtime 8/8、Trigger 8/8；完整停止后，重启自动恢复同一资源集，无需逐个手动启动。
- 已验证三次优雅停止，最后一次记录的 32 个进程身份全部退出，5610 监听关闭，运行状态文件清理；开发服务仍就绪。
- 首轮真实调用为治具 HTTP Runtime 30 次、塑盒 ZeroMQ 30 次，并发一个带 5 秒 Delay 的 Preview；全部业务结果正确，Preview 资源接收确认及会话释放成功。
- 目录监听自动驱动显示工作流。首轮后治具显示 768/768/0，塑盒显示 2720/2480/240、NG、91.18%；与隔离 JSONL 一致。双击大图保留同一份统计。
- 客户端主动请求 WebSocket deflate 扩展时，服务端协商结果为空，确认压缩关闭。
- 首轮结束 LocalBuffer 2 GiB 全部空闲，活动 lease/borrow、隔离资源及分配失败均为 0。原生产 JSONL 的 SHA-256 未变化。

## 修复后复测

保持原 3 秒 SDK 状态调用超时、相同模型和图片、相同并发方式，重新启动修复后的发行代码。约 90.45 秒后观察到部署 4/4、Runtime 8/8、Trigger 8/8 和完整启动器服务栈均就绪；这是本机观察值，不是启动时间保证。随后并行执行约三分钟：

SDK 每次治具结果均为 24 个空槽；塑盒满盘样本每次为 72 个合格槽及 8 个问题槽。两轮测试加原隔离基线后，治具 JSONL 为 62 行、1,488/1,488/0；塑盒满盘为 64 行、5,120/4,640/480；塑盒空盘保持 1 行、80/80/0。全部记录所引用的图片及结果 JSON 存在且位于隔离目录。浏览器再次运行显示工作流，应用模式和双击大图显示 NG、5,120、4,640、480、90.63%，与磁盘统计一致。原生产 JSONL 的 SHA-256 再次确认未变化。

第一轮 .NET 状态超时保留为失败证据。修复后同一期限复测通过，没有通过放宽期限验收。复现结果及原失败记录保留于验收包的 `logs/acceptance/`，汇总为 `summary.json`；测试配置和临时脚本不作为长期交付物。

验收服务停止后再次执行 `validate-layout`，结果为 `valid=true`。清理 `.tmp/release-acceptance-20261005/` 的请求被自动审批以 `blocked by policy` 拒绝，未重试绕过；该临时目录暂存，待允许清理时移除。

## 结论与验证边界

CPU 发行包本轮功能验收通过：真实模型导入、随包运行时启动、自动恢复、同步 SDK 调用、并发预览、磁盘统计、浏览器展示及优雅停止均取得实际验证。此次发现的依赖约束缺口及 HTTP 事件循环阻塞已修复。已有原 CPU 发行目录未被修改，正式发布仍须按新源码重新组装并校验 bundled Python。

验收覆盖 CPU 完整服务栈的真实导入、启动、恢复和调用。NVIDIA profile、GPU 推理、现场外部调用方、断电与磁盘损坏、24 小时以上长稳均不由本轮短测代表。桌面启动器已正式发布且发行清单校验通过；本轮完整栈通过随包 Python launcher 启停，不把它表述为桌面窗口/托盘交互验收。

本轮没有对每个模型进行带标注数据集精度评估，也没有覆盖全部八个工作流的业务输入组合。30 次业务样本不足以给出可靠的高分位延迟承诺；首次 HTTP 调用包含冷态成本且达 9.18 秒，不能声明全部调用一秒内完成。并发 Preview 尚需按业务目标另设暖运行性能门禁。资源回收通过不等于已证明长期不存在内存增长。
