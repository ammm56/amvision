## 已确认问题

### P1：空目录清理越过 junction 和内部控制目录边界

位置：`backend/service/infrastructure/filesystem/retention_files.py::delete_empty_local_retention_directories`。

该函数使用 `os.walk(topdown=False, followlinks=False)`，直到已经进入子树后才检查当前目录名称和 reparse 属性。Windows junction 不等同于符号链接；本机实际遍历进入了 junction 目标。`.amvision-*` 目录的下级目录同样未被提前排除。

隔离复现：

1. 创建 `root/redirect` junction，指向同一测试工作区内、但位于清理 root 之外的 `outside`。
2. 在 `outside` 创建 `empty-child`。
3. 对 `root` 调用空目录清理。
4. 结果 `removed_count=1`，`outside/empty-child` 被删除，junction 本身仍然存在。
5. 对 `root/.amvision-protected/child` 重复验证，控制目录本身保留，但空的 `child` 被删除。

这是删除目标范围之外的空目录，不是已证明会删除目标之外的非空文件。普通文件扫描已经跳过 reparse/control 项，不能将其保护能力等同于空目录清理也正确。

### P1：删除空目录与新文件保存存在并发冲突

位置：上述空目录清理函数，以及 `backend/nodes/save_locations.py::_write_filesystem_bytes_atomically` 等保存路径。

可发生的顺序：保存创建日期目录 → 清理发现目录为空并删除 → 保存创建临时文件失败。文件级路径锁不覆盖父目录的创建和删除，清理目标级锁也不与 Save 协调。

在真实 Save helper 创建临时文件前注入一次空目录清理，稳定得到 `InvalidRequestError`，原因异常为 `FileNotFoundError`。通用 `atomic_write_bytes` 路径同样复现，失败阶段为 `create_temporary`。这是确定性并发交错复现，不代表已在现场观测到该故障。

当前九个节点均开启删除空子目录，因而具有此风险。关闭该选项可绕开本次已复现的两类空目录问题，仍然按期限删除普通文件，但不是缺图或大目录耗时问题的解决方案。

### P2：显示工作流依赖的最后一张图片可能被正常清理

清理保留统计 JSONL 和汇总状态，但超过一个月未生成新图片时，最后一条统计引用的图片也会过期。现有六个业务 Load Local Image 节点仍按路径直接读取；`use_blank_image_when_empty` 仅处理空输入，不处理磁盘路径已不存在。图片删除后，显示工作流可能失败。该边界经源码和实际编排确认，本次未删除现场图片复现。

### 性能与诊断边界

- `delete_limit` 限制删除数量，不限制扫描时间。每次工作流调用均完整扫描九个目录；空目录清理还会再次遍历。
- 扫描/删除循环未主动检查 ExecutionControl 的取消与截止时间，不能将删除上限视为执行时限保障。
- `PathWriteCoordinator._InterprocessPathLock.try_enter` 将 `_try_lock_file` 的所有 `OSError` 都作为竞争失败返回，未区分真正的锁冲突和其他系统错误。属于代码审查发现，未制造现场锁服务故障。
- 权限和未知 I/O 错误会使节点失败；同一工作流中的清理失败可能导致显示工作流失败。删除是逐文件副作用，不具备整批回滚语义。

## 修复顺序

1. 空目录遍历必须在进入子树之前排除 reparse/junction 和内部控制目录，并增加对应 Windows 回归用例。
2. 明确空目录删除与 Save 的父目录生命周期协调；不能仅凭“目录为空”判断可以安全删除正在创建的生产目录。先关闭空目录删除可以作为明确、可逆的配置缓解措施。
3. 对已过期缺失图片设计显式的存在检查与占位图分支；只处理文件不存在，不能吞掉权限、损坏等错误。生产数量仍由保留的 JSONL 计算。
4. 锁错误分类、取消检查和错误诊断补齐后，验证占用、并发保存、目录被外部删除、取消和进程中断场景。
5. 大规模清理优先由独立维护 Workflow 经外部调用触发，或显式接受显示工作流调用增加的扫描时间；不引入隐藏队列、定时线程或自动调度。

修复后重复真实预览、并发交错用例和文件规模测试，再进行现场长时间运行验证。
