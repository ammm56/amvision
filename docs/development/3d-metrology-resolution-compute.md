- U 最小、V 最小的分位端点均为缺低侧邻居的格边估计，真实邻格点数为零。半格相位使边界坐标平移 0.015 mm。

独立连续矩形测试验证格边估计、缺邻格标识与原始行语义；它不提供本工件缺测真实边的位置，也不把格宽变成通用准确度保证。当前可见包络方法保持显式 `estimated` 来源。若现场精度不能接受该敏感性，应另行确定真实边点估计或采样要求，不能通过修改门禁、平均相位或填入手工报告值处理。

## 3. 优化依据与等价边界

### 10.2 测到的成本与未采用方案

同一实际 A_top_L 输入上，直接构造 CSR 及不同树叶大小的后续对照均保持完整邻接/标签，但约 0.266–0.285 秒，原 query_pairs/COO 路径约 0.213 秒，未采用。此前逐行邻域和距离矩阵也未显示收益；不能把试过的替代实现全部写入生产。

2. 半圆分别记录物化/局部选择、投影/重复/秩、原生 Delaunay、覆盖/面条件/边、截面校验、正反原生求交、来源匹配和拓扑整理。明确哪部分是库内计算，哪部分是项目包装，不使用逐行跟踪后的墙钟当正式节拍。

4. 沿现有配置记录实际数值线程库。局部旧/新候选在同进程交替各三次，记录全部值及工作集，不在计时内同时做几何对比或资源轮询。两平台顺序执行；不调系统电源、亲和性或显示设置。

如果某个拟优化阶段本身耗时很小，先停止该候选，不据此重复全链路。局部证据只说明有无等价收益，不预先承诺可以累计出 10 秒结果。

### 11.3 第二步：半圆路径的候选与边界

首选验证现有 `boundary_section.py` 对库接口的使用，不重写三角剖分或求交算法：

- **复用点积。** 当前先计算 `dots = local @ normal` 供来源判断，原生求交随后又计算点积。本机受控 trimesh `5.1.1+amvision.2` 的 `mesh_plane` 已具备 `cached_dots`。先单独验证传入同次点积以及反法向对应值，覆盖正负零、容差相等、倾斜、远原点和尺度变化；不能假设取负或换矩阵算式总是逐位相同。发生符号/线段/失败原因差异就不采用该路径。
- **仅减少原生求交的候选面。** 库的 `local_faces` 返回原网格面号，可用原有符号和显式容差生成保守候选：保留跨越两侧的面及含零符号的面，只排除可证明严格同侧且无零符号的面。全部原面仍先完成索引、退化、共面区域等既有检查；不是从 Delaunay 中删点、缩 ROI 或跳过坏面。候选按原面序传入，正反两次调用及同源端点一致性检查保留。
- **来源匹配的块处理。** 仅当阶段证据显示逐线 Python 来源匹配仍显著占时，才在现有函数内评估有界批量计算。仍按库输出次序消费端点，保留全部源边、权重、源面、重复边归属和取消检查，不用坐标近邻合并不同来源。没有收益则保留当前实现。

以上逐项验证、逐项决定，不能一次混改。已有[官方接口](https://trimesh.org/trimesh.intersections.html#trimesh.intersections.mesh_plane)支持点积缓存和限定面集；实施以本机锁定受控版本源码为准，不因在线文档版本更新就升级依赖。

原生 Qhull 若仍占主要时间，本批不尝试无依据换选项、点序、坐标精度、分块独立剖分、抽样或只取边缘点。这些可能改变共圆选边、支持拓扑或失败语义，不属于已批准的等价包装优化。也不引入跨 Run 网格缓存；有实证的新算法方向应单独说明和审核，不能宣称当前成本是理论下限。

### 11.4 第三步：钢片精确距离分区

仍沿 `envelope_selection.metric_membership` 使用 SciPy `cKDTree` 和 `connected_components`，保留全部正/负侧目标点、原 `connection_distance`、`eps=0`、完整邻接、种子歧义及缺测规则。

重点评估尚未做过的**索引宽度和图数据转换**：本机 SciPy 图校验路径存在 `astype(float64, copy=False)`；当前图 data 是 uint8，点对索引由库返回。先证明实际调用中的转换、复制、排序分别占多少，再比较合适存储类型的公共 COO/CSR 构造方式。不能把源码存在转换直接认定为主要根因，也不能保证预先改为 float64 更快。

若评估局部 int32 稀疏索引，必须同时核对顶点上界、边数和 CSR 末端指针是否可表示；大数据仍选择能完整表示的类型，不截断邻接。点云公开 source_indices、资产、SDK 和 64-bit 进程边界不变。这是算法临时数组存储选择，不是新增 32-bit 平台或兼容协议。

保留“计数后、分配前”的原工作预算准入。不得直接删除 `count_neighbors`，等全部边分配完才发现超预算；不得用近似查询、邻居上限、分块截边、只保留种子附近或自写并查集代替完整图。没有明确、独立证明前也不使用 SciPy 私有原生入口绕过校验。公开行为依据为 [query_pairs](https://docs.scipy.org/doc/scipy/reference/generated/scipy.spatial.cKDTree.query_pairs.html) 和 [connected_components](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csgraph.connected_components.html)。

候选必须在十二对象上统一核对邻接对、连通标签、组件数、种子目标、全部实测源行、格占用和剖面。小型独立真值覆盖孤立点、精确重复点、多个分量、半径等号及 nextafter 两侧、种子命中多个目标、过密预算拒绝和取消。不能只凭 A_top_L 尺寸一致通过。

### 11.5 第四步：组合正确性与 Preview 未闭合项

通过局部对照后再集成，复用现有三维测试。半圆比较全部面/边数组、相交源边/面、权重、端点和有序拓扑；共面整片仍无效，共面边仍正反对称。包络比较全目标归属、生成来源和所有剖面，不只比较最后的 L/W。50 项数值继续原 `1e-7 mm` 绝对误差及原 valid/reason，不放宽任何质量门禁。

预算、取消、异常、Scope 关闭、保存恢复、调试捕获开/关一致性与三维读取方均纳入影响范围；不重建资源系统或改变默认关闭的捕获。仅内部等价变化，不新增前端开关或让操作员选“快/慢算法”。数值与来源保持不变时不重复系统缩放、主题或全页面 UI 验收。

Ubuntu Preview 组合时序失败单独处理：先记录受理、worker ready、run.started、首节点、display.updated、node.finished、取消及退出时间，确认耗时在启动、执行还是交付；保留原失败顺序的相邻用例，做有界组合复现。测试侧存在“从 submit 开始的 25 秒窗口”和“从图执行开始的流式交付”混合，属于需验证的可能原因，不是已定根因。不能只增大超时、用单例通过覆盖组合失败，或把测试窗口直接视为生产停止错误；若未闭合，继续明确保留限制，不报告全组合通过。

### 11.6 第五步：收益出口与最终验收

- 每项局部候选必须先满足完整正确性、预算与取消，再看配对耗时。没有稳定收益或造成新工作集压力的修改不合入；不为小幅噪声收益增加新抽象。
- 有收益候选先跑一次完整数值图，确认没有把计算搬到未计时阶段。若已超 10 秒，不重复跑六轮赌一次更快，也不将局部阶段秒数简单相加当正式结果；检查一次新的热点分布后决定下一项。
- 只有准备交付的冻结候选才执行两平台真实发布版本 → WorkflowAppRuntime → Trigger → 独立 worker → 数值返回的首次一次及后五次。每次严格 `<10.0`；诊断与运行中资源采样关闭，结果及调用后回收均检查。首次失败也如实保留，不挑最好一轮。资源峰值另作有界观测，不混进节拍、不追加长稳或 P99。
- 最终审计调用链、依赖和公开契约，保留源文件摘要、全部结果及失败记录；停止本轮 worker/Broker/测试服务，清理 `.tmp/` 和 Ubuntu 原生临时环境，原始点云及手工报告不动。

若以上等价候选没有足够收益，结论应是“当前串行候选仍未达到目标，并已排除这些具体路径”，不是“已优化完成”。下一步需有新的成本证据或单独审核的算法设计；不自动转向并行，不增加等待队列，不靠改质量门禁达标。

### 11.7 与性能分开的验收

S2 正式角区法仍保留，原 0.03 mm 重采样稳定性诊断失败。后续需要独立重复采集、补充角域或标准件，不能靠同一云再次改权重宣布解决。实体精度仍缺可追溯参考值、允许误差、重复采集与装夹变化的量值对照；手工报告和 CloudCompare 同云核对只能辅助算法定义，不替代实体真值。本批不改配方定义、不新增生产阈值，也不以满足 10 秒代替这些验收。M3.4 三态、近 1 GB 容量及独立发行仍按原计划单独推进。

### 12.2 Preview 窗口与组合回归

测试原来把 worker 启动和图内流式事件共用从 submit 起算的 25 秒窗口，而生产调用是在 ready 后开始请求计时。测试现按既有启动配置等待 ready，再使用原 25 秒流式窗口；必须同时看到 value、image、node.finished 才取消，取消/退出仍用独立 10 秒边界。记录 start/ready/run/node/display/cancel/close，不修改生产 timeout 或生命周期。

加入 26 秒受控启动延迟，证明启动不再吞掉图内窗口。首版测试夹具误把已存在 worker 的复用调用也延迟，造成后续文件 Preview 超时；已限定只延迟首次实际启动，并在两平台重新执行组合，不修改生产行为来迁就错误夹具。

真实发布版本 → WorkflowAppRuntime → LocalBuffer/Trigger → 独立 worker → 50 项数值返回，诊断/显示/调试捕获/运行中资源轮询关闭。计时从输入就绪、writer 关闭后开始，不把受理/映射/返回移出计时；首次保留。两平台正式调用依次执行，没有同时运行本任务其他计算测试；机器并非独占环境，不据此猜测超限原因。
