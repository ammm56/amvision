## 已实施的修复

| 问题 | 根因及修复 | 验证边界 |
| --- | --- | --- |
| IPC owner 探测竞态 | reader 原来取得 publisher 的独占锁后再释放，会阻止真实 owner 启动，也会被另一个 reader 误判为 owner。改为只读观察，保留文件身份、epoch、session 校验。 | Windows 原生 ReadFile 仅错误 33 表示锁占用；Ubuntu 使用 OFD GETLK。两个真实观察进程暂停后，新 publisher 仍可取得锁，第二个 publisher 仍被拒绝。 |
| 不确定状态误清理 | 观测权限错误或身份变化不能代表 owner 已退出。训练遥测仅在明确无 owner 时删除独有 session 文件，不确定时释放 reader 并等待重新发现。 | 权限失败、替换、旧 epoch、重新发现和再次发布回归通过。 |
| reject 在外层等待 | 实时调用尚未到执行 token 的 reject 分支，就先等待生命周期锁。外层现在传递 wait/reject；reject 不等控制操作完成。 | 另一线程持有控制锁时，调用在读取状态、创建 Run 前失败；未删除原停止、generation、fingerprint 和容量校验。 |
| 不同 Runtime 锁碰撞 | 原 64 个 hash 分段可能让无关 Runtime 相互等待或拒绝。改为按 Runtime 唯一的弱引用锁注册表，活动调用持有强引用。 | 同 Runtime 重入、跨 Runtime 隔离、异常释放和 1,000 个历史 ID 不累积。 |
| 节点事件放大 monitor 扫描 | 每次节点事件唤醒都执行全量 desired-state 查询。现在同一 monitor 即时处理 deadline，但数据库扫描只由原半秒周期或实际回收事件触发。 | 模拟一秒 1,000 次唤醒，从 1,001 次扫描降为 3 次；扫描中到达的恢复事件保留，数据库错误不会使监控退出。 |
| Workflow manager 停止未确认 | monitor/recovery join 超时、异步回调未完成和组停止异常原来可能被忽略，随后仍释放依赖；start 又清除停止标记。沿用已有 supervisor 的停止确认约定，有界拒绝未完成启停，保留依赖，显式重试停止成功后才可恢复。 | 4 个缺陷用例在修改前失败；修复后相关 53 项通过，包含启动过程中停止、清理异常保留引用、禁止停止后同步准入。 |
| segmentation pinned 总量错误为零 | 三代 segmentation 只报告 prediction/proto 分项，pool 按单输出 memory kind 筛选，丢失实际占用。增加权威总量，混合 pinned/pageable 正确相加；错误快照不再伪装为零。 | 初始 22 项失败；修复后 58 项通过，覆盖全部 16 个常驻输出报告器、释放后归零及错误观测。真实发行 API 的 sync/async 各 1 个实例均报告 832,032 B，运行健康。 |

相对上一轮 `outer-frozen-*`，本轮修改 9 个生产后端文件：`runtime_service.py`、`worker/manager.py`、`local_message/event_ring.py`、`mmap_primitives.py`、`training_telemetry.py`、`deployment_runtime_pool.py` 及 YOLOv8/11/26 segmentation 的 TensorRT session。未重做进程框架，未增加业务等待队列、控制进程或降级路径，未改变模型 core、精度、输入尺寸、输出解码和数值容差。

### 请求级核对

`bounded-stop-diagnostic` 使用只在退出后导出的预分配缓冲，未关闭 GC 或修改阈值。4,000 次 SDK 测量请求均与 backend 区间关联，backend 记录无溢出；只在同 PID 内比较时间区间。Windows Uvicorn 恢复退出信号可能不执行 atexit，诊断通过现有 manager 停止完成点导出，不改业务退出行为。第一次仅依赖 atexit 的缺失证据保留在 `bounded-*`，不能作为零次 GC 的证明。

- 实际 monitor 扫描间隔中位数约 0.513 秒；4,416 次准入/调用对应 485 次恢复扫描，不再每次节点事件扫描数据库。
- 测量请求中最大的 backend GC 重叠约 0.528 ms。4,000 个测量请求区间之外仍有最长约 150 ms 的全代 GC，不能据此声称长暂停已从整个系统消失。
- 最慢模型请求 63.35 ms，准入约 1.91 ms、调用约 51.33 ms，两段均无 backend GC 重叠；同请求 session infer 约 33.50 ms，CUDA event 区间约 23.02 ms。CUDA event 区间不等同于纯 kernel 计算，可能包括调度间隔。
- 观察器开/关的均值没有出现此前逐请求 JSON 日志造成的明显膨胀，但单对实验不足以精确界定 GPU 状态方差。该诊断只用于归因，不认证性能。

本轮没有重新出现历史 35.444 ms 小图持续慢窗口。此前捕获的 173 ms GC 是另一类现象，不能反推为该历史窗口的唯一根因。

最终轮小图出现新的单轮相对 P99 超限。该轮 diagnostics 关闭，现有证据未将具体慢请求唯一归因到 GC、monitor 或操作系统调度；不能把已修复的扫描放大问题等同于全部小图尾延迟根因。模型的 cadence 对照也不能用于解释无模型小图失败。

### 默认模型剩余问题

独立 full-core session 对照绕开平台准入与 IPC：连续调用 P99 约 8.5–9 ms，加入 18 ms 请求间隔后约 28–30 ms；关闭 event 计时仍存在。显式 CUDA spin-wait 无改善，未写入生产实现。auto/spin 对照的原始 prediction 和 proto 哈希相同，但只覆盖这个固定工程样本与产物。

证据证明请求间隔能够触发 session 退化，不能仅靠修改平台准入解释或消除。共享内存所有权握手也增加请求间隔，不能为性能删除 PREPARE、handoff、ACK 或 receipt 校验。频率变化和 WDDM 调度各占多少尚无受控反事实证据，不能直接认定驱动有 bug。[NVIDIA TensorRT 环境与测量说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/benchmarking.html)说明浮动时钟和 WDDM 可能增加波动，但不替代本机因果验证。

GPU1 没有安排其他计算任务，但仍承载 WDDM 桌面图形；当前 Windows 电源方案为平衡。未变更 GPU 时钟、功耗上限、驱动或系统电源方案。keep-warm 只保留此前授权的独立对照，不启用为默认修复。
