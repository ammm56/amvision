# amvar app 应用、运行界面与打包恢复实施基线

## 1. 状态、职责与阅读规则

状态：设计已接受，新增能力待实现。依据 [ADR-0012](../decisions/ADR-0012-workflow-views-and-app-packages.md)，本文是 amvar app 应用组成、运行界面、Workflow JSON 导入导出、应用下载上传恢复及语言模型生成界面的唯一详细实施基线。本文写入不代表完成代码、数据迁移、浏览器验收或现场认证。

当前代码仍是已实现行为的事实来源。本文包含已确定的契约语义和分阶段固化的资源/包格式设计，不是已经注册的公开 endpoint 或完整 JSON Schema。实施时必须同步形成版本化契约、迁移和测试，不能把文档示意直接当成可调用接口。

本文同时作为设计器与生产显示的共同约束：第 3 节定稿应用组成清单、命名数据源、运行入口映射三个模型的语义，第 5 节定义页面操作与状态转换，第 6 节定义结果传输、公开消息、统一 token 与执行交接，第 13 节定义对应验收。第 6 节的新结果流路径和消息语义已确定，但仍待实现；其余管理/包格式的 Schema 按第 14 节在对应阶段形成可执行契约与测试。

优先级：长期稳定和结果正确优先，其次是高性能；实现保持简单、明确、通用，不增加隐藏执行、隐式默认值、业务重试或同步等待队列。

核心是已经实现的 Workflow/Runtime/Trigger，运行页面仅辅助现场监视和一般调用。本文的“实时结果”指在线接收执行完成结果，不要求硬实时、固定帧率或每次执行逐条显示；页面显示可以较慢，但不能拖住业务执行。业务数据的生成、组织、计算、保存、读取和清理均由 Workflow 决定，页面不成为第二个结果处理系统。持久化的是界面配置和发布文档，不是页面收到的生产结果。

前后端按公开契约隔离：本项目页面与第三方自行实现的页面使用同一 HTTP/WS 接口。WebSocket 允许携带 Base64 输出图片；单条完整 JSON 消息上限按第 6.4 节固定为 64MB。界面设计器不是调用或订阅后端的前提，替换前端不要求修改 Workflow/Runtime/Trigger。

## 2. 已确认的不变量

1. 采用方案 A：运行界面绑定 Workflow App 公开输入输出，不绑定内部节点参数、节点位置或 Preview 私有数据。
2. amvar app 是多个 Workflow/Runtime/Trigger 与运行界面的组成资源；一个页面允许显示多个命名 Runtime 数据源。组成和显示不是新的执行引擎，也不要求将独立 Workflow 合成一个图。
3. 内部节点参数、连线和业务算法只在 Workflow 编辑画布修改，随后按既有发布、选版规则生效。
4. 界面仅选择现有 App Entry 输入。`request_json` 字段由表单组成，不因此新增公开 binding 或修改 Workflow。
5. App Entry 声明支持哪些输入不代表每次必须全部提交；缺少实际需要的数据由消费节点执行报错。页面不新增必填规则；缺省、null、false、0、空字符串、空数组、空对象不能相互替换。
6. 界面只承担输入、明确目标的调用、多来源展示和显示格式化；业务数据合并、ROI/模型结果关联、规则判定及业务统计留在 Workflow，不在页面隐藏编排。
7. 界面、主题及组件资产独立版本管理，不进入 Workflow 内容指纹；仅修改外观不重启 Runtime、不修改 Trigger。
8. 打包按明确选择的成员和依赖固定交付组合，不要求多个 Workflow、界面和所有组件使用相同版本号，不新增强制同步发布的应用总版本。
9. 页面打开、刷新、重连和设计预览不执行 Workflow，也不启停 Runtime/Trigger。页面仅在有效连接期间接收所订阅 Runtime 的实时结果。
10. 显示从统一 Runtime 结果边界获取，不依赖调用协议或 Trigger 回传字段；现有 SDK/Trigger 响应结构不变。
11. 无对应订阅时不做新增的显示准备、保存或发送；Workflow 明确配置的编码、保存等节点仍正常执行。不新增 Runtime 显示开关、结果队列、缓存、历史补发或全节点 trace，不改变 none、原有同步 admission、异步任务和 Trigger 合并语义。
12. 模型只参与界面创作；生成进入草稿并经校验、预览、确认后发布。已发布界面可在模型离线时运行。
13. Workflow JSON 与完整 App 包共用现有文档语义；完整包不是数据库备份、进程检查点或平台发行包。
14. 导入不自动执行节点、安装代码、启动 Runtime、启用 Trigger 或回放历史事件。
15. 已明确的 64MB 消息上限是产品约束，不是实测性能保证；其余资源限制、性能结论或稳定性认证须经实测，不以架构解耦替代验证。
16. 保存草稿、发布界面、应用到运行入口、打开页面订阅和手动调用是不同动作，不能互相隐式触发；打开页面建立订阅不等于启动或调用 Runtime。
17. 设计预览不执行；试运行复用正常 Runtime 调用，真实节点副作用、资源占用和调用规则不变。
18. 在线显示仅保留当前收到的画面，不要求硬实时。内置页面手动调用显式使用已有 `response_mode=run`，按本次 HTTP 返回的执行 ID 和状态确认；不建立固定结果模式或历史查询。允许错过显示更新；显示故障不能改变、丢弃、合并或抑制业务调用。
19. 现有 Workflow App、Graph、Runtime、Trigger、API、SDK、变量和 ID 命名保持不变；仅前端系统文案把原 Workflow 的“应用”显示为“工作流”，新 amvar app 显示为“应用”。
20. 来源以稳定 `source_id`、公开 binding 和字段路径关联，运行入口将来源明确映射到 Runtime；同名字段、列表顺序、显示名称和更新时间不参与隐式关联。
21. 新结果流允许直接发送公开 Base64 图片，64MB 限制针对整条消息，而非每张图片。超限或显示失败只影响本次显示交付，不改变业务输出、终态、SDK/Trigger 回传或资源清理。
22. 页面发送、断开、解码和渲染不进入核心执行的等待条件；不持有执行锁等待网络，也不为页面延长 LocalBuffer 租约。共享机器仍须验证 CPU、内存和网络资源竞争，不能宣称物理零开销。
23. 第三方可只依据版本化 HTTP/WS、公开 binding/payload 与授权规范自行实现界面，不依赖内置界面文档或设计器，不改变核心执行协议。
24. 本阶段采用登录即全部权限的使用模型，永久调用 token 与默认用户/SDK 共用；不引入第二套账号、授权或 token 服务。未登录、无效或已撤销 token 不能访问，新页面不绕过既有 token 校验。
25. 一个 Runtime 结果流发送完整公开输出 mapping，不按组件过滤字段。只需要 Runtime 状态的来源不订阅结果流；显示控件选取字段不改变网络消息或节点执行。
26. 同步、持久化异步及 `none + event-only` 瞬时异步共用终态交付，清理失败、超时和取消按原真实终态处理；不在清理前发布成功，不把未受理请求伪造成已执行结果。

## 3. 资源关系与独立版本

```text
amvar app（前端：应用）
├─ Workflow App A --发布--> App Version A --选版--> Runtime A <-- Trigger A
├─ Workflow App B --发布--> App Version B --选版--> Runtime B <-- Trigger B
└─ 运行界面草稿 --独立发布--> 界面版本（命名数据源、公开绑定、组件/主题）
                                  ↓ 显式应用
                            运行入口（source_id → Runtime）
                                  ↓ 加载
                            一个多来源生产运行页面

应用组成清单管理成员；各 Workflow、Runtime、Trigger 仍保持原有生命周期。
页面连接仅订阅对应 Runtime 的公开结果；应用包固定所选组成、文档、版本、配置和依赖，不保存订阅或结果。
```

`navigation.workflowGraph`、`navigation.workflowApps`、`workflowEditor.applications` 等翻译键、`WorkflowAppListPage` 等组件/变量、`/workflows/graph`、`/workflows/apps` 路径、公开 API、数据库、SDK 和资源 ID 均保持原状。新应用功能使用独立键、资源和管理入口，不占用旧 Workflow 路径。现有 App Entry 节点及发布版本仍是原概念；本次显示名称调整不造成数据迁移或重新发布。

新导航“应用”管理 amvar app；应用详情内管理组成、运行界面设计/版本、运行入口和下载恢复。首版围绕一个主生产页面，不额外建立与应用并列的另一套“运行界面”顶层资源入口。工作流编辑与界面设计仍是两个不同画布，不能在生产页修改任何画布。

运行界面和入口归属 amvar app，不再归属单个 Workflow App。一个界面版本声明多个命名数据源，入口将这些来源映射到实际 Runtime；控件不硬编码 Runtime，不保存 Worker 对象。一个界面可通过不同入口用于测试和现场映射，入口不是新的 Runtime、执行器或常驻进程。入口有稳定访问地址，鉴权后返回原入口；地址不包含凭据。

界面版本不可变；修改生成新版本，明确发布与回退。设计草稿修改不改变已打开的生产界面；页面切换界面版本必须整体更新，不能混用新布局与旧绑定。已有输入草稿不得因后台发布自动丢失或提交。

### 3.2 契约兼容

- 每个数据源以明确选择的 Workflow 及已发布 App Version 契约为依据，不要求 Runtime 已启动。生产运行逐来源使用映射 Runtime 当前激活版本的公开 contract，不使用最新草稿或仅凭最新发布序号判断。
- 停止态入口配置可按 Runtime 已选择的目标版本预检，但必须标为待启动核对；desired version 不能当成已经激活的版本。
- 按界面实际使用的 binding、方向、payload type、Schema 和字段路径校验；不拿完整 Workflow 内容指纹相等当作界面兼容条件。
- 内部节点替换且所用契约兼容，界面可继续使用；新增未使用输出不应直接导致整个界面失效。
- 删除所用 binding、改变所用类型或字段结构时明确报告；不自动修复 binding、不替换同名字段、不切 Runtime 版本。新增未使用的公开输入不构成“页面未补齐必填输入”的阻断条件。
- 任意 JSON 的深层字段若没有 Schema，发布时只能证明外层 binding 有效，不能伪造深层类型保证。执行时字段不存在或类型不符，显示绑定错误，不填 0 或成功状态。
- Runtime 切版、generation 改变或页面重连后校验并切换数据来源；旧结果不能覆盖新实例状态。
- 兼容检查在加载、发布和实例切换时进行，结果只用于当前配置/页面状态；不在每次生产调用中扫描完整图、数据库或组件目录，不建设生产结果缓存。
- 兼容报告按 `source_id` 定位受影响组件和动作；某来源停止、不兼容或连接认证失效不应清空其他来源。页面可显示“部分不可用”，不能伪造一个所有 Runtime 共同的执行状态。

### 3.4 最小资源字段

以下语义作为三个模型的共同约束，完整字段类型和公开 Schema 在实现前核对。新增 amvar app、界面、界面版本、运行入口及组成关系；不为既有 Runtime 增加显示交付配置，不新增试运行任务系统、应用执行器或永久浏览器会话记录。

| 资源 | 字段草案 | 归属与约束 |
| --- | --- | --- |
| AmvarApp | `amvar_app_id`、`project_id`、`display_name`、`description`、`config_revision`、`composition`、可空的 `default_workflow_view_entry_id`、创建/修改时间与主体 | 完整应用组成；独立身份，旧 `application_id` 仍只指 Workflow App |
| WorkflowView | `workflow_view_id`、`project_id`、`amvar_app_id`、`display_name`、`description`、`draft_revision`、`draft_document`、`draft_fingerprint`、创建/修改时间与主体 | 可修改草稿；不在此修改成员 Workflow |
| WorkflowViewVersion | `workflow_view_version_id`、`workflow_view_id`、`version_number`、`source_draft_revision`、`document`、`document_fingerprint`、按来源组织的 `binding_requirements`、`dependency_manifest`、创建时间与主体 | 不可变；契约需求和依赖由服务端从文档推导，不相信客户端自报兼容 |
| WorkflowViewEntry | `workflow_view_entry_id`、`project_id`、`amvar_app_id`、`display_name`、`workflow_view_version_id`、`source_bindings`、`interaction_mode`、`config_revision`、`display_options` | 一个入口固定一个界面版本和多个命名 Runtime 映射；使用修订号检查 |

`draft_document` 包含 `format_id`、`sources`、`components`、`actions`、`layout`、`theme`、`assets`。`sources` 按第 3.6 节声明每个来源的设计依据，不再有整页单一 `basis_app_version_id`。组件声明稳定 `component_id`、类型/版本、属性及明确绑定。设计依据与 Runtime 实际版本按第 3.2 节校验，不要求版本 ID 相同才兼容。

`interaction_mode` 首版限定为 `monitor` 与 `interactive`：前者不显示页面调用控件，后者可显示公开输入及执行操作。这是页面布局/交互选择，不是角色或权限隔离；登录用户仍有全部操作权限，不另做 monitor 专用 token。`display_options` 只保存语言、全屏等显示选择，不隐藏业务参数或启停动作。

界面 `version_number`、草稿 `draft_revision`、应用/入口各自的 `config_revision` 和 Runtime generation 各司其职，不共用计数器。当前显示内容、访问令牌、现场表单、选中组件和 Worker 句柄不写入发布文档。

### 3.5 模型一：amvar app 组成清单

`composition` 明确列出 `workflow_application_ids`、`workflow_runtime_ids`、`trigger_source_ids` 三类成员集合。数组仅用于列举，不以数组位置表示角色、调用顺序或归属关系。界面和入口通过自身 `amvar_app_id` 关联，读取组成清单时一并列出，不额外保存两份可各自修改的界面/入口 ID 数组。

- 第一阶段成员属于同一 Project；Project 用于资源组织，完整应用不新增租户或权限边界。创建完整应用可以从空组成开始，未配置主入口时显示未配置，不生成默认 Workflow 或 Runtime。
- Workflow、Runtime、Trigger 是引用成员，不是复制或独占所有权；同一既有资源可以被多个应用选择。加入/移除不隐式创建、删除、停止或启用资源。
- Runtime 的所属 Workflow、Trigger 的目标 Runtime 以原资源的真实引用为准，不在应用清单重复维护可冲突的归属字段。添加成员时列出所需成员，由明确选择或确认补齐，不静默导入整个 Project。
- 有效组成中 Runtime 的 Workflow 必须在清单中，Trigger 的目标 Runtime 必须在清单中；移除成员前核对界面来源、入口映射及其他成员引用，不能留下悬空引用。变更前报告依赖，明确修改引用后再提交；新应用关系不进入每次 Runtime 调用的热路径查询。
- 从原 Workflow/Runtime/版本管理入口删除资源时也要核对应用组成、发布界面契约依据及运行入口的反向引用，不能只在移除应用成员时检查。引用检查属于配置/删除操作，不扩大执行热路径。
- 一个 Runtime 可以绑定多个 Trigger；成员 Runtime 不必都配置页面数据源，例如纯后台生产链路可以只进入交付包。页面也不因有 Trigger 成员而自动配置其结果为来源。
- 默认运行入口必须属于同一 amvar app；首版“打开运行页”使用这一明确入口，不从入口列表选择第一项。未指定时要求配置，不猜测。
- `config_revision` 用于组成配置的并发更新检查，不是 Workflow 发布版本。应用不新增总运行进程、总调用队列、全成员事务或强制共同发布版本。
- 删除应用不级联删除成员 Workflow、Runtime、Trigger 或共享依赖；自身界面/入口存在时先明确处理其引用，再删除空的应用资源。成员的既有独立版本和启停能力不改变。

新资源使用独立 `amvar_app_id`；其 ID 生成格式在实现阶段冻结，不能套用或复用既有 `workflow-app-*` 身份。导出选择是一次操作的选择范围，不自动改写应用日常组成。

### 3.6 模型二：命名数据源

数据源是界面文档内的声明，不是独立服务或数据库数据接入器。`sources` 是以稳定 `source_id` 为键的映射；例如 `inspection`、`maintenance` 只是可配置的通用标识，不预置行业角色。

| 来源字段 | 语义 |
| --- | --- |
| `source_id` | 即 `sources` 的键，界面内唯一；不使用翻译后的名称作为引用 |
| `display_name` | 界面中便于理解的名称，不参与绑定 |
| `application_id` | 该来源所依据的既有 Workflow App ID，必须是应用成员 |
| `basis_app_version_id` | 该 Workflow 的明确已发布契约依据，不取最新草稿 |

输入、输出和状态组件统一使用 `source_id`；公开数据绑定再包含 `binding_id`、方向和可选 `field_path`。所需契约由服务端从组件/动作推导，按来源生成 `binding_requirements`，避免维护两份独立可修改的契约。

- `inspection.request_json` 与 `maintenance.request_json` 属于不同输入空间；同名 binding 不合并，不自动广播。
- 来源与实际 Runtime 解耦；同一 Workflow 的两个 Runtime 可声明两个来源。来源名不等于 Workflow 名，也不强制等于 Runtime ID。
- 来源键在绑定后保持稳定；修改显示名称、移动控件、排序或翻译不改变关联。确需更换来源键时只修改草稿中的相关组件/动作，发布新界面版本，再将目标入口的新版本与新映射整体提交；旧发布文档和仍使用它的入口不改写，不靠字符串全局替换。
- 一次执行动作包含稳定 `action_id` 和一个明确 `source_id`，只组装该来源允许的公开输入、调用该来源映射的 Runtime。共享控件需显式声明各动作的输入映射，不能选择一次值就调用全部来源。
- 首版不支持动作链、自动跨 Runtime 扇出、失败切备用来源、页面重试队列或任意 API 数据源。跨 Workflow 业务协作继续通过 Workflow 或既有集成协议完成。
- 无 Schema 的 JSON 字段沿用静态校验限制；命名来源不会使任意 JSON 自动获得类型保证。

### 3.7 模型三：运行入口映射

`WorkflowViewEntry` 固定一个发布界面版本和 `source_bindings` 映射。键与版本文档中的 `source_id` 完全一致，值包含既有 `workflow_runtime_id`。不将标量 Runtime ID 简单改成数组，不按 Runtime 列表顺序绑定。

以下仅示意引用结构，`<...>` 不是实际资源 ID：

```json
{
  "amvar_app_id": "<amvar-app-id>",
  "workflow_view_version_id": "<view-version-id>",
  "source_bindings": {
    "inspection": { "workflow_runtime_id": "<production-runtime-id>" },
    "maintenance": { "workflow_runtime_id": "<maintenance-runtime-id>" }
  }
}
```

- 入口与界面属于同一应用；映射 Runtime 是应用成员，所属 Workflow 必须匹配该来源的 `application_id`。不能仅因另一 Workflow 的字段同名就自动映射过去；复用界面到其他 Workflow 时显式修改来源并发布或通过导入映射生成派生版本。
- 创建/更新有效入口时校验来源键完整且没有多余键，全部 Runtime 身份明确；停止态允许配置并标记待启动核对。不配置隐藏默认 Runtime，不静默保留废弃来源映射。
- 应用界面新版本及完整映射在一次带 `expected_config_revision` 的配置更新中提交；只保证入口配置一致，不锁住或同时切换各 Runtime。
- 测试入口与生产入口可以映射到各自 Runtime；生产页不能随意换实例。设计试运行可以临时明确选择映射，但不能因此改写正式入口。
- 来源状态、契约、连接认证、当前显示及本次调用分别管理。某来源断开或不兼容时只影响相关组件与动作；其他来源继续使用，不实现“所有来源都就绪才运行”的屏障。
- 多个来源映射同一个 Runtime 时可复用当前网络连接和正在显示的数据，但不建设共享结果缓存，不合并来源身份、输入草稿或显式操作。两个动作分别点击仍是两次正常调用，不添加业务去重。
- 入口修改后旧页面固定原版本与映射并提示整体重载；不静默将正在进行的调用或未提交输入换到新 Runtime。后端继续校验 token 与目标资源有效性，不新增动作权限配置。
- 入口仅保存映射，不保存 Runtime 当前版本副本、启动状态或执行数据作为权威；Runtime 切版仍由原资源流程管理，页面逐来源重新核对兼容性。

## 4. 输入与输出绑定

### 4.1 只使用 App Entry 公开输入

`request_*` 是默认 binding 名称，控件应按契约中的 binding ID、payload 和 transport 能力配置，不硬编码名称猜类型。现有默认输入与控件对应如下：

| 输入 | 控件 | 提交边界 |
| --- | --- | --- |
| request_image_ref | 图片选择/上传 | 经既有上传或 multipart 接口得到有效引用，不提交浏览器本机路径 |
| request_image_base64 | 图片选择/上传 | 明确使用现有 Base64 binding，不隐式改写为其他输入 |
| request_json | JSON 编辑器或结构化表单 | 组装同一 value 输入，服从 request_schema |
| request_text | 单行/多行文本 | 保持原始文本，不自动解析 JSON |
| request_file | 单文件选择 | 现有文件上传及引用接口 |
| request_files | 多文件选择 | 保留明确的文件顺序和多文件协议 |

普通页面通过 HTTP Runtime 调用支持所有已公开类型，不为浏览器实现本机 mmap 或 ZeroMQ。高性能 Trigger 仍只使用既有 image-ref/JSON/text 能力，不因界面增加文件或 Base64 transport。

这些公开输入按实际调用选择，不能因为 App Entry 或页面列出了六种类型就要求全部上传。页面只提供图片、图片加 JSON 或其他实际组合均可；新 Runtime 版本增加公开输入也不要求页面增加对应控件。缺少实际使用的数据由 Workflow 消费节点报错，输入报文的基本格式校验和既有错误语义仍保留，不通过注入空值或成功结果掩盖问题。

### 4.2 request_json 表单

多个控件可分别绑定某个来源 `request_json` 中的 `recipe`、`station`、`batch_id`，提交时组装该来源的一份 JSON 对象。这些是本次输入字段，不是新 App Entry binding，不改内部节点参数。不同来源分别组装，不能因 binding 同名共用提交对象。

- 采用明确字段路径，复用项目路径语义；不能按控件排列顺序关联。
- 同一动作/来源中，同一字段多写入者、父对象与子字段冲突在设计校验中拒绝。JSON 原文编辑与结构化表单同一时刻只有一个写入来源；不同来源的同名字段不构成冲突。
- 缺省字段按缺省提交；不因为页面存在控件就提交 null、空图片、空文件或虚构默认值。
- 可选控件明确区分“本次未提供”和“提供空值”；例如未提供 request_text 与提交空字符串、未提供 station 与提交 0 不等价。图片只提交明确选择的 binding，不为另一种图片输入补空 payload。
- 显式预填值可作为界面配置展示，由实际表单提交；不隐藏注入或反向修改 Workflow default。
- 可选字段仍可省略；未消费的可选输入不要求补齐，消费节点的既有错误语义保持不变。
- 提交构造层与后端现有输入校验复用同一公开契约；前端校验不替代后端权威校验。
- 一次输入不会改变外部 Trigger 下次提交的参数。页面刷新、重连和资源读取不重发业务调用。

### 4.3 输出

每个显示组件使用 `source_id`、公开输出 binding ID、可选字段路径和显示配置。控件 ID 用于界面文档身份，移动控件、修改标题或节点位置不改变绑定。数组下标仅在明确数据路径中具有语义，不用节点/控件位置隐式配对数组。

允许单位、精度、文字、图标和颜色映射；合格判定、跨字段计算、ROI 与推理结果配对、业务累计和数据合并必须在 Workflow 中完成。图片叠加展示若支持原图与几何分离，必须使用同一结果中的显式来源和坐标契约，不重新推断关联。

Save Image 的 image-ref/saved_output 与 Save JSON 的保存回执不是相同类型。界面不因节点叫 Save 就自动读取其内部输入或磁盘内容；所需图片、文件或 JSON 必须成为明确公开输出，再按相应资源契约显示。现有 Preview body 可按公开类型适配，但不能访问 Preview 私有缓存。

多来源默认分区显示各自当前收到的结果与时间，不承诺等于服务端最新执行，也不宣称它们属于同一生产记录。生产 Workflow 与监视 Workflow 的 `workflow_run_id` 不同；需要表达同一记录时，公开输出必须显式传递原始生产执行 ID 或唯一记录键。不能按“两个最新结果”、接近的时间、文件名或可能重复的批次号猜测关联。首版不建立前端跨来源历史 join 缓存；严格联合判定或一致摘要由独立汇总 Workflow 输出，无需把所有原始 Workflow 合成一个图。

### 4.4 输入组装与输出解析标准

输入控件先按来源和公开 binding 组装本次请求，再使用既有 HTTP JSON/multipart 调用。`value.v1` 的 JSON 业务值、`text.v1` 的原始文本、`image-base64.v1` 的编码图片以及文件引用分别按现有类型封装；不因为文本看起来像 JSON 就自动解析，不把浏览器文件路径当服务端引用，不把 Base64 输入偷偷改为 image-ref。上传和引用的生命周期沿用现有 HTTP 输入规则，WS 的输出容量限制不改变上传协议。

输出解析顺序固定为：校验消息版本及实际 Runtime 身份 → 按公开 binding ID 取 payload → 按该 binding 的 `payload_type_id` 适配 → 按明确字段路径取值 → 渲染组件。类型依据来自实际执行版本的公开契约，不按内容猜类型。字段路径基于类型适配后的业务值：例如 `value.v1` 解开明确的 `value` 包装后，`batch_id` 指业务字段；不是任意遇到同名 `value` 就继续解包。具体路径语法复用项目现有规则并在公开 Schema 中说明。

| 公开类型/内容 | 传输与解析 | 页面显示边界 |
| --- | --- | --- |
| `value.v1` | WS JSON 中保留 `{ "value": ... }`，适配器读取业务值；对象、数组、字符串、数值和布尔保持原类型 | JSON/表格/数字等组件按明确字段读取；不对对象重复 `JSON.parse`，不对业务字符串隐式解析 |
| `text.v1` | WS 中保留文本及已有媒体类型/字符集字段，适配器读取 `text` | 文本按原文显示，不作为 HTML 或脚本执行 |
| `image-base64.v1` | WS 中传输 `image_base64`、`media_type` 及已有尺寸字段 | 校验图片类型后由浏览器解码显示；可复用 data URL 或 Blob/Object URL 基础组件，无需落盘 |
| `response-body.v1` 图片 body | 按 `type` 和 `image.transport_kind` 识别 `inline-base64` 或 `storage-ref` | 分别走内联图片或受控 HTTP 资源读取；不依赖节点 ID 或 Preview Run |
| 已保存 `image-ref.v1`、`file-ref.v1`、`file-refs.v1` | WS 交付明确引用和元数据，正文按既有受控 HTTP 资源契约读取 | 不把任意磁盘路径或执行期内存引用作为 URL；JSON 文件只有明确选择 JSON 读取/展示时才解析 |
| 明确公开的 Preview body | 只按其已声明的 body 类型适配；`source_image`/`display_image` 按契约区分 | 可以显示公开内容，但不访问编辑器私有记录、artifact 会话或内部节点状态 |

未提供、显式 null、空字符串、空数组、false 和 0 分别处理。某次输出缺失时该组件显示本次缺失状态，不能保留上一执行的值并与本次图片拼成伪结果；未知类型、字段不存在或解析失败只标记相应显示错误。JSON 业务键保持 Workflow 原样，不为统一系统字段命名而改写业务键。

浏览器一次解析收到的 JSON 消息；Base64 仅作为对应图片字段解码，不对每个组件重复保存整份消息。多个组件可读取同一当前结果，但不另建结果集合。图片媒体类型及解码失败处理必须公开、可测试；不能把任意 `data:`/URL 内容作为可执行页面加载。

## 5. 界面文档、组件和编辑器

### 5.1 一个文档，多个创作入口

文档包含格式版本、稳定组件 ID、组件类型/版本、布局、输入输出绑定、显示属性、主题引用、本地资源引用和允许操作。运行上下文、表单现场值、访问令牌、最近结果和 Worker 句柄不混入发布文档。

人工可视化编辑、模板创建、模型生成使用同一解析器、校验器、文档和 Vue 渲染器。必须支持 AI → 人工 → AI → 导出 → 恢复的往返，不维护生成式页面和手工页面两套格式。

第一阶段不建立任意 HTML/JavaScript、页面表达式执行器或第二套流程图。界面文档支持多个命名 Runtime 来源的输入与显示，不支持任意 API 数据源、跨 Runtime 业务编排、页面定时任务或控件业务事件链。

### 5.2 组件目录

| 类别 | 首批能力 |
| --- | --- |
| 输入 | 文本、数字、枚举、布尔、JSON、图片、文件、多文件 |
| 图片 | 适应窗口、缩放、平移、原图查看；几何与缩略图坐标关系明确 |
| 结构化结果 | JSON 折叠/复制、明确列绑定的表格；大列表有界渲染 |
| 标量 | 文本、数值/单位/精度、明确值映射的状态 |
| 文件 | 已公开文件的名称、长度、下载 |
| 说明与布局 | 标题、说明、网格、分组、标签页 |
| 操作 | 使用当前有效 token 调用既有 Runtime 接口；不绕过公开输入契约 |

组件注册至少声明类型、版本、接受的数据类型、属性 Schema、允许动作、空值/加载/错误状态和资源依赖。复用已有 Vue 图片、JSON、表格基础组件，先审计生命周期，不复制 Preview Run 状态管理。

首版导航使用第 3.1 节的“应用”，在 amvar app 内进入界面设计、版本和可全屏运行页。设计器左侧为组件/按来源组织的公开契约，中间为布局，右侧为绑定/属性；首版提供网格、尺寸、排序、分组、标签页及主题，不先建设通用网站平台。

设计预览使用明确标记的示例数据，不调用 Workflow，也不查询服务端历史显示结果。手动“执行一次”是独立显式动作，仍遵守 Runtime admission，失败不自动等待或重试。

### 5.3 主题和扩展

- 主题层负责颜色、字体、间距、背景、边框、阴影及可关闭动效；组件外观变体负责不同呈现；新交互由受控组件源码实现。
- 现代简约、科幻 HUD、像素风等均不改变 binding、错误含义或执行协议。动态背景和动效不得成为运行依赖。
- 主题作用域限制在运行界面容器，不污染平台导航、管理页和节点编辑器。
- 使用现有中文、英文、日语、韩语切换机制；固定系统状态和控件文案本地化，业务原文不自动翻译，主题不复制四套业务实现。
- 首先覆盖桌面工作站、工控机和全屏模式。窄屏按现有前端原则支持查看，移动端验收单独标注，不能由桌面测试推断。
- 字体、图片等随资产本地分发，不依赖 CDN。扩展组件经过开发审查、测试、版本发布及安装信任校验；不接受配置中任意注入脚本。

### 5.4 页面操作与副作用

“应用”详情中的运行界面管理提供设计、试运行和版本管理；生产运行页使用独立地址。工作流编辑画布修改执行逻辑，界面设计画布只修改显示文档。各页面共用受控组件和渲染器，不共用草稿编辑状态。

| 操作 | 修改对象 | 执行 Workflow | 对生产页或 Runtime 的影响 |
| --- | --- | --- | --- |
| 编辑布局、绑定、主题 | 浏览器界面草稿 | 否 | 不改变已发布界面 |
| 保存 | 服务端界面草稿 | 否 | 不发布，不改变运行入口 |
| 界面预览 | 无持久修改 | 否 | 只渲染明确标记的示例数据 |
| 试运行中的执行一次 | 一个动作指定来源的一次 Runtime 调用 | 是 | 真实节点副作用和资源占用不变；不执行其他来源，不修改生产界面 |
| 发布 | 新不可变界面版本 | 否 | 不修改现场入口，不建立结果订阅 |
| 应用到运行入口 | 入口的界面版本引用与完整来源映射 | 否 | 新打开页面使用新组合；已有页面提示更新 |
| 打开生产页 | 当前浏览器显示状态及有效订阅连接 | 否 | 等待后续实时结果，不启动 Runtime/Trigger，不补发旧结果 |
| 生产页执行一次 | 指定来源的本次公开输入请求 | 是 | 遵守原有 Runtime 调用规则；不广播给其他来源 |
| 关闭页面 | 当前浏览器状态与资源 | 否 | 释放连接及当前显示资源，不停止 Runtime/Trigger |

“界面预览”与 Workflow 编辑器 Preview Run 不是同一动作。试运行应显示明确目标并说明是真实调用；不以“预览”名称掩盖 Save、Cleanup 等副作用，也不要求每次正常调用额外确认。

### 5.5 设计页：创建、保存、校验与预览

先创建/选择 amvar app 并配置成员，再创建空白/模板/复制界面，逐个添加命名数据源，选择成员 Workflow 及其已发布 App Version。没有契约时可保存未完成布局，但不能伪造可绑定字段或发布无效来源；相应 Workflow 先按既有方式发布。打开已有界面读取服务端草稿和修订号，不直接修改发布快照。

设计器沿用第 5.2 节布局：左侧组件及按来源组织的公开输入输出、中间布局、右侧绑定/属性、顶部保存/预览/试运行/发布和草稿状态。选中组件能够定位到“来源 → Workflow 契约 → 公开 binding → 字段路径 → 接受类型”，不能只显示无法追溯来源的字符串。

保存状态与校验状态分开表达：

- 保存：`已保存 → 已修改 → 保存中 → 已保存 / 保存失败`。
- 校验：`待校验 → 校验通过 / 存在问题`。
- 已有发布版本与草稿有修改可以同时成立，不用互斥的“已发布/编辑中”状态覆盖事实。

保存携带 `expected_draft_revision`；另一个标签页或主体先保存时报告冲突，不自动覆盖或合并布局。保存失败保留浏览器修改，不把本地内容标成已持久化；首版不引入多人实时协同。

预览按来源使用明确标记的示例数据，不跟随实时结果，不依赖执行历史查询。覆盖空结果、错误、长文本、大数组、图片缺失及一个来源不可用而其他来源正常等状态。示例与试运行数据不随界面默认发布/打包，进入和退出预览不保存、不发布、不调用。

### 5.6 试运行：固定上下文与请求状态

先保存界面草稿，再逐来源明确选择试运行 Runtime 映射。展示各来源的 Workflow、实际运行版本、名称、状态及契约兼容结论；不自动选择首个 Runtime、不启动、不切版。停止态来源可查看配置但不能执行，提供前往既有 Runtime 管理页的入口；不阻止其他可用来源试运行。

点击一个动作固定界面草稿修订/指纹、`action_id`、`source_id`、映射 Runtime ID 和实际提交输入，以本次 HTTP 请求关联实际响应。内置页面统一显式传 `response_mode=run`，从现有响应读取 `workflow_run_id`、实际版本和 `state`，不猜测业务字段。该模式不返回内部节点记录，不是 `record_mode`，不要求开启数据库记录或 debug。HTTP/SDK 的默认 `app-result` 保持原样。不自动执行所有来源；其他来源画面不算作本次调用的结果。输入框后续修改不改变已提交内容；当前表单、HTTP 请求完成状态和实时画面分别表达，后续实时结果可以正常更新画面。试运行不建设永久任务表或固定结果存储。

状态区分：尚未调用、正在提交、等待结果、Workflow 成功、Workflow 失败、明确拒绝且未执行、连接中断且结果未确认。网络错误不能证明节点没有执行；未知结果不自动重发，退出页面不隐式取消或停止 Runtime。

表单读取后 Runtime 可能切版，调用仍服从现有 Runtime 的真实执行规则；页面核对实际返回的版本/执行身份，不把加载时版本冒充实际版本。版本变化后重新校验所用 binding，缺失或不匹配明确显示，不自动改参或重发。本次不为辅助页面新增 HTTP revision 前置条件或改变现有调用协议。

发布必需结构与绑定校验，但不强制每次标题/颜色修改后真实调用生产 Workflow。试运行验证结论只对应被验证的草稿指纹，修改后不能沿用为当前版本已验证。业务返回不合格不等于界面验证失败。

### 5.7 发布与入口应用

发布接受已保存的明确草稿修订：服务端核对修订、校验组件/绑定/资源、固定文档与所用契约/依赖、创建不可变版本并返回身份和指纹。失败不修改旧版本或现场入口；相同内容可复用既有版本，这是发布去重，不是业务调用去重。

不存在的公开 binding、方向错误、已知类型不兼容、JSON 写入冲突、未知组件/资源和非法动作阻止发布。缺少完整 Schema 的 JSON 深层路径按第 3.2 节报告静态验证限制，不能一概禁止使用或伪造保证。

“应用到运行入口”明确选择入口、发布界面版本与完整 `source_bindings`，携带 `expected_config_revision`，按各目标 Runtime 契约分别校验。来源新增/删除必须显式补齐/移除映射，不继承未知键。停止态只做目标版本预检，启动后核对实际 active revision。不启动 Runtime/Trigger，也不要求另行配置 Runtime 显示开关；公开输出的展示选择属于界面绑定。

新打开页面使用入口当前指定版本；已打开页面固定原会话组合，提示更新，不热替换局部组件。明确重载后整体切换；未提交输入需明确处理，不能自动丢失或提交。入口重新配置 Runtime 时旧页面不静默转向其他实例；无效或撤销的 token 由现有认证拒绝，入口地址不是登录凭据。

### 5.8 生产页：加载、状态与操作

生产页只保留现场名称、简洁连接/Runtime 状态、配置好的输入和实时结果区，以及执行一次、全屏等必要操作。不提供历史回放、固定某次结果或暂停后恢复模式。不展示组件选框、绑定编辑、节点目录或发布按钮；版本、执行 ID 和错误详情放入详情区域。系统文案使用既有四语言机制，业务原文不自动翻译。

打开顺序：使用有效 token → 入口、固定界面版本及完整映射 → 分来源读取 Runtime 实际状态/契约 → 兼容检查 → 建立对应结果连接 → 等待后续结果。不查询 latest 或历史显示快照，也不为填充画面自动执行 Workflow。各来源独立加载，不等全部 Runtime 就绪；尚未连接、已连接但尚无结果、Runtime 未启动分别表达。

以下维度按来源独立维护，不把全部情况塞进一个页面 `status`。整页仅汇总可用/部分不可用等显示提示，不能作为业务联合判定：

| 维度 | 状态示例 |
| --- | --- |
| 网络连接 | 连接中、已连接、断开、认证失效 |
| Runtime | 停止、运行、故障 |
| 界面兼容 | 可用、不兼容、待核对 |
| 当前显示 | 等待结果、当前收到的结果、连接已断开时保留的旧画面 |
| 本次调用 | 待提交、等待、成功、失败、结果未确认 |
| 资源显示 | 可用、加载中、已失效 |

Workflow 执行成功不等于产品合格；合格状态绑定 Workflow 明确公开的业务字段，不根据 HTTP 200 或 succeeded 推断。Runtime 正常与浏览器断网可以同时成立；图片失效不改写业务终态。

每个来源只有在线显示：接收一条结果后更新当前画面，不追加历史数组，不要求固定刷新周期。手动 HTTP `response_mode=run` 响应确认该次请求的执行 ID、实际版本和状态，不用迟到的 HTTP 响应覆盖更新后的画面；外部 Trigger 的后续结果正常显示，不建立本次结果锁定模式。首版先建立结果连接再进行页面试运行；显示通道未连接或错过消息时，不承诺 HTTP 成功就必然出现对应画面，也不以未显示为由重复调用。

连接断开时明确标记断开及上次收到结果的时间，保留画面不表示仍为实时。关闭释放订阅、图片对象和监听器；刷新重新等待结果，重连只恢复订阅，不补发断线期间结果、不提交表单。登录过期沿用现有鉴权恢复，不自动重放结果未确认的业务请求。

表单、手动请求状态和当前画面按来源隔离，只在当前页面使用，不持久化为应用配置或服务端结果集合。某来源失败或断开不清空其他来源；页面显示不承诺所有执行逐条可见，可靠保存由 Workflow 完成。

### 5.9 从工作流准备到现场交付的操作路径

以下是跨页面的使用顺序，不是后台自动执行链：

1. 在“工作流编辑/工作流”中创建、导入或选择 Workflow，编辑节点、公开输入输出并按既有方式验证和发布；准备对应 Runtime 与 Trigger。
2. 在“应用”中新建 amvar app，选择已有 Workflow/Runtime/Trigger 作为组成成员；加入成员不创建副本，也不改变其运行状态。
3. 在应用的界面设计中声明命名来源及契约依据，配置输入、显示组件和明确目标的动作；用标记的示例数据做不执行的界面预览。
4. 保存界面草稿，明确选择试运行映射，按需要点击指定动作验证；真实副作用沿用正常调用，不自动执行其他来源。
5. 发布界面，配置生产入口的界面版本和完整来源映射，并明确指定应用默认入口；不增加逐 Runtime 显示交付配置。
6. 根据现场需求显式启动所选 Runtime、启用所选 Trigger，再打开生产页。成员已经运行时不要求为页面重新启停；页面打开、关闭或重连不改变执行状态。
7. 交付时从应用选择范围、检查依赖并下载应用包；目标环境上传、预检、确认映射、恢复，再按第 10 节逐资源启用和验证。

| 所在页面 | 操作对象 | 不能混同的操作 |
| --- | --- | --- |
| 工作流编辑/工作流 | 单 Workflow 草稿、发布版本及 JSON 文件 | 导入工作流不是上传恢复整个应用；发布工作流不是发布界面 |
| 应用组成 | amvar app 成员引用与默认入口 | 保存组成不是发布所有成员，也不是启动应用进程 |
| 运行界面设计 | 界面草稿与独立界面版本 | 界面预览不是执行 Workflow；界面发布不更新生产入口 |
| 运行入口配置 | 界面版本与来源到 Runtime 的映射 | 配置映射不是切换 Runtime 的 Workflow 版本 |
| 生产运行页 | 公开输入请求和各来源结果显示 | 不编辑节点、界面文档或正式入口映射 |
| 应用下载/上传恢复 | 所选组成、准确版本、配置和依赖 | 不是平台发行包安装、数据库备份或历史执行恢复 |

## 6. 在线结果传输、前后端隔离与稳定性

### 6.1 来源与通信

```text
HTTP 页面调用 / ZeroMQ / 本机共享内存 / 目录 Trigger
                         ↓
                  现有 Runtime 执行
                         ↓
                 统一公开输出处理边界
                 ├─ 原 HTTP/SDK/Trigger 返回与资源清理（不等页面）
                 └─ 有订阅且可立即交接时，交给独立显示通信层
                                      ↓
                          WS JSON/文本/Base64 图片/资源引用
                                      ↓
                          本项目 Vue 页面 / 第三方独立前端
                          （引用正文按需通过受控 HTTP 读取）
```

显示交接在统一执行完成结果边界完成，不读取 SDK 包装层或 Trigger 回传结果作为唯一来源。Trigger 可不回传某个字段，页面仍可显示完整的 App 公开输出；这是独立的显示交付，不扩大第三方业务响应。失败执行交付其实际终态和错误，有实际公开输出才附带，不能由页面构造成功结果。

复用现有版本化 REST/WebSocket 路由规范、token 校验和连接管理，不新增分级权限。HTTP 负责公开输入提交、文件上传、管理和资源读取；WebSocket 直接交付结构化结果，包括公开 Base64 图片，不要求每条结果再经 REST 查询同一份 JSON。单条完整消息上限为第 6.4 节定义的 64MB。登录用户具有全部操作权限，独立客户端使用与 SDK 相同的默认全权限用户永久 token；纯监视页面不显示执行按钮只是界面配置，不是只读账号。远程浏览器访问 backend 地址，不连接 Worker、mmap 或服务端 file 路径。无需新增前端框架、Redis、MQ 或独立微服务。

订阅关系由 backend 通信层维护，执行器不管理浏览器连接，也不因页面改变节点执行。第 6.5–6.7 节固定首版结果 endpoint、消息语义和认证方式，均为待实现接口；“执行逻辑与协议不变”不等于零代码接入或零成本。当前同步 none 路径的普通 WorkflowRun 完成事件与记录分支关联，none + event-only 的临时异步完成回调也不是完整公开结果出口。新增交付必须覆盖第 6.9 节的全部路径，脱离历史记录开关，不为页面开启 minimal/full 或写入 Runtime 事件历史。

同页重复 Runtime 可复用当前连接，跨页面只向持有效 token 且明确订阅该 Runtime 的连接发送，不因任意 WebSocket 在线就广播全部 Runtime。来源映射决定页面如何分区，不改变结果身份，也不建立跨来源全局顺序、业务关联或原子结果承诺。不新增应用专属 Broker、连接内多路订阅协议或结果缓存。

### 6.2 订阅与交付行为

| 情况 | 明确行为 |
| --- | --- |
| 无对应 Runtime 有效订阅 | 不做新增的显示准备、保存或发送；出口只有轻量需求判断；图中已有编码/保存节点照常执行 |
| 存在正常订阅 | 交付当前完成执行的公开结果，同次交付不因页面数量重复执行节点 |
| 首次打开或刷新 | 读取配置/当前 Runtime 状态后建立连接，等待后续结果，不获取历史 latest |
| 连接建立时执行已经在途 | 只交付在有效订阅期间经过结果交付点的结果；错过交付点不补读、不重跑 |
| 断线或服务重启 | 不保留断线期间结果，重连后接收后续结果 |
| 最后一个连接关闭 | 后续执行不准备显示结果；已在交付中的数据及时释放，不改变执行资源正常清理 |
| 同一连接仍在发送上一条，新的结果到达 | 只跳过该连接的本次显示交付，不缓存待发项，不取消上一条在途消息；业务调用和其他可用连接继续 |
| 连接发送超时、断开或失败 | 结束并释放该连接的在途传输，不重试历史结果；其他连接及业务调用继续 |

每条结果消息发送该 Runtime 本次执行的完整公开 binding mapping；控件在客户端选择其中的字段，不向服务端提交组件列表或字段投影。同一 Runtime 的不同页面因此使用同一种消息，不逐客户端重新构造不同业务结果。不需要显示结果的来源只读取既有 Runtime 状态，不建立结果连接。该取舍减少动态过滤逻辑，但只显示一个字段的页面也会收到该 Runtime 的全部公开输出；需要减少正文时由 Workflow 调整公开输出或使用独立监视 Workflow。

公开输出的展示选择属于界面绑定，不新增 Runtime 显示启用配置。连接与 token 的有效性只控制结果交付，不改变 Runtime 成功判定、返回协议、记录模式或资源执行顺序。断开可能与一次已开始的交付重叠，必须释放在途数据，不能承诺断开瞬间已经发生的全部成本消失。

页面只提供当前连接的在线监视，不要求低延迟帧流，也不保证每次执行都逐条可见。发送尚未结束不等于连接故障，不仅因下一条到来就断开慢连接；真正的发送失败/超时才关闭。跳过更新后可能停留在之前收到的结果，直到下一次可接收交付；显示执行身份和时间，不声称一定显示服务端最后一次执行。可靠保存、最新文件读取、历史查询、统计、业务合格判定及跨 Workflow 汇总由 Workflow 节点实现，再提供公开输出。首版不采集逐节点中间数据或提供逐节点实时进度；既有 Runtime 状态接口只描述实例状态，不伪造执行百分比。

### 6.3 Preview 现状、可复用图片方式与资源释放

现有编辑器的实际路径与新规划必须区分：

1. `Image Preview` 通过 `build_preview_response_image_payload` 产生图片 body，默认 `inline-base64`，也支持 `storage-ref`。编辑器同步 Preview 的直接 HTTP 响应可带原始结果；已有 WS 主要通知状态，前端再读取 HTTP 详情，不是已经存在的生产 Base64 图片结果流。
2. 浏览器发现 `image_base64` 时构造 data URL 显示；发现受控 `object_key` 时通过 HTTP 获取 Blob，再创建 Object URL。新结果替换或页面释放时清理旧 URL。
3. Preview 的高分辨率处理会产生最长边 1920 的显示缩略图；具备 Preview artifact 路径等条件时可能将原图改为存储引用。持久化/事件使用的清理逻辑还会移除 Base64 正文。不能将这些内部数据、截断记录和隐藏显示优化当成完整生产输出，也不能整体复用 Preview 的历史、轮询和资源所有权。

新运行页复用的是图片编码格式、受控读取和浏览器显示基础，不是 Preview Run 的会话与记录机制。首版同时支持两条明确路径：

| Workflow 公开输出 | 传输 | 保存和生命周期 |
| --- | --- | --- |
| `Image Base64 Encode` 的 `image-base64.v1`，或 `Image Body` 明确选择 `inline-base64` 的 `response-body.v1` | 编码图片与 JSON/文本一起通过 WS JSON 消息发送；浏览器解码显示 | 无需添加 Save 节点，不为显示落盘；只保留当前在途正文与页面当前画面 |
| 已保存图片/文件的有效公开引用，或 `Image Body` 明确选择 `storage-ref` | WS 发送引用和元数据；浏览器按需经受控 HTTP 读取正文 | 文件由 Workflow/已有资源系统管理；显示模块不复制、保留历史或决定保存期限 |

- 上述 `Image Base64 Encode` 和 `Image Body` 及其通用 `build_response_image_payload` 已存在；待实现的是独立生产结果交付与页面适配，不另造界面专用图片节点。正式内联方式不沿用 Preview 隐式缩略图策略。
- **图中显式编码是 Workflow 执行成本。** 即使没有任何页面连接，图中配置的图片编码节点仍按原执行语义运行；不能因订阅人数改变节点执行。无订阅只省去新增显示序列化、传输等成本。高性能生产图可继续保存结果，由独立监视 Workflow 读取并编码。
- LocalBuffer/mmap 引用不是浏览器可读取资源。内联方式必须由图中的通用节点在资源有效时完成编码；交付已拥有独立内容的字符串，不在执行资源释放后读取失效引用，不等待页面消费或延长核心租约。无落盘 Base64 已纳入首版；直接向浏览器暴露临时内存引用不在范围内。
- 编码格式、质量、尺寸以及是否保存由 Workflow 明确选择。显示层不自动缩图、重编码、隐藏保存或超限后偷偷改成 HTTP 引用；组件缩放显示不等于改写原始业务图片。
- 页面不扫描目录、不猜最新文件、不根据文件名配对 JSON 与图片。公开引用要能定位对应执行内容，不能把可被覆盖的路径当作不可变内容身份。
- 资源接口校验有效 token，只读取明确公开的资源，不开放任意绝对路径。全权限不取消现有 ObjectStore 公开命名空间、路径和文件类型边界。磁盘 Save 的任意路径不自动成为公开 HTTP 地址；未公开的文件由普通读取/编码节点转换为公开输出。
- 存储引用的内容身份在图片阶段落实：使用已有不可变资源身份，或公开引用中明确的内容摘要并校验读取正文。仅凭路径、文件长度或修改时间不能保证同次执行。摘要应在已有节点编码/保存/读取正文时生成，不在显示交接热路径重新扫描文件；读取校验失败只报告资源已变更。缺少可靠内容身份时不能宣称具备覆盖检测，可在 Workflow 中显式选用内联 Base64；显示层不自动复制文件或延长保存期限。
- 已删除、被替换或无法读取时报告不可用，不以同目录其他文件代替；传输不得将旧结果说明与新文件内容混合。当前通用公开文件 GET 不保证摘要核验，不能把目标设计当作已有能力；第 12 节图片阶段须完成同路径覆盖及读取竞争测试后才验收引用显示。
- 后端只持有当前传输必需的数据并及时释放。浏览器只持有当前画面和在途读取/解码资源，新结果替换或页面关闭时释放旧消息引用、Object URL、图片请求和监听器；旧回调不能覆盖新结果。Base64 字符串、Blob 和解码像素不得分别追加历史集合。
- 显示模块不拥有生产保存文件，不因页面关闭、断线或资源失效删除它们。保存期限和数量清理由 Workflow 决定。

### 6.4 无结果队列、无缓存的性能边界

不新增结果队列、latest 缓存、显示快照集合、数据库记录、磁盘显示历史、可靠重发、确认消费或补偿系统。也不按连接保存待发送的执行结果列表。实时显示可以错过更新，但不能丢弃、合并或抑制实际 Workflow/Trigger 调用。

网络发送不可避免占用在途数据和协议栈缓冲；这不等于建设应用级结果缓存。同一连接只处理当前在途消息，无待发送结果槽或列表；仍忙时只跳过新的显示交付，不阻塞 Runtime 或其他客户端，不缓存“下一条最新结果”。浏览器解码/渲染也不建立历史待处理列表；忙时允许跳过整条显示更新，不把它拆成不同执行的字段。发送失败/超时按第 6.2 节关闭连接，超时是释放失效传输的边界，不是生产显示帧率要求。

核心结果出口只做轻量需求检查和可立即完成的交接，接不下就跳过显示。面向页面的 JSON 序列化、网络等待和浏览器确认不得放在 Worker 执行锁、同步返回的等待链或 Trigger ACK 的完成条件中；也不得持有执行资源等待发送。连接发送由通信层处理，不能把队列改成每次执行都创建的无界 `create_task`、线程池任务或事件循环回调列表。每个连接以及共享交接处都必须有明确在途上限，不靠积压掩盖慢网络。

**64MB 限制口径：** 本设计沿用产品用语“64MB”，实现常量固定为 `64 * 1024 * 1024 = 67,108,864` 字节，即 64MiB。限制对象是发送给一个客户端的一条完整 UTF-8 JSON WebSocket 消息，含消息骨架、所有输出、Base64、字段名及转义后的正文；按未压缩消息计量，不是原始图片字节数、单张图片大小或单个 WebSocket frame 大小。

- 小于或等于上限可交付，超过上限拒绝该条显示结果，释放传输数据；业务执行及原返回不受影响。多个图片字段、嵌套 Base64 和其他 JSON 合计计算，不能把每张图片分别当成 64MB。
- Base64 正文长度约为编码图片字节数的 4/3，实际还有 JSON 开销。因此不能承诺传输一张原始编码文件大小 64MB 的图片，也不能按解码前字符串字符数忽略 UTF-8 其他字段。
- 超限不截断 JSON、不丢字段后冒充完整结果，不自动落盘/缩图，不应用层分批拼包绕过限制。通信层用简短显示错误说明原因与关联执行身份；该诊断也不排队、不保证离线送达，不把业务成功改为失败。
- 该上限只针对新增页面结果流；不全局放大已有任务/训练/Preview WS 的限制，不修改 HTTP 上传、SDK、ZeroMQ、本机共享内存或目录 Trigger 协议。浏览器输入继续走现有 HTTP，不新增 WS 执行命令。
- 实现须在复制或编码超大消息前做有界检查，并对实际 JSON 编码字节数核验；不能先在核心线程构造无上限大字符串再检查长度。服务端发送、客户端接收与解码检查按相同口径测试，代理设置不能无意采用更小上限或依赖压缩绕过上限。
- 64MB 是协议上限，不是单连接总内存或浏览器图片解码内存上限，也不是吞吐/延迟保证。JSON 字符串副本、Base64 解码与大尺寸图片像素均会占用额外资源；像素/解码、连接数量和发送超时的实现限制须实测并显式说明，不能隐藏降级。浏览器已有接收缓冲不能被描述为应用能完全控制的零缓冲。

现有 `InMemoryServiceEventBus` 使用订阅队列。新实时结果通道只能复用适合的鉴权、路由规范和连接管理，不能原样套用其排队语义后宣称无队列。已有任务、训练、Preview、Runtime 状态流维持原行为，本次不全局删除或改造它们。在线结果的一次非阻塞交接实现必须检查从线程/进程出口到网络发送的全链路，不能只限制最后一段。当前 `send_json` 在 await 网络发送前同步序列化 JSON，仅把调用放进 async 函数并不隔离大消息的 CPU 成本。

在提交事件循环回调、创建任务或提交序列化执行器之前，先取得有界的当前在途名额；未取得立即跳过本次显示，不在调用线程等待。连接状态只允许 `idle → preparing/sending → idle/closed`，没有 pending-next。相同执行向多个空闲连接交付时可共享本次编码后的不可变正文，最后一个在途使用者结束即释放，不保留作重连或后续页面使用。后台执行器也不能积压任务，异常和取消均须归还名额。具体执行器由基准选定，不把线程池当作解决 GIL 竞争的保证。

实施阶段必须公布连接上限、全局在途字节预算、序列化并行上限、发送超时及客户端图片解码/像素限制的实际值。只有这些上限同时受控，才能证明多连接内存有界；不能按“每条不超过 64MB”直接推导总内存稳定。数值通过第 12 节原型测量冻结，超出只影响新增显示交付，不修改核心调用容量。标准浏览器 WebSocket 没有应用可用的接收背压控制，后台标签页等场景也需实测；客户端忙时跳过显示更新不等于网络接收缓冲完全消失，不为此增加业务 ACK、消费确认或结果队列。

显示序列化、交付和资源读取失败只影响显示，不覆盖业务终态、SDK/Trigger 响应或中断核心资源清理；Workflow 中显式图片编码节点失败仍是正常的节点执行错误，不能被显示层吞掉。无订阅路径不新增每次执行的图扫描、数据库查询或显示文件操作；有订阅时仍有序列化、网络和读取成本，不能承诺绝对零开销。即便逻辑解耦，共享 CPU、进程/GIL、内存和磁盘仍可能竞争；必须实测核心返回和下一次调用，不只测试 WS 是否后台发送。性能不达标先缩小显示接入成本，不能靠业务排队、延迟 ACK 或延长租约解决。

实施前后按相同输入比较无浏览器、单页面、多页面、慢网络、反复连接断开及共享磁盘负载。既有同步双实例合理负载、Preview 运行和 none 模式须保持正确；所有数值和长期稳定结论来自实测，短测不能替代工业认证。

### 6.5 实时消息与当前画面关联

首版新增路径固定为 `/ws/v1/workflows/app-runtimes/results?workflow_runtime_id=<id>`，使用第 6.7 节的现有 token 方式认证。此路径尚未实现，不与已有 `/workflows/app-runtimes/events` 混用。一条连接只指定一个 Runtime，无需 amvar app、界面或入口 ID；不接受 `after_cursor`、字段筛选或连接内执行命令，不支持补发或按结果 ID 查询。Runtime 停止不阻止订阅，是否执行仍由现有 Runtime 规则决定。

复用现有消息骨架并固定如下取值；代码阶段据此形成单一后端 Schema、TypeScript 类型和独立客户端合同样例，不再另造一套前端专用结构。

| 骨架字段 | 类型与取值 |
| --- | --- |
| `stream` | 固定字符串 `workflows.app-runtimes.results` |
| `event_type` | 下表所列完整事件名 |
| `event_version` | 固定字符串 `v1` |
| `occurred_at` | UTC ISO 8601 时间字符串，表示事件产生时间 |
| `resource_kind` | 固定字符串 `workflow_app_runtime`，沿用既有资源种类拼写 |
| `resource_id` | 本连接订阅的 Runtime ID 字符串 |
| `cursor` | 始终为 JSON `null`，不生成可恢复游标 |
| `payload` | 对应事件的 JSON 对象 |

| `event_type` | payload 规则 |
| --- | --- |
| `workflows.app-runtimes.results.connected` | 仅返回 `max_message_bytes: 67108864`，表示连接建立；不是执行结果，不携带历史数据 |
| `workflows.app-runtimes.results.completed` | 下述完整终态消息 |
| `workflows.app-runtimes.results.display-error` | 下述显示交付诊断，不改变 Workflow 终态 |
| `workflows.app-runtimes.results.heartbeat` | 空对象；沿用连接保活方式，不查询业务执行进度 |

连接响应完成后才登记可接收结果的订阅，登记前完成的执行不补发。保活与结果共用连接的当前发送占用，不能在大消息发送期间并发写入或另建保活积压。

`completed.payload` 的字段固定如下，全部字段存在，只有明确允许的字段可为 null：

| 字段 | 类型与含义 |
| --- | --- |
| `project_id`、`application_id` | 非空字符串，实际执行所属 Project 与既有 Workflow App；不是 amvar app 身份 |
| `workflow_runtime_id`、`workflow_runtime_revision_id` | 非空字符串，实际执行实例及 revision |
| `runtime_generation` | 整数，原执行上下文中的 generation，不自行计数 |
| `workflow_app_version_id`、`workflow_run_id` | 非空字符串，实际发布版本与已接受执行的身份 |
| `completed_at` | UTC ISO 8601 时间字符串，表示最终完成时间 |
| `workflow_state` | `succeeded`、`failed`、`timed_out`、`cancelled` 之一；不代替业务合格字段 |
| `outputs` | JSON 对象，键为公开 binding ID，值为该 binding 的原始类型化 JSON payload；无实际公开输出时为 `{}` |
| `error` | 成功时为 null；其他终态为含 `code`、`message` 字符串及 `details` 对象的错误描述；优先保留既有错误码/详情，无错误码时使用 `workflow_run_failed`、`workflow_run_timed_out` 或 `workflow_run_cancelled`，不嵌入内部堆栈、节点记录或凭据 |

版本、generation、run ID 在接受调用时从真实执行上下文固定，不在完成后查询 Runtime 当前版本来拼装，也不从业务 JSON 猜测。没有成功建立执行身份的 admission 拒绝、无效请求仍走既有调用错误，不虚构一次 completed。资源清理失败按核心最终判定发送失败，不先发送成功再更正。

`display-error.payload` 携带同样的执行身份、`completed_at`、`workflow_state`，以及 `display_error: {code, message}`；不携带 `outputs` 或重复业务 `error`。首版诊断码固定为 `workflow_result_message_too_large`、`workflow_result_serialization_failed`。该诊断只在当前在途名额内尽力发送，不另建待发队列；超时/断线时无需保证诊断可达。图片 HTTP 读取或浏览器解码失败由组件显示资源错误，不伪造服务端 completed。

连接校验复用现有约定：无效 token 为 `4401`，缺失/非法 Runtime 参数或不支持的恢复/筛选参数为 `4400`，Runtime 不存在为 `4404`；显示连接容量不足为 `4429`，发送失败/超时关闭使用 `1011`。握手被拒绝时浏览器未必能读取服务端关闭原因，页面同时显示连接失败，不把缺少关闭详情解释为 Workflow 失败。

结果在同一连接按服务端完成结果交付顺序显示，不重排为调用开始顺序，不比较不同 Runtime 的全局序号。页面只保留当前收到的结果；图片、JSON、文本按其执行 ID 一起关联。旧连接、旧 Runtime generation 的回调不能覆盖新来源，迟到的图片读取回调不能覆盖更新后的画面。连接生命周期标识仅在本地隔离旧回调，不构成历史恢复系统。

WS 的 `outputs` 始终按公开 binding ID 保留键，即使只有一个输出也不展平、不删掉类型 payload 包装。结果取自执行完成时的公开 binding 输出，不取内部 `node_records`、SDK 的 `data` 包装、Trigger 的 `response_payload` 或经过脱敏/截断的历史记录。实际 Runtime/版本/执行身份由后端提供，不要求 Workflow 手工生成，也不从业务 JSON 中同名字段猜测。

现有 HTTP `app-result` 在成功且只有一个公开输出时会直接返回该输出，多输出时返回 mapping；成功响应并不保证有 `workflow_run_id`。内置页面手动调用显式使用现有 `response_mode=run`，取得真实 run ID、版本和状态，不改变 HTTP/SDK 的默认 `app-result`。第三方若仍选 app-result，不凭“下一条 WS”或到达时间猜测手动请求的执行身份。显示区始终标明自己实际收到的执行身份。HTTP 响应不反向覆盖实时区，不维护两套结果集合、锁定模式或服务端本次结果接口。

`response_mode=run` 仍可能在 HTTP 中返回与 WS 相同的公开图片正文；首版接受并明确测量该重复传输成本，不为了省一次手动响应修改原协议、偷偷删字段或开启 debug。前端只用 HTTP 确认本次请求并及时释放不再使用的正文，不将 HTTP 和 WS 各保存一份显示历史。外部 Trigger 调用不因这一页面选项改变返回数据。

none 模式下手动调用复用既有 HTTP 同步 invoke；浏览器异步等待 HTTP 不等于创建持久化异步 WorkflowRun。不为了页面修改 none 为 minimal/full，也不通过历史 Run 查询恢复画面。需要历史或最新保存结果时，由普通 Workflow 明确读取并公开输出，页面打开不自动调用它。

试运行与生产手动执行继续复用已经存在的：

- `POST /api/v1/workflows/app-runtimes/{id}/invoke?response_mode=run`
- `POST /api/v1/workflows/app-runtimes/{id}/invoke/upload?response_mode=run`

使用既有 `run` 响应，不默认 debug，不引入界面专用执行引擎或新的结果包装层。当前 invoke 的 `workflows:write` 检查可由现有默认账号的 `*` 权限通过；不为页面新增操作员角色、专用 scope 或第二套调用认证。响应模式与 `record_mode` 分离，不为取得 run ID 产生历史记录。

页面从动作 `source_id` 解析目标 Runtime 后复用该目标的既有接口；`amvar_app_id`、来源映射和动作编辑配置不混入 Workflow 公开输入。新增应用不是另一个可统一执行全部成员的 invoke 端点。

不为页面新增 revision 请求头、显示参数或调用阻断协议。实际执行版本沿用既有 Runtime 规则，页面按实际返回身份处理，版本变化后的输入问题按正常执行反馈。现有请求解析支持顶层公开输入，不能将界面身份或控制字段塞进 JSON 顶层冒充 binding；JSON/multipart 与 SDK 均保持原有契约。

### 6.7 全权限用户与统一 token

本功能采用简单的统一规则：登录用户拥有查看、调用、编辑、发布、应用管理及部署管理的全部权限，不新增角色、应用 ACL、Project 授权配置或细分 scope。纯监视/交互页面只是按钮与控件配置，不是不同权限级别。默认沿用现有全权限账号及其永久调用 token，与 .NET SDK 使用同一认证机制，不为 amvar app 或每个 Runtime 单独签发 token。

当前本地认证的事实与新设计分开表述：默认账号为 `scopes=("*",)`，长期 user-token 默认不过期；登录返回的 session access/refresh token 则有自己的期限。内置页面继续复用现有登录态，不把短期登录 token 宣称为永久 token；独立页面/SDK 使用配置好的默认用户永久 token，不自动将登录令牌转换成永久令牌。既有认证模块还支持受限账号，本次不新增或依赖这些分级能力，也不隐式迁移现有账号、重置 token 或删除旧认证接口。

| 调用方式 | 认证方式 |
| --- | --- |
| HTTP 调用、管理与公开资源读取 | `Authorization: Bearer <token>`，复用现有 token 校验 |
| 能设置握手头的 WS 客户端 | 同样使用 `Authorization: Bearer <token>` |
| 浏览器标准 WebSocket | 使用现有 `access_token=<URL编码后的token>` 查询参数；依赖既有 `websocket_query_token_enabled` 配置，不新增票据交换或 WS 登录命令 |

永久表示没有默认到期时间，不表示撤销/禁用后仍有效。无效、撤销或账号失效时沿用现有认证机制拒绝连接/请求；断线重新连接重新校验，不因认证恢复自动重放业务请求。不为每次 Workflow 执行新增用户表查询或显示权限查询，连接存续期间的认证处理复用已有机制，不承诺尚未实现的即时全连接撤销。

页面分享地址、界面发布文档和 amvar app 包不携带 token；浏览器 WS 握手查询参数是连接凭据，不应复制成分享链接，也不得写入可见日志。客户端只向明确配置的 backend 发送凭据，异机访问按现场要求使用 HTTPS/WSS。第三方配置同一个现有 token 即可调用，不硬编码开发默认 token，不新增凭据代理或权限管理页面。

全权限不改变资源是否存在、Runtime 必须显式启动、发布快照不可直接修改、停止态恢复、参数/文件路径校验等功能规则。来源系统的账号信息不从应用包恢复；目标环境使用其已有默认账号和 token。现有 SDK 配置下载的 `include_access_token` 选项保持原语义，不能为应用包排除凭据而顺带修改 SDK 下载默认行为。

### 6.8 第三方独立前端与标准交付

内置运行页只是标准客户端之一。第三方可自行设计、部署页面或其他显示客户端，使用相同默认用户永久 token 读取 Workflow 公开契约、调用目标 Runtime 的 HTTP 接口、订阅对应 WS 结果，并通过受控 HTTP 获取引用资源；不必先创建内置界面文档、安装内置设计器或读取 Vue/Pinia 状态。多来源客户端使用明确 Runtime 身份关联，不把选择多个来源变成后端批量执行命令。

- 本项目维护的前端仍统一 Vue 3、随发行包本地分发；第三方独立实现可自行选择技术栈，不要求本仓库维护另一套 React/其他框架。也不把第三方页面任意脚本上传成可信核心组件。
- 前端可与后端分机部署，通过配置的服务地址访问；同源部署优先，跨源部署明确允许来源、HTTP CORS、WS 握手 Origin、鉴权及 HTTPS/WSS/代理规则，不关闭授权来实现可访问。复用项目身份体系，浏览器不能任意设置 WS Authorization 头的限制需在接入文档说明；不把管理凭据固化在页面或包中。
- UI 打开/关闭、重连、显示失败或更换供应商不启停、取消或重发业务执行。第三方订阅也受同样 64MB、无积压/无历史、token 校验、公开资源及连接释放规则约束，不获得特殊的 core/worker 访问路径。
- 公开契约独立于组件：实施交付必须包含精确 endpoint、消息版本/完整 Schema、公开输入输出 payload、成功/失败示例、64MB 字节口径、慢连接/超限/重连语义、资源读取、鉴权与错误码。内置页面和独立测试客户端使用同一规范通过合同测试，不能把读内置前端源码作为接入前提。
- 使用内置界面时，界面文档、主题、组件和入口映射随 amvar app 包交付。第三方完全独立部署的页面不自动被平台抓取或打包；核心 Workflow/Runtime/Trigger 包仍可按所选范围恢复，第三方页面资产和交付依赖必须明确声明，不能冒充已包含。页面切换不要求重新发布这些核心成员。

### 6.9 统一终态交接的实现顺序

源码核对表明不能只在 HTTP 路由或一个成功回调加广播。实现需逐项覆盖以下现有路径，最终汇入同一个轻量交接接口；以下是改造位置说明，不是新增执行模式。

| 路径 | 当前接入缺口 | 实现要求 |
| --- | --- | --- |
| 同步 Runtime，含 `record_mode=none` | 普通完成事件受记录分支影响；HTTP 与 Trigger 可创建不同 service 对象 | 使用清理后实际终态及原始公开输出，交接独立于持久化和 HTTP/Trigger 响应组装 |
| 持久化异步 Runtime | 完成回调可能清理/截断持久输出，成功、失败、超时、取消出口分开 | 各终态共用交接，公开正文取自本次实际结果，不从历史查询或已有短期 raw-output 缓存回读 |
| `none + event-only` 临时异步 Runtime | `_build_transient_async_run_callbacks` 当前未捕获 run ID；成功通常直接返回，取消回调为空 | 捕获接受调用时已有 run ID、版本与 generation；补齐各终态的显示交接，不创建 WorkflowRun 历史或为了显示改变 event-only 行为 |
| 请求格式/admission 拒绝 | 请求可能未成为一次被接受的执行 | 保持现有错误响应，不生成伪造的 run ID、业务输出或 completed |

1. 在 backend 应用生命周期中管理唯一的显示通信组件，HTTP 依赖工厂及 Trigger 使用的 service 工厂注入同一实例。请求结束不销毁全局订阅，服务关闭释放连接与当前在途数据。不在 Worker 中建立浏览器会话，也不按每次调用重新创建发送器。
2. 在现有接受调用位置固定只包含标量身份的执行上下文。none 异步已有执行 ID，应传给回调，而不是完成时生成另一个 ID；版本和 generation 同样不能查询当前值替代。此上下文不构成历史缓存，生命周期不超过本次执行/交接。
3. 先完成核心的结果判定和原有资源清理，再由应用服务交接已独立持有的公开 payload。`snapshot_execution` 在清理前构造输出不等于最终成功点；不得从该位置提前广播成功。清理/worker 故障由既有核心规则决定终态，显示不捕获或改写这些错误来伪装成功。
4. 成功、节点失败、超时、取消与 worker 异常都走统一的“终态已确定”交接。沿用现有 run/generation 防迟到回调机制，同一执行只进行一次终态交接，不新建永久已发送集合。显示交接异常局部处理，原同步返回、Trigger ACK 和核心清理继续按原规则完成。
5. 无对应订阅在检查身份后立即返回，不扫描图/公开正文、不复制 Base64、不查询数据库。存在空闲接收能力时按第 6.4 节先取得有界名额再交接。只传公开输出及小型上下文，不把整个 WorkerResult、内部节点记录、原图矩阵或 mmap 句柄挂到后台任务。共享正文必须保证交接后不被原响应处理原地修改；优先明确不可变所有权，不在核心热路径深拷贝大结果。
6. 在此最小链路上先验证同步、异步和 none 的结果一致性、资源释放与 token 接入，再开始显示组件。禁止为了补齐结果流同时改造现有事件队列、Trigger 协议、Runtime admission、模型实例并发或业务记录策略。

## 7. 生产检测与监视维护组合

生产 Workflow 可保持既有高性能调用和 Save 节点；目录 Trigger 调用另一个普通监视/维护 Workflow，后者读取结果、清理文件并通过自己的公开输出供运行界面显示。它们作为同一 amvar app 的独立成员，一个页面可分别显示生产状态、监视图片/JSON 和维护结果，不要求合并节点图。

生产来源可以只使用既有 Runtime 状态接口、不订阅生产结果，由监视来源提供已保存图片及 JSON；选入组成清单不等于订阅每个成员。订阅来源发送完整公开输出，控件在客户端选择显示字段，不增加 Runtime 级图片交付开关。一个来源暂不可用时其他来源继续显示，各来源更新时间独立，不把读取监视结果当成重新执行生产 Workflow。

推荐读取一份在图片保存完成后发布的结果 JSON，由其中的执行/业务标识和图片引用定位同次结果。独立选择“最新图片”和“最新 JSON”不能证明同次执行。该组合使用通用保存、读取、JSON、绘制和维护节点，不新增场景专用节点。

目录 Trigger 的间隔、样本边界和重启语义沿用[现有实施基线](directory-watch-trigger-implementation.md)。它是变化通知，不保证每张图逐条处理；默认 3 秒触发带来相应显示延迟。监视 Workflow 的执行状态不等于生产 Workflow 的逐节点过程。独立 Worker 仍共享磁盘、CPU、内存等物理资源，需要竞争负载测试。

平台不新增 Save 目录与监控目录重叠判断，也不因 Runtime 忙而跳过正常目录触发。读取结果的入口是否使用 request_json 由 Workflow 决定，该输入仍可选。

## 8. Workflow JSON 导入导出

### 8.1 文档范围

导出单个 Workflow 的 Application、Template、公开 binding、节点参数、连线、图布局、分组、说明和依赖声明。复用当前文档格式，最外层交换容器若新增必须有明确 format_id；不复制另一套节点执行 Schema。

不默认导出 Preview 原始数据、临时上传文件、运行句柄或完整模型 bytes。示例输入若提供，必须明确选择、标记并单独处理敏感数据。公开默认值和内部节点参数属于 Workflow 文档，但凭据按敏感字段规则处理，不能因其位于参数中就明文导出。

### 8.2 编辑交互

- 工具栏提供导出/导入，支持文件选择和拖入 JSON。
- 区分导出当前编辑文档与指定发布版本，不以未保存草稿冒充运行态版本。

- ComfyUI 风格指打开/拖入/导出体验，不等于原生 ComfyUI JSON 或节点可直接运行；转换器不属于首版。
- 图片中嵌入 Workflow 元数据可后续评估，首版 JSON 往返不依赖图片容器。

往返比较区分执行语义与编辑数据：参数的缺省/null/false/0、绑定键、边、说明和布局都必须保留；仅在明确“导入为新工作流”时映射 Workflow 根资源身份。

```text
├─ amvar-app.json     本次选择的应用组成和默认运行入口引用
├─ workflows/         多个 Workflow 草稿及所选不可变发布快照
├─ runtimes/          各 Runtime 原有部署配置、版本引用和角色映射
├─ triggers/          各 Trigger 协议配置和输入输出映射
├─ views/             界面文档、所选界面版本、运行入口、主题和静态资源
├─ dependencies/      依赖清单、模型文件、节点包、组件资产
└─ site-bindings.json 目标环境需要确认的目录、端口、地址、资源映射
```

路径只是草案，实施时定义大小写、规范化路径和 manifest 条目规则。包内使用包局部稳定引用标识关联资源，不把 runtime-01 这样的包内角色误作真实 Runtime ID。

manifest 至少定义包格式版本、包身份、来源 amvar app/Project、导出选择范围、各资源引用及版本、文件长度/校验和、平台/组件要求、已包含资产、外部依赖和待填现场配置。`amvar-app.json` 表达可恢复的所选组成；manifest 表达交付事实与依赖，两者由同一个固定导出快照生成并交叉校验，不独立维护成员关系。明确区分包格式版本、应用配置修订、Workflow 发布版本、界面版本和依赖实现版本。

### 9.2 一致导出范围

以 amvar app 组成清单作为选择起点，允许明确选择多个 Workflow、各自的 Runtime/Trigger、界面版本和运行入口。提供“选择全部组成”及按资源选择，不默认打包整个 Project，也不限制为单个 Workflow 根。成员及选项完整分页加载，不能静默漏掉 Runtime 或 Trigger。

导出先展示“主动选择、依赖补齐、外部要求、未包含”四类范围。Trigger 依赖目标 Runtime，Runtime 依赖准确 Workflow 版本，入口依赖发布界面及所有来源映射。取消被依赖资源时只能明确一并取消依赖方、确认补齐，或声明目标环境必须提供的外部资源；不能静默丢掉映射后仍标为完整应用包。

部分导出不修改现场 amvar app 组成；包内清单准确表达本次选择，默认入口未包含时不另选第一项。含外部要求的包标记为需要补充配置/依赖，恢复前必须完成映射；不以“完整离线包”描述它。只有 Workflow 文件交换需求时走第 8 节，不强制打包界面。

包固定当前草稿和所选 Runtime 实际引用的发布版本，不自动使用最新发布版。active/desired 版本不同的配置必须分别表达，不能在导出时悄悄选择或启动 desired。多个 Runtime 使用不同版本时包含其依赖并集；所选界面来源的 `basis_app_version_id` 也是明确依赖，即使不同于 Runtime 当前版本也不能漏掉。其他无引用历史版本可显式增加，不默认无限打包。

界面独立发布并由包固定所选版本，同时保存运行入口逐来源的 Runtime 映射和组件/主题资产依赖，不新增 Runtime 显示配置。相同 Workflow 文件或共享资产可去重，不合并不同 Runtime、Trigger 或模型实例。只打包“怎样显示”的文档，不打包“显示过什么”；当前画面、表单现场值、连接订阅、选中组件、访问令牌和试运行结果不进入包，也不作为发布依赖。

导出先在短事务/一致文档读取边界固定引用及草稿内容，然后复制不可变资产。并发编辑、选版、删除或界面发布不能产生混合文档；检测到选择范围变化时使用明确一致快照或失败重试提示，不长期锁住生产调用等待压缩完成。

### 9.3 依赖完整性

现有发布清单记录直接资源引用，不能据此宣称完整可迁移。需要按明确资源类型解析传递依赖：Workflow → 模型部署实例 → 模型产物/文件/标签与运行要求；界面 → 组件版本 → 主题/字体/图片。Custom Node 依赖也必须有受控声明，不能只扫描字段后缀、任意字符串或整个磁盘猜测依赖。

- 包内携带实际必需资产，或明确声明目标环境依赖；不完整包不能标成无需补充资源的完整离线包。
- 相同不可变模型文件可按校验信息去重；实例数量、资源角色和参数不可合并，尤其保持双实例同步推理配置。
- 模型文件、规则和模板图像可以纳入依赖；配置中的监控/输出目录不意味着该目录的全部生产数据都是资产。
- 共享依赖可匹配复用；不自动覆盖其他 App 使用的模型、节点包或组件包。
- 包不包含整个 SQLite 数据库、所有项目账号、系统 Python/conda、GPU 驱动或平台安装目录。平台/64-bit/运行库要求列入 manifest，沿用源码 conda 与同目录发行 Python 边界。
- 普通包不保存明文密钥、token、模型服务凭据，保留敏感引用和待补配置；密钥迁移若需要，须另行定义受控加密方案，不借本文自动实现。
- 自定义可执行节点/组件携带内容与允许安装是两件事；哈希只证明完整性，不证明信任。缺失代码不通过导入自动执行 pip、构建脚本或任意 JavaScript。
- TensorRT 等运行产物须校验目标平台、运行库和硬件兼容性；不得自动换后端、重转模型或将不匹配资产当作兼容。

### 9.4 不打包的执行状态

不打包 PID、Worker epoch、GPU 内存、mmap、LocalBuffer lease、锁、socket、待执行任务、重试队列、幂等缓存、未提交目录窗口或 Preview 缓存。历史运行记录、生产保存图片/JSON 默认不包含，需要历史数据迁移时另定范围，不混入应用恢复。

## 10. 上传恢复与迁移

### 10.1 统一步骤

1. 上传到本次操作的 staging，流式计算长度和 checksum。
2. 校验包格式、文件清单、路径、容量、依赖及平台兼容性；尚不运行包内代码。
3. 展示恢复计划：amvar app 组成，以及各成员的新建/复用/冲突/缺失、版本关系、来源映射、现场映射、敏感待填项和部署实例数量。
4. 明确选择导入为新应用或恢复原应用，逐成员确认身份策略及目录、地址、端口、设备和资源映射；复用资源须明确选择，不能因名称相同自动复用。
5. 按依赖顺序写入资产与声明，经校验形成不可变 Workflow 版本，再创建停止态 Runtime、禁用态 Trigger，恢复应用组成、界面版本和逐来源运行入口。整个操作完成前不作为已完成应用交付；不恢复结果、连接或不存在的 Runtime 显示配置。
6. 回读核对各 Workflow/Runtime/Trigger、来源契约、入口映射、checksum、跨 Workflow 的明确文件引用及 SDK 配置，输出完整或待补状态；不能把未完成恢复标记为可运行。入口可以打开查看配置状态并等待后续实时结果，不能因为打开页面而启动或执行，也不恢复旧画面。
7. 用户明确选择启动/启用哪些资源后才允许执行，逐资源报告结果，不自动启动全部成员；测试调用也必须独立确认，不能因恢复验收自动执行删除或保存节点。

### 10.2 身份和版本

| 操作 | 处理 |
| --- | --- |
| 导入为新 amvar app | 生成独立 amvar_app_id；新建的每个 Workflow App/Graph 各自使用同一组 14 位时间标识，多个 Workflow 不能共用一组；Runtime 由平台生成 UUID；按引用表映射组成、Trigger、界面来源及入口 |
| 恢复原 amvar app | 身份可用时保留 ID；成员逐一检查，冲突先报告，只有明确处理停止态目标后才允许替换；不覆盖其他应用共用资源 |
| 快照内容未改变 | 保留原不可变内容与来源校验信息，并校验目标实际依赖 |
| ID/路径/模型引用重映射改变文档 | 保留来源信息，创建导入派生版本和新指纹，不修改原快照冒充原版本 |
| Runtime 恢复 | 重建 Worker/通信身份，不复制原 PID、epoch 或活动 Run；同机替换遵守既有 generation 防迟到回调规则 |

只在明确声明的资源引用和路径字段上做映射。普通文本、任意 JSON、动态路径表达式不全局替换、不猜测。多个 Workflow 的保存/读取以及目录 Trigger 的路径关联仅按明确现场映射维护，不从相同路径字符串自动推断业务关系；不新增目录重叠防呆策略。导入时 `source_id` 和 `component_id` 保持文档内稳定，映射所指的资源身份，不能按新 UUID 重新排列后配对。

Trigger 命名沿用项目标准：`zeromq-<workflow-runtime-id>`、`local-shared-memory-<workflow-runtime-id>`；多个 directory-watch 使用其既有唯一命名规则，不强行合成一个 Trigger。端口/地址冲突报告后明确配置，不静默换端口。

本次新建/替换的 Runtime 保持停止、Trigger 保持禁用；运行中资源不能被恢复操作直接覆盖。明确复用的既有资源保持原状态，不为了停止态恢复而擅自停止其他应用正在使用的资源；恢复计划必须区分新建/替换与外部复用。默认新建执行资源，需要全部停止的交付不能复用正在运行的实例。目录 Trigger 在后续显式启用时重新建立当前观察基线，不回放恢复前事件、不为了处理旧文件额外触发一次 Workflow。

### 10.3 SDK 配置

按目标环境实际 Runtime、Trigger 和调用地址重新生成，不沿用来源机器 endpoint。命名仍按每个既有 Workflow App 单独计算：单 Runtime 使用 `config_<workflow-app-id>.json`；多个 Runtime 使用 `config_<workflow-app-id>_runtime-01.json` 等，已有 01–08 示例不是新增数量限制。不能用 amvar_app_id 替换文件名中的 Workflow App ID，也不能把多个 Workflow 各自的单 Runtime 错算为同一个 Workflow 的多 Runtime。

包内按 Workflow 组织 SDK 配置，索引明确对应 Workflow ID、Runtime ID、Trigger ID 及配置文件；界面来源通过其 Runtime 映射关联，不依赖目录或编号猜测。恢复不能按新 UUID 排序交换编号和目标。SDK 仍按 HTTP 与高性能 Trigger 各自能力支持输入，接口和响应包装不因恢复改变。账号凭据在目标环境配置，不明文嵌入包。

### 10.4 原子性、安全和容量

- 上传、哈希、压缩、解压和模型资产复制采用流式处理；不能整个 ZIP 或模型加载为 bytes。
- 校验绝对路径、路径穿越、链接/重解析点、重复条目、大小写冲突及解压后容量/文件数量；文件只能落在验证后的本次 staging/正式资源范围。
- 使用现有 Repository/Unit of Work、短事务和可恢复操作记录组织数据库与文件；恢复中断不能留下已经启用的半成品。
- 重试同一导入操作不得重复创建资源。失败只回收本次新建且无其他引用的资源，不删除预先存在的共享依赖。
- 更新同名共享扩展须显式说明受影响 App，不自动安装、升级或降级；不匹配时保持诊断状态。
- 导入使用同一有效 token 和全权限规则，仍检查目标资源状态、冲突和文件边界；包中原作者/账号只作来源，不恢复来源系统账号或权限配置。
- 取消、磁盘不足、进程中断和并发导入需可诊断、可清理；清理只操作确认无任务使用的精确临时目录。

## 11. 语言模型生成界面

### 11.1 创作期输入与输出

生成上下文默认只包含已选择的命名来源及其公开输入输出契约、组件目录及 Schema、主题/布局规则、当前界面文档、用户提示和经确认的示例数据。不因属于同一应用就发送全部成员数据。模型 provider 可本地或远程，接口在创作服务边界封装；不要求在现场运行节点图中新增模型调用。

默认不发送 Workflow 内部图、生产图片、密钥、完整执行日志或其他 App 数据。远程模型和额外示例数据的使用必须明确；未配置模型时人工编辑与已发布运行页保持可用。

模型输出完整界面文档或对固定草稿版本的修改。生成开始固定草稿版本/指纹；返回时发生人工编辑则报告冲突，不能覆盖新草稿。保留稳定组件身份以便审查差异，不把整页重建当作无差别补丁。

### 11.2 校验和发布

依次校验文档格式、组件存在性/版本、属性类型、公开绑定、JSON 写入冲突、动作类型及明确目标、静态资源、组件数量和布局嵌套边界。未知组件或虚构数据字段直接提示，不能静默替换。Schema 合法不代表业务显示正确，必须提供预览和差异确认。

生成只更新草稿；不自动发布、不运行测试、不修改 Workflow、应用组成或生产入口映射、不更换 Runtime、不启用 Trigger，也不扩大公开输入。生成服务失败或超时不影响生产执行。

主题调整、布局和既有组件组合可通过文档完成。全新交互组件允许开发者用 AI 辅助生成源码，但仍走代码审查、测试、静态构建和组件注册，不在运行浏览器执行未经审核的生成代码。

### 11.3 恢复与复现

包保存最终发布文档、资源、组件版本及必要来源信息。提示词、provider、模型标识等仅作可选来源记录，不代替产物，不保存密钥或无界生成日志。恢复不重新调用模型，不要求来源模型账号或网络可用。

受组件目录约束的 Generative UI 是参考方向，不是已选第三方库。依赖是否采用须验证 Vue 3、离线、绑定边界、文档往返、资源控制和维护成本，不整体引入任意 action、watcher 或计算表达式能力。

## 12. 模块、迁移与实施阶段

### 模块分工

- contracts：amvar app 组成、命名来源、界面文档/版本/入口映射、组件声明、实时结果消息、Workflow 交换容器和应用 manifest 的版本化 Schema；不新增显示缓存或历史对象模型。
- application：应用组成维护、界面草稿/发布/入口应用/逐来源兼容校验、统一结果交付、依赖解析、导出/恢复计划、生成草稿服务；职责拆分但仍属于模块化单体。
- infrastructure：有界在途消息发送、64MB 检查、受控已保存资源 streaming、当前传输资源释放、包 staging、受控扩展资产及配置持久化；不建设显示副本仓库，不把 OS 细节写入领域模型。
- API：REST CRUD/发布/上传下载/恢复计划，支持公开 JSON/文本/Base64 图片的 WebSocket 结果流；内置及第三方前端共用版本化协议、权限和错误，不新增页面业务调用协议。
- frontend：既有 Workflow 四语言显示名称调整、新应用管理、独立运行页、文档渲染、组件 registry、设计器、导入导出/恢复向导及模型生成入口，沿用 Vue 3；旧变量、路由和组件名称不变。
- SDK：恢复后的配置生成及既有调用回归，不创建专属界面调用协议。

这些是职责规划，不要求每项新建一个进程或微服务。正式目录与管理 endpoint 在对应阶段确定，结果流按第 6.5 节实施，复用现有边界优先。

### 前端显示名称调整的实施与核对

1. 依据第 3.1 节列出导航、工作流编辑/列表/详情、新建操作、空状态、确认框及 Runtime/Trigger 关联选择中的系统文案，逐项确认其确实指代既有 Workflow。
2. 在现有四语言消息中更新对应显示值，保留翻译键、插值参数、组件/变量名、路由及参数名；新 amvar app 使用独立文案键。不能全局替换 App、Application 或“应用”。
3. 核对页面仍调用相同服务、按相同 ID 查找资源；历史用户名称、模板、节点、保存文件、发布快照与 SDK 配置无需改写，不补做数据迁移。
4. 更新确实断言旧系统文案的前端测试预期；不得为保持旧显示文本而保留错误用词，也不得顺带重命名测试所使用的技术资源身份。
5. 对四语言导航、打开旧链接、新建/保存/发布工作流、Runtime/Trigger 选择及新应用入口分别验证；阶段尚未实现的新页面明确标记未测。真实副作用验证使用隔离资源，不为文案验收执行生产保存或清理任务。

### 数据迁移

新增 amvar app、组成关联、界面、界面版本、运行入口和导入操作等持久结构时附带 Alembic 和 Repository 实现，验证 SQLite、MySQL/PostgreSQL 兼容性。应用/草稿/入口修订与 Runtime generation 分离，不新增 Runtime 显示配置、结果表或显示历史。默认记录模式和已有 Workflow App/Runtime/Trigger 数据保持原状，不自动创建完整应用、界面或改写历史发布版本。旧 UI 显示名称调整单独验证，不触发数据库迁移或重命名旧代码。

格式版本未知或无法迁移时明确拒绝；需要转换的旧文档通过显式转换生成新内容，保留来源，不在热路径长期维护隐藏双读。现有已发布 App 的公开输入输出、Runtime/Trigger ID 及调用方式不因增加界面强制改变。

本任务阶段测试缓存统一位于 `.tmp/<task-name>`；确认本次进程停止后清理精确目录，不删除其他任务使用的 `.tmp` 内容。长期结论进入稳定专题或可重复测试，不把临时证据目录作为文档交付。

## 14. 实施前需要冻结的细节与文档收敛

已确定的是 amvar app 命名、前端术语边界、组成清单/命名数据源/运行入口映射三个模型，以及核心优先、页面辅助且非硬实时、不建结果队列/缓存/补发、输入按需提交、内联 Base64 与已保存资源两种图片方式、第三方前端共用标准的边界。WS 完整 JSON 消息上限为 64MB（67,108,864 字节），结果路由、消息字段与错误语义、完整公开 mapping、手动 response_mode=run、全部执行出口和统一全权限 token 已在第 6 节固定，不再列为产品待决事项。

可以从第 12 节阶段 0 开始编码与验证，不需要再增加权限设计。尚未形成代码的 Schema、管理路径/新资源 ID、组件技术选型、包路径与导入操作结构，按“各阶段必须交付的可执行契约”逐项实现前固化；在途交接实现、连接/超时/解码资源限制和引用内容身份则必须以原型及测试证明。它们是对应阶段的放行条件，不是已经验证通过的能力，也不是阻止最小链路开工的未决架构。新路由和资源在实际注册前仍不能作为可调用 API 使用。

按对应阶段分别评审，不重新引入单页面单 Runtime、内部参数编辑、页面必填输入补齐、跨 Runtime 页面业务编排、隐式执行、结果缓存或同步等待队列。快照接口/TTL、Runtime 显示开关和页面专用 revision 请求头已从本基线移除。“仅已保存图片”被内联 Base64/受控引用双路径取代；直接暴露临时内存、视频帧流或应用层分包协议不属于本次实现，不为支持 Base64 顺带扩展。加密凭据迁移仍属后续独立范围。其余未定默认值由最小实现与负载验证确定，不能以本文替代代码或工业长期认证。

当阶段实现并通过门禁后，将稳定规则分别合并到 Workflow/前端架构、API、节点扩展、部署运维和前端设计专题；本文件不再重复已稳定契约。全部阶段收敛后删除实施基线或将必要可重复门禁移入专门开发文档，保留 ADR 并更新全部索引。
