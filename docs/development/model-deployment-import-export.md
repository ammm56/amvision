# 模型部署实例导出与导入

状态：单实例导入/导出已实现，完整部署包仍暂缓。本文保留设计边界；当前 API、模块和真实验收结果分别见 [API 说明](../api/model-deployment-transfers.md) 与 [实现和验收](model-deployment-import-export-implementation.md)。

## 1. 目标与范围

开发机完成训练、转换和模型部署后，从部署实例导出一个文件，在另一台视觉软件导入，得到能够使用现有启动、预热、推理和删除功能的模型部署实例。

首版一次处理一个 DeploymentInstance。内部包含该实例使用的 Model、ModelVersion、可选 ModelBuild 和必要 ModelFile，使用者不需要先手工上传模型、登记类别或重新填写部署参数。

Workflow App 使用已有 JSON 导出/导入；Runtime 和 Trigger 根据源机器参数手动创建。本功能不读取或改写 Workflow 图、发布版本、Runtime、Trigger，也不收集流程使用的 Mask、模板图、目录和自定义节点。现有 Workflow JSON 本身不携带这些文件，相关流程仍需按已有方式配置。

首版不做批量组合包、独立模型上传中心、模型自动转换、运行中覆盖升级、在线发送或全链一键启动。完成并验收当前能力后，再决定下一项功能。

## 2. 代码依据与必须保留的语义

| 当前实现 | 对设计的影响 |
| --- | --- |
| [DeploymentInstance](../../backend/service/domain/deployments/deployment_instance.py) 保存模型引用、后端、设备、完整 runtime_configuration 和 metadata | 导出必须包含执行策略、生命周期和 backend_options，不能只复制页面中的名称与实例数 |
| [部署服务](../../backend/service/application/deployments/deployment_instance_service.py) 将 runtime_target_snapshot 固定在内部 metadata，推理从这个快照解析目标 | 以部署实际快照为准，不能用当前模型登记信息重算后悄悄改变输入尺寸、类别或参数 |
| [RuntimeTarget](../../backend/service/application/runtime/targets/runtime_target.py) 包含模型类型、任务、精度、输入契约、labels、model_config、ModelBuild 能力及文件引用 | 传递可移植的结构化内容，目标重建本地路径；不能复制含源机器 URI 的内部 snapshot 原样运行 |
| [Runtime 状态](../../backend/service/domain/deployments/deployment_runtime_state.py) 分别维护 sync、async，默认 stopped | 导入时两个通道均为 stopped；DeploymentInstance 的业务 status 仍为 active，不把两种状态混成一个字段 |
| [模型登记](../../backend/service/domain/models/model_records.py) 新增 deployment-import 来源，与 pretrained-reference、training-output 并列 | 导入来源独立，源任务 ID 仅作追溯信息，不是目标外键 |
| [现有资源删除](resource-deletion-implementation.md) 已管理文件、记录、占用和恢复 | 导入文件必须有独立归属，并在这一阶段补齐删除闭环 |

当前 create_deployment_instance 由服务生成新 ID，并自行提交事务；原样调用不能实现保留源 ID 和模型/部署原子登记。导入服务组合现有配置校验与 Repository 登记，使用一个 UoW，保持现有公开创建接口的行为。

## 3. 页面交互

浏览器已核对现有部署页：顶部有运行模式、刷新，实例卡片有启动、预热、重置、停止、删除、状态信息。首版只在这里增加两个入口。

### 导出

- 每个实例操作区增加“导出”，可访问提示为“导出部署实例”。运行中的实例允许导出，导出不改变运行状态。
- 点击后显示文件收集/打包进度，成功后点击“下载”取得 `<名称>.amvision-deployment.zip`。单个实例无需再打开依赖选择向导。
- 缺文件或配置不一致时显示具体文件/字段和原因，导出失败，不生成看似完整的文件。

### 导入

- 部署页顶部、刷新前增加“导入部署实例”。通过系统文件选择器选择单个包，上传分析后打开现有样式的配置对话框。
- 显示目标项目（默认当前项目）、实例名称、模型/任务、后端、精度、输入尺寸和文件大小。允许修改名称、设备与实例数；其他运行配置折叠到“高级设置”，沿用现有类型和校验。
- 后端与精度由所带产物决定，不能在表单中任意更换。设备改变导致 backend_options 类型不一致时明确要求调整，不能保留 CPU 参数却显示 GPU 配置。
- 无问题时点击“导入”；完成后点击“完成”关闭对话框，列表显示实例和导入初始停止状态。随后使用现有启动、预热、推理功能。
- 冲突、文件损坏或不兼容就地显示，不用多层确认框。导入失败不影响已有部署。

复用当前按钮、表单、对话框和主题变量，保留键盘操作和焦点返回。长文件任务显示阶段和真实进度，重复点击不得重复登记；刷新后可查询当前操作，不另建一套传递资源管理页面。

## 4. 最小文件内容

格式为 `amvision.model-deployment.v1`，ZIP 中仅包含 `manifest.json` 与 `files/`。这一格式只描述一个部署及固定模型关系，不设计任意资源图或通用依赖插件框架。

清单由 Pydantic 2 模型序列化，分为包信息、部署配置、模型信息、版本信息、可选 Build、推理配置、文件列表。文件项记录包内相对路径、逻辑名称、用途、所属资源、字节数和 SHA-256；文件内容直接保存，不用 base64 JSON。

| 内容 | 收集规则 |
| --- | --- |
| 部署配置 | 原 ID、名称、模型引用、后端、设备、runtime_configuration；剔除运行状态和统计摘要 |
| 固定推理配置 | 以实际 snapshot 中的任务、模型类型/scale、精度、model_input_spec、labels、model_config、model_build_metadata 为准；保留明确的宽高语义 |
| PyTorch 部署 | 选中的运行权重、标签及该适配器确实需要的配置文件，不带训练目录 |
| 转换后部署 | 实际 Build 文件集；OpenVINO XML/BIN、ONNX 外部数据按相对关系成套保存；TensorRT 保存所选 engine 和已有能力信息 |
| snapshot 引用的 checkpoint / labels | 首版一并包含，即使当前 Build 推理主要使用转换文件，也不能保留指向缺失文件的 URI；当前反序列化会检查这些路径 |
| Model / ModelVersion / ModelBuild | 仅登记所需对象及运行必要 metadata；源训练、转换、数据集和父版本信息作为来源摘要，不递归导出历史 |

不包含任务记录、训练日志、数据集、其他模型版本、无关转换文件、预热缓存、PID、lease、共享内存、sync/async 心跳状态、源项目权限或服务配置。

模型类型和任务支持范围按当前 resolver/predictor 注册核对，不能根据文件扩展名猜测。初始文件适配按已实现模型族和后端逐类实现，先冻结 OpenVINO CPU 的完整样例，再扩展其他已有后端。未知依赖类型明确拒绝，不通过复制整棵源目录补漏。

当前代码中的 runtime_profile_id 用于传递、展示及与 ModelBuild 的一致性检查，未发现独立 RuntimeProfile 仓库读取。本版将其作为可空标识保留，Deployment、Build 和 snapshot 保持一致；不新增 Profile 记录或迁移子系统。执行参数仍来自 runtime_configuration 和固定推理配置。若后续适配器增加外部 Profile 解析，须显式扩展格式和校验。

## 5. 模型和 Workflow 引用

目标为空且 ID 未占用时，优先保留 Deployment、Model、ModelVersion、ModelBuild 的源 ID，源 Project 映射到目标所选项目。这样现有 Workflow JSON 引用相同 ID 时可以继续解析，无需新增工作流改写功能。

- 同来源、同文件摘要、同配置且属于同一目标项目的模型依赖可以复用；两个部署共用模型时不重复复制同一版本文件。
- 同一导入提交使用幂等键。重复提交返回既有结果，不能再创建一个实例或重启它。
- 重新导入同包，先核对上次结果是否仍存在且一致；一致则提示已存在。目标配置已改变时不能凭旧回执认定一致。
- 同 ID 但内容或项目不同，阻止覆盖，提供“创建副本”。为冲突对象分配新 ID，只重写这个部署包内部的固定模型引用。
- 发生 ID 变化，结果列出新旧部署/版本/Build ID，提示在 Workflow 编辑器重新选择对应资源。同名且类型一致的 Model 聚合可复用；具体版本、Build 和文件仍单独核对，不能仅凭名称复用。

需要区别两种 Workflow 节点使用方式：引用 Deployment 的节点使用部署 ID；直接引用 ModelVersion/ModelBuild 的模型加载节点使用模型 ID。只保留部署 ID 不能覆盖后一种情况。即使 ID 相同，也必须通过目标图的现有保存、发布和预览校验。

完整手动使用顺序：导入部署并测试推理 → 导入 Workflow JSON → 核对模型/部署及其他外部引用 → 保存、发布 → 创建 Runtime → 创建 Trigger → 发起真实调用。不能承诺仅导入这两个文件就自动迁移任意工作流的全部外部依赖。

## 6. 实现边界与失败处理

后端在 `application/deployments/` 下新增导出、导入、文件清单等独立模块，契约和存储实现分别放在现有对应层。复用队列/Worker、ObjectStore、Repository/UoW 和部署运行服务，不新增跨 Workflow 的统一迁移子系统。

API 已提供创建导出、下载、上传分析、提交、查询、取消、删除预览和导入模型管理，固定路径和错误结构见 [API 说明](../api/model-deployment-transfers.md)。大文件处理放在 worker，上传/打包流式执行；浏览器不负责把模型读成完整内存 Blob 再拼 ZIP。

导入分成三个可独立验证的步骤：

1. 暂存并检查：格式、文件摘要、文件配套关系、支持的模型/后端、目标项目权限、设备及 ID 冲突。此时不创建业务模型或实例，不加载权重执行代码。
2. 登记：把文件放入目标按模型版本/Build 归属的受管目录，用目标 ID/URI 构造运行快照，一个 UoW 提交模型、文件、实例和两条 stopped 运行状态。
3. 完成：清理上传/解包副本，返回实例详情。启动和预热由现有功能独立执行，导入成功不等于运行测试通过。

数据库与磁盘不能假定天然原子：记录仅覆盖本次导入的 prepared/committed 清单，提交前失败清理本次新文件；提交后中断由恢复任务完成收尾。复用模型文件不得进入本次回滚删除清单。状态恢复做到这一条模型链路即可，不先抽象跨系统恢复框架。

源导出期间持有与删除服务兼容的占用，读取固定 snapshot 并校验文件未变化；无需停止部署。目标登记再次检查冲突及删除占用。拒绝 ZIP 越界路径、重名路径、链接和超出配置的解压量；取消、磁盘满、进程退出和清理重试必须可恢复。

导入 ModelVersion 来源为 `deployment-import`，目标训练任务/数据集/转换任务关系为空，保留源信息供追溯。数据库枚举/约束与操作记录变化附 Alembic 迁移，兼容 SQLite、MySQL、PostgreSQL；source_kind 的 API、前端显示和使用分支同步处理。

删除生命周期随导入一起完成：删除 Deployment 时，自动清理与本次删除关联且已无其他引用的导入产物；本地训练/转换产物保持原归属。共享导入产物保留并说明原因。模型页仍提供未使用导入产物的独立删除入口，避免在其他引用解除后无处清理。详细规则见第 10 节。

兼容性只覆盖目标已安装且本项目已接通的运行后端，不自动换后端或转换。TensorRT 核对已有构建信息及目标运行环境；无法静态确认的项目明确标为待启动验证，不把文件校验成功当作 GPU 兼容结论。需要重新转换时使用现有转换流程另行完成。[NVIDIA Engine Compatibility](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html)

## 7. 逐步规划、实现和验收

下表保留实现和扩展的依赖顺序。当前已完成的组合、测试与尚未实测的模型范围以 [验收记录](model-deployment-import-export-implementation.md) 为准；后续新增模型组合仍逐项验收。

| 阶段 | 本步范围 | 必须通过后才能继续 |
| --- | --- | --- |
| 1：冻结最小契约 | 单个 OpenVINO CPU 部署，逐项核对 snapshot、XML/BIN、checkpoint、labels、Profile、ID 和来源映射；设计导入来源及文件归属 | 真实只读样例形成清单；每个运行字段和文件有明确去向；包 schema 和错误结构确定，无未解释源路径 |
| 2：只做导出 | 实例导出服务、流式 ZIP、完整性校验、下载、导出占用和清理 | 可解包并校验全部文件；导出不改变源实例；缺文件与并发删除正确失败；暂不导入业务库 |
| 3：只做后端导入闭环 | 隔离目标项目登记模型/Build/文件/部署，两个模式 stopped，使用现有启动和推理 | 源服务不可访问时仍能加载、预热、推理；类别、输入、输出契约和结果按后端容差核对；源库不变 |
| 4：清理与故障 | ID 保留/冲突/副本、幂等、共享模型、断连、磁盘满、提交前后故障、重启恢复、模型删除 | 不覆盖已有资源；不残留半个部署；无复用文件误删；删除与暂存清理后文件和记录符合归属 |
| 5：页面接入 | 部署页两个入口，简洁表单、进度、结果与冲突提示 | 浏览器完整操作成功；亮暗主题、键盘、窄屏正常；失败可理解、可重试 |
| 6：扩大已验证范围 | 逐个补 PyTorch/ONNX/TensorRT 和现有模型任务适配，真实 CPU/NVIDIA 发行包，配合已有 Workflow JSON 手动创建 Runtime/Trigger | 每个新增组合单独通过；端到端调用与目标重启成功；不以一个 classification 样例代表全部任务通过 |

参数验证包括非正方形输入/明确宽高、类别顺序；进入相应任务或后端阶段时，还需覆盖 pose kpt_shape、动态输入及 TensorRT profile 等容易丢失的内容。核心测试放根目录 `tests/test_*.py`，前端按现有 `tests/frontend/` 组织。

实际发行验收使用隔离项目、数据根和端口，从源码 assemble-release 生成发布包，验证目标不依赖开发机路径、源码 conda 或源服务。最后再验证导入 Workflow JSON、手动创建 Runtime/Trigger 的使用流程，作为现有能力的组合验收，不借机扩展它们的导入导出功能。

## 9. 磁盘位置与训练、转换的关系

所有路径相对于实际配置的 ObjectStore 根目录 `LocalDatasetStorage.root_dir`。源码默认根为 `data/files`，发行版使用发行服务自己的配置；不得把开发机绝对路径写进包或目标配置。下表中已有路径是当前默认组织，导入路径是本次新增设计。

| 文件归属 | 相对路径 | 生命周期 |
| --- | --- | --- |
| 已有训练产物 | `task-runs/training/<task_id>/...` | 训练任务及其登记产物管理 |
| 已有转换产物 | `task-runs/conversion/<task_id>/...` | 转换任务及其登记产物管理 |
| 新增导入版本文件 | `projects/<project_id>/models/imported/versions/<model_version_id>/files/...` | 导入模型版本管理 |
| 新增导入 Build 文件 | `projects/<project_id>/models/imported/builds/<model_build_id>/files/...` | 导入模型 Build 管理 |
| 已有部署事件等文件 | `deployments/instances/<deployment_instance_id>/...` | 部署实例管理，模型文件不放这里 |
| 新增上传/解包/导出暂存 | `projects/<project_id>/model-deployment-transfers/<operation_id>/...` | 操作期间保留，终态/到期清理，不是模型永久目录 |

文件层级保留 OpenVINO 配套文件和 ONNX 外部数据的相对位置；逻辑文件名通过校验，目录 ID 由后端规范化，不允许包决定任意磁盘路径。模型重命名不改目录；整个软件目录移动后，由新的存储根解析相对 URI。

导入后的模型继续使用 Model → ModelVersion → ModelBuild → ModelFile 这套现有登记关系。导入版本的 training_task_id、dataset_version_id、parent_version_id，以及导入 Build 的 conversion_task_id 不伪造目标记录；源 ID 只放在类型明确的来源摘要。Build 的 source_model_version_id 则必须指向真实目标版本。

新增受控的 `ImportedModelArtifact` 归属记录，分别指向一个版本或一个 Build，保存所属项目、存储前缀、文件集摘要及来源。一个记录只能归属其中一种资源，使用唯一约束防止重复登记。ModelVersion 的 source_kind 增加 deployment-import；Build 是否为导入产物以自己的归属记录为准，不能从其来源版本推断。归属信息由服务写入，不能通过通用 metadata 更新接口更改。

这样可以明确区分：

- 导入版本上重新做本地转换：新 Build 由本地 conversion task 管理，文件进入现有转换目录；不能按导入 Build 自动清理。
- 本地训练/转换模型不会仅凭同 ID 或同名自动变为可复用的导入版本/Build；导入资产与本地资产明确分开，兼容的 Model 聚合可共用。
- 两个部署使用同一个导入版本/Build：共用同一登记和目录，按实际依赖判断是否仍被使用；不维护另一套手工累加的引用计数。
- 已导入模型可在模型页查看、被现有模型选择器选择。具备所需权重且当前功能支持时可用于后续转换；只带转换文件的包不凭空获得缺失权重。本功能不新增继续训练适配，也不制造训练任务来满足页面显示。

不把预训练资产政策变成通用上传入口：本功能仅接收合法部署实例包。源是预置模型时，目标新复制的文件仍属于项目内导入产物；目标已有平台预置版本不会自动转为导入版本，且永不纳入导入清理候选。

暂存保留默认值：未完成上传且已无活动连接、放弃的分析结果保留至 24 小时；完成的导出文件保留 24 小时；终态操作回执保留 7 天，均可配置。已进入 prepared/committed 的未完成恢复操作不按 TTL 删除，先恢复再清理；活动 worker 和下载占用未释放时不得按到期时间删文件。浏览器已下载到用户目录的 ZIP 属于用户文件，不由后端清理。

## 10. 删除时到底删除什么

原则：先区分“删除实例的阻止条件”和“模型是否可以顺带回收”。两者不能共用一个遇到共享模型就全部报错的判断。

| 情况 | 删除实例 | 模型文件和模型记录 |
| --- | --- | --- |
| 任一 sync/async 通道未停止，或实例仍被工作流直接引用 | 阻止，列出现有依赖/状态 | 不变 |
| 本地创建的实例引用训练/转换产物 | 删除实例及运行状态、实例专属文件 | 保留，沿用原任务的删除规则 |
| 导入时新增的版本/Build，仅被当前实例使用 | 删除实例 | 一并删除无其他引用的导入 Build、版本、ModelFile 和归属记录；空 Model 聚合也清理 |
| 另一个部署仍使用同一导入模型 | 删除当前实例 | 保留共享部分，不阻止仅删除实例 |
| Workflow 直接引用导入 ModelVersion/Build，但没有引用这个实例 | 删除当前实例 | 保留被工作流使用的部分，不能删除历史发布仍依赖的文件 |
| 导入版本已有本地转换 Build 或被任务作为输入使用 | 删除当前实例 | 保留仍被引用的版本；无引用的导入 Build 可以单独回收 |
| 导入实例复用了目标已有本地或平台模型 | 删除实例 | 不自动删除已有模型 |
| 后来手动创建的实例使用导入模型，且是最后一个引用 | 删除实例 | 同样清理已经无引用的导入产物；规则依据资产归属，不依据创建按钮来源 |

计算顺序为：先检查实例能否删除；再收集其关联的导入 Build/版本；将仍被其他资源引用的候选保留；按 Build → 版本 → 空 Model 计算可清理集合。待删除集合内部的引用不应误判为外部依赖，保留 Build 对版本的引用必须继续生效。文件仅按归属记录和 ModelFile 清单删除，不递归删除共享模型父目录。

现有 ResourceDeletionPlan 对选中集合的外部引用采用阻止策略。新增“可选回收的导入模型”时，应先从集合中移除有外部引用的候选，再调用严格删除检查，不能把共享导入模型直接加入后导致整个实例删除失败。工作流草稿、发布快照、Runtime、其他部署、Build、任务输入和下载/导出占用都要纳入检查；读取依赖失败时不能按零引用清理。

`_check_workflow_references` 在导入产物回收和实例删除路径中使用严格检查。当前项目必要快照缺失时阻止实例删除；可选模型回收不能确认引用完整性时保留模型。不能把缺失文件当作零依赖，也不让其他项目无关的缺失快照阻止当前项目删除。

沿用现有一次删除确认对话框，通过后端删除预览给出准确内容：

- 本地模型：“删除部署实例。训练和转换模型将保留。”
- 独占导入模型：“同时删除不再使用的导入模型文件（大小）。”
- 共享模型：“删除部署实例，保留仍被使用的模型。”可展开使用者名称。

不增加“是否删除模型”的常驻复选框，避免由操作者猜测文件归属。确认后重新检查引用；影响范围改变则返回更新后的预览，不按过时范围删除。普通预览只读，不提前移动文件。

清理失败时复用 ResourceCleanupPanel 显示“记录已删除，文件清理待重试”，不能只提示全部删除成功。保留的导入模型在模型页标注“导入”；解除最后依赖后，可从模型页删除未使用产物。首版不做全库周期性孤儿模型扫描，只回收本次删除关联对象及显式选择的未使用导入模型。

## 11. 页面位置与完整操作状态

### 11.1 部署页

顶部操作顺序：运行模式 → 导入部署实例 → 刷新。实例操作顺序：启动 → 预热 → 重置 → 停止 → 导出 → 删除 → 状态信息。窄屏自然换行，不压缩为无名称图标；导出使用次要按钮，不与启动争夺主操作样式。

实例增加低强调的来源标识“导入”或“本地创建”，表示实例的创建方式。模型页的“导入模型”区分别列出版本和 Build 的实际归属；实例标签仅表示创建方式，删除范围以服务端预览为准。

导出状态保留在对应实例的操作行：导出按钮使用已有 loading 动效，处理中禁止重复点击，失败就地显示原因并允许重试；完成后下载按钮紧接导出按钮。页面顶部不显示传递记录。刷新后回读每个实例的最新导出状态，切换项目不混入上一项目进度。后台按实例合并导出请求，内容未变复用同一 ZIP，变化或缓存无效时原位更新，完整规则见 API 说明。

### 11.2 导入对话框

标题“导入部署实例”，最大宽度 640px、宽度不超过视口减 32px，最大高度为视口减 48px。复用已有遮罩、过渡、背景、边框、按钮和输入样式，不修改其他对话框全局尺寸。标题和底部操作固定，内容单独滚动；已通过真实发行页面浏览器核对，长名称和配置内容可正常显示。

| 从上到下的位置 | 内容与操作 |
| --- | --- |
| 文件选择与上传 | 顶部入口使用系统文件选择器；上传时显示文件名、总大小和取消。只接受一个实例包 |
| 模型摘要 | 模型名称、任务、后端/精度、输入尺寸、类别数；只读，不显示整份 JSON |
| 基本设置 | 使用部署页当前项目；实例名称、目标设备、实例数。在现有项目入口选择项目，不重复增加项目选择步骤 |
| 高级设置 | 展开后编辑当前后端已有配置和生命周期参数；保留导出值，不按目标默认值静默重置 |
| 仅在有问题时显示 | 缺依赖、设备冲突、模型/实例 ID 冲突及“创建副本”；影响 Workflow 引用的 ID 变化可复制查看 |
| 底部 | 关闭 / 导入；配置修改后为“检查配置”，完成后为“完成”。分析未完成、有阻止项或提交中时禁用导入 |

正常状态顺序：选择 → 上传 → 校验 → 可导入 → 正在导入 → 完成。已知不支持的后端、损坏文件或无法满足的配置阻止提交；仅运行时可知的显存和模型加载结果留给启动验证。设备原值可用时保留；不存在时要求从目标设备列表选择，不自动把 CUDA 换成 CPU。

上传阶段“取消”中止浏览器请求；若服务端已受理，以回读记录为准，可在导入对话框中取消。未提交不会创建实例，未使用暂存按到期规则清理；分析阶段取消请求任务停止。已开始提交时不承诺取消事务，关闭表示后台继续，页面可查看结果。只有服务器确认未提交/已回滚才显示取消成功。上传断开可重新上传，首版不实现分片断点续传；网络超时先查操作结果再决定重试，避免重复导入。

成功后自动关闭导入对话框并刷新实例列表，导入实例直接显示在列表中，不自动启动，也不在页面顶部显示结果记录。创建副本导致 ID 变化时，提交前在对话框的资源映射中核对；完成后的 ID 和映射保留在短期操作 API 回执，实例继续使用其实际 ID。未完成的导入从顶部“导入部署实例”入口继续处理。

### 11.3 模型页与已有选择器

不新建“导入模型”导航页。模型页增加“导入模型”区，列出版本/Build、文件总大小和必要来源摘要；不会出现虚假的“训练完成”“转换任务详情”。已有模型选择器能列出可用导入版本和 Build，无法用于某种操作时给出具体原因。未使用导入产物的删除继续使用现有资源删除反馈组件。

默认导出必须带齐 snapshot 中现有 checkpoint/labels 及实际运行文件；这可能让转换后部署文件比单个 engine 大。首版接受这个可预测行为，界面显示真实总大小；减少权重体积留到另行验证 resolver/predictor 不再需要该文件后再做，不在导出时静默省略。

## 12. 当前设计核对结论

本次已明确实例与模型的双重来源、磁盘目录、共享与独占删除、模型页入口、基本/高级表单、取消与重试、ID 冲突和手动 Workflow 衔接。当前实现及已通过组合见 [实现与验收记录](model-deployment-import-export-implementation.md)。

新增模型组合仍必须逐项验证：不同模型族的配套文件清单，源固定 snapshot 与可复用目标模型的语义一致性，旧删除清单对新增可选回收集合的处理，以及不同后端真实加载结果。它们是明确的实现门禁，不能写成已经“全部没有问题”。未经一致性验证的模型不复用；来源记录与固定 snapshot 不匹配时定位差异并拒绝导出，先修复来源，不默默选择其中一份。
