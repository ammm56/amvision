## 持续运行与发行门禁

### P0：验收职责与判定设计

验收工具继续放在 `tests/integration/`，不进入 API 或推理热路径。复用当前证据、资源与环境模块，发行测试只负责装配与协调。

- 统一记录 `prepare → warmup → measure → fault/recovery → drain → cleanup` 阶段、开始结束时间、模型/运行时身份和实际请求数。故障恢复使用单独子窗口；稳定资源趋势只消费 `measure` 内的数据。
- 资源门禁要求稳定负载阶段至少两个不重叠的完整窗口，同时满足预先声明的最短测量时长、采样覆盖率和最大连续缺口。子进程退出造成的丢弃样本可观测；不能仅凭早期 10 个有效样本就接受后续长时间缺样。
- 分别记录内存、句柄、线程的峰值和增长；根据目标配置增加 GPU 显存、数据库/WAL、日志和输出文件增长。GPU 采样不可用时报告 `unavailable`，不能记作 0；要求 GPU 资源认证的 profile 在此情况下不能整体通过。
- 报告分开表达 `functional`、`performance`、`resource`、`recovery`、`cleanup`、`coverage`。总体结果按必选项计算：有失败则失败，必选项未执行/数据不足则未完成，只有全部必选项通过才整体通过。新报告显式版本化，保留旧报告原文和读取兼容。
- 增加 `short`、`performance`、`soak` 验收配置；没有明确选中的门禁不被暗中视为通过。短功能检查可保留低样本，但不得再给出性能认证结论。
- 负载清理按本轮创建的资源 ID 回收。Trigger 仅 disable 仍会保留端点登记，后续应通过现有删除接口清理本轮测试记录，或使用独立数据库；不能只靠换端口使重复验收成功。
- 任何清理步骤失败都继续尝试其余步骤，保留原始失败和清理错误；按 PID、创建时间及发行目录核对进程归属，禁止回收其他服务。

### P1：性能测量设计

当前 32.44 ms 对 23.09 ms 的差异是共享内存与 ZeroMQ 的对照，并非源码修改前后的回归结果。先使用原冻结模型和图诊断，不推断根因，也不改变既有共享内存协议、容量或 ACK 语义。

1. 复现原来的 162-byte 工程输入，再覆盖 1080p、4K、20MP；区分 encoded 与 raw BGR24，核对两端实际像素一致。增加无模型传输图与现有工程模型图，分开观察传输及推理耗时。
2. 使用已有 `enable_timings` 和 SDK probe，核对写入/发布、接收/准入、Workflow invoke、推理、结果序列化、读取与 ACK 的分段耗时。只在诊断轮启用详细计时，最终性能门禁另跑无详细计时轮，避免埋点影响结论。
3. 初始诊断配置采用至少 20 次预热、5 轮、每轮每条路径 1000 次，交替执行 A/B 顺序。并发从 1 开始，再按实际部署容量覆盖 2、4；每个组合单独报告样本数和 P50/P95/P99。

## 进程归属核对与更正（2026-10-14）

项目原本就是跨平台系统，已有 `ProcessTreeSupervisor` 的 Windows Job 与 POSIX process group 实现。本次缺陷不是原架构整体不可用，而是 full launcher、开发 Worker Supervisor、spawn 运行时和服务接管的生命周期入口未统一。正常退出能工作，不能证明异常退出也没有残留。

固定三层真实进程时序的对照复现显示：中间进程先退出、孙进程继续持有文件时，HEAD 的 taskkill 路径和上一节未提交的暂停后快照路径均返回成功，但孙进程仍存活；既有 Job 路径完整回收。证据为 `data/acceptance/process-ownership-20261014/baseline.json`。因此，上一节快照停止方案的局部通过结论不能作为完整进程回收保证，该方案已删除。历史性能、600 秒资源结果原样保留，不能抵消这一异常退出缺陷。

本次在既有 `backend/runtime/processes/` 内统一命令和 spawn 生命周期，Windows 复用 Job 原语，POSIX 使用组身份守护与控制管道；业务、启动器与恢复接口不依赖具体平台。启动登记在 target 放行之前完成；停止封闭新登记、按显式归属结束嵌套组、确认清空后才释放资源和恢复。查询失败、身份不明或组残留时保留归属并拒绝恢复，不再按父子快照、taskkill 或 PID-only 状态降级。详细分层及升级规则见 [进程归属与恢复准入](../architecture/platform/process-ownership.md)。

## 尾延迟与线程窗口复核（2026-10-15）

### 已验证的修复

- 同解释器的受管角色 launcher 完成配置后直接在已登记的组根 PID 执行业务入口，消除上一轮仍存在的八个等待型角色解释器。当前 PID、内核出生标识、归属链、停止标记和 OS 组成员均须核对成功；普通继承环境变量的子进程不能冒充组根。不同解释器或独立入口继续由同一个 ManagedProcess 边界管理，不创建第二套控制机制。Ubuntu 的进程组身份守护不是这种空等待包装，不按 Windows 的优化方式删除。
- 通用 mailbox 空扫描改为快速筛选状态候选，取得锁后仍校验完整状态、epoch、generation、deadline 和 CRC。128 槽空扫描的独立微测从约 44.4 us 降至 0.67 us；微测不代表整链路 P99。
- PREPARE 的 Broker 分配复用已有有界执行器，避免唯一 poller 被同步分配阻塞。容量不足仍立即拒绝；没有新增任务池或等待队列。取消、失败、停止均等已有操作结束后回收 receipt，不提前释放正在使用的输入。
- poller 对繁忙描述符只做一次非阻塞锁尝试，继续处理其他槽；下次轮询重试，不在该描述符内累计短等待。PREPARE/ACK 交换使用短阻塞观察间隔，模型执行阶段保持既有间隔，不采用忙轮询。
- mapping 生命周期内最多缓存八个独立空闲 guard 句柄。活动租借不共享 Linux OFD 锁句柄；每次仍检查文件身份和精确长度，锁定或解锁 I/O 失败的句柄立即关闭。四线程、每请求十次 guard 的实际池实现对照中，平均值约 1.74–1.77 ms 降至 1.31 ms，P99 约 2.53–2.61 ms 降至 1.94–1.99 ms。
- 无取消时复用已有 request context 快速检查，不反复加锁读取零取消原因；真实取消、过期或 identity 失效仍走严格检查。SDK 等待计时器按实际等待惰性创建，移除进程级 `timeBeginPeriod` 租约，不改变主机时钟和电源设置。

第一阶段 Windows 组合回归为 **548 passed、2 skipped**，包括真实进程归属、孙进程回收、恢复准入、IPC、控制面和 SDK 合约。Ubuntu WSL 对应进程与 mmap 回归为 **89 passed、4 skipped**。跳过项按平台能力区分，不能算成跨平台通过。前端 HTTP **7 passed**，Vue 类型检查及变更差异空白检查通过；本轮没有更改页面。

### 模型尾延迟的独立证据

在同一个实际 full-core TensorRT session 内，固定 engine、输入、数值精度和前后处理，只改变请求间隔，重现了 GPU1 空闲降频影响。连续调用平均约 7.42 ms、P99 9.48 ms；增加 18 ms 间隔后平均约 22.10 ms、P99 30.06 ms，SM 时钟降至 210–255 MHz。恢复连续调用后平均约 7.30 ms、P99 8.55 ms。去掉 CUDA event 计时但保留真实 stream 同步未消除现象，不能把 event 计时认定为根因。切换顺序存在时钟滞后，不能把每一历史异常都归因于降频。

临时 CUDA Graph 对照使用同一 session、同一 buffers；五个随机输入的 prediction/proto 原始数组逐位一致。连续调用平均从约 7.37 ms 降至 5.19 ms，但 18 ms 请求间隔下 Graph 的 P99 仍为约 24.63–25.91 ms。因此没有向生产代码加入不能解决本次尾延迟的 Graph 分支。完整数据为 `model-cadence-probe.json` 与 `model-graph-probe.json`。

用户明确批准了现有 keep-warm 的独立配置对照。临时导入实例仅设置 `keep_warm_enabled=true`、间隔 0.01 秒；实际健康状态确认 activated，成功计数递增且错误为零。三轮、1,800 次模型调用零错误，相对 P99 三轮均通过：ZeroMQ/shared 分别为 37.77/41.12、44.33/34.73、37.03/40.93 ms。后续 60.219 秒混合调用完成 366 次、零错误，故障恢复和停止清理通过。

这不是原配置正式通过结论：该对照开启 diagnostics，并附加只读观测；保温增加空闲 GPU 负载，真实请求也可能等待已提交的 dummy infer。现有指标没有把这段等待单独计时，不能用整个 gateway 与模型 latency 的差值冒充精确保温等待。观测包含停止后的空闲样本，报告整段 GPU 平均值时必须说明范围。正式配置仍保留 keep-warm 关闭，不改变 GPU 时钟、电源、驱动模式或验收门禁。

### 线程增长的证据边界

`thread-window-attribution.json` 按原失败资源样本、同一首五样本中位数和最大完整五样本窗口重算：137 到 172，增长确为 35。六类 worker 各增长 4，合计 24；backend 增长 6、daemon 增长 3、full supervisor 增长 2。该角色归因可精确复算，但原始报告没有逐线程启动地址，不能把全部 35 个线程绑定到某个原生函数。

独立空闲解释器实验和原生符号解析确认 Windows 线程池及 COM RPC 线程会在没有应用任务时出现和退出；`ntdll+0x1a2e0` 对应 TppWorkerThread，`combase+0x115670` 对应 CRpcThreadCache::RpcWorkerThreadEntry。这解释了保留额外解释器会放大原生常驻开销，但不是直接证明历史 35 个增长全部来自这些符号。本轮通过复用既有组根减少解释器，不终止单条 OS 线程，不把原生线程排除在门禁外，最终资源结论以原上限 32 的完整测量为准。

### 正式复验暴露的控制队列竞态

`guard-frozen-performance` 使用原配置完成 20,000 次模型及小图调用，零调用错误；小图五轮全部通过，模型两轮相对 P99 失败，其中一轮也触发 P99-P95 门禁。但随后 mixed-load 的 `async/start` 返回 503：读取控制响应队列 leased 文件失败，尚未进入 120 秒稳定负载。因此该轮功能失败、资源覆盖不足，不能记为资源验收通过。

真实句柄定向测试固定了发布时序：Windows 原子 rename 已完成，发布端的 DELETE 句柄尚未关闭；消费者可把文件移动到 leased，但普通 `read_text` 未共享删除权限，会立即抛出 PermissionError。领取和直接查询两条回归修复前均失败，错误路径与真实轮一致。真实历史响应未保留底层 errno，不能把定向复现替代为历史调用栈；该读写模式不匹配则可在 HEAD 中直接核对。

队列统一复用已有 `open_shared_read`，保持原 UTF-8、JSON 解码和异常语义，不添加读取重试、sleep、业务队列或备用协议。定向队列、原子文件和 inference 控制回归 **59 passed**；随后增加缺失及损坏文件不被吞掉的回归。最终重新组装与冻结使用 `queue-frozen-*`，不覆盖 `guard-frozen-performance` 的失败证据。

### WSL 归属身份复核

后续 WSL 组合回归出现一次 POSIX 守护身份误拒绝，结果为 114 passed、1 failed、6 skipped，保留于 `ubuntu-queue-final.xml`。该次没有记录两端创建时间，不能直接判定它与后续受控复现具有完全相同的触发时序。200 次独立启动没有再现启动失败，但观察到 `/proc/stat` 的 btime 从 1791902086 变为 1791902088。Linux psutil 的公开 create_time 以 starttime 加当前 boot_time 换算，跨进程的墙钟结果不适合作为持久归属标识。

在不修改系统时钟的情况下，仅将父端 create_time 读数增加两秒，固定复现三项失败：启动门拒绝、活组恢复检查误判、当前 owner 被建立为另一个 scope。修复统一放在现有进程适配层：Linux 使用 boot ID 与内核 starttime 计数，组根、守护及 scope owner 共用同一读取函数。保留 PID、PGID、停止封闭与完整成员检查；错误出生标识仍严格拒绝，不增加重试或容差。内部 group/scope 记录升级为 v2，旧运行必须先停止，不保留 v1 降级。

身份修复后的 Windows 组合回归 **582 passed、7 skipped**，WSL **126 passed、6 skipped**。包含真实中间进程退出、孙进程回收、重开归属、owner 崩溃、登记失败及墙钟变化测试。前端 HTTP **7 passed**、Vue 类型检查、变更 Ruff F/E9 与 git diff --check 通过。WSL 结果仅覆盖进程、mmap 和本地队列，不代表完整 GPU 发行认证。正式发行包经 assemble-release 重组，再冻结，不手工修改发行副本。

### Broker 周期扫描修复

进一步核对发现，arena 状态查询和有占用时的周期回收会同步构造整表 descriptor 快照。生产测试几何为 2 GiB arena、1 MiB 最小块，共 2,048 项。独立原实现测量中，空表状态查询平均 4.526 ms，一个 active 项时状态查询平均 4.528 ms、P99 5.173 ms，周期扫描平均 4.463 ms、P99 5.431 ms。该成本发生在 Broker 控制线程，不能用异步任务名掩盖。

## 后台生命周期与跨平台身份复核

2026-10-15 后续实施沿用既有进程适配器、Outbox、Reconciler 和服务 bootstrap，没有增加调度器、业务等待队列、第二套组回收或兼容状态。证据目录为 `data/acceptance/runtime-lifecycle-20261015/`。

确认并修复的边界如下：

- Outbox 与 Reconciler 在停止 join 超时后曾清空线程引用，允许旧线程仍在访问依赖时恢复。现在超时向上传递，保留引用和依赖，显式完成 stop 后才能恢复；Outbox 已领取批次继续按原规则完成。
- API 停止忽略 Trigger 超时并继续释放 Workflow、Broker、数据库；daemon 停止也可能在生产者失败后继续关闭消费者。现在资源容器封闭恢复准入，失败可重试，依赖只在使用者退出后关闭。
- backend 根据属性名拼接枚举组件，漏掉 classification、segmentation、pose、obb 的八个 sync/async supervisor。改为十五个实际成员的明确枚举。
- Deployment supervisor 监控线程停止超时曾继续释放设备 reservation。现在保留线程、进程和设备归属，停止期间拒绝模型拉起。
- Inference Mailbox 曾在 dispatcher 未退出时清空引用，状态发布线程超时未向上传递。Mailbox 现在先发布关闭标记取消客户端，再确认 dispatcher 和在途 handler 退出，最后释放 mapping、executor 和 owner。状态线程同样须确认退出。
- daemon 启动回滚原先简单倒序处理启动列表；最早 prepare 的 Mailbox owner 会排在最后，尽管其 dispatcher 已经开始接入。回滚现在复用正常停止的依赖顺序，不重复实现关闭流程。

定向失败和修复证据分别保留为 `threads-red.xml`、`upper-red.xml`、`enumeration-red.xml`、`monitor-red.xml`、`adapter-red.xml`、`startup-red.xml` 及对应的通过报告。`adapter-green.xml` 曾暴露立即取消语义回归，后续通过拆分关闭标记与资源释放修复；该失败记录不删除或覆盖。

独立服务、Broker、full 与桌面启动器统一使用内核出生标识；展示用 create_time 不参与持久身份比较。内部协议整体升级，旧运行需先停止，不保留旧身份降级。真实桌面三项进程测试曾发现 inspect_process 独立入口缺少代码路径，已修复并重跑通过。桌面完整构建发现缺失 app.manifest，源文件和 gitignore 例外已补齐，未引入管理员权限要求。

扩大测试首次为 61 passed、2 failed。其中一项是旧测试仍访问已清空的线程引用，已改为核对保存的原线程确实退出及当前引用清空；另一项是真实 Windows mmap 归属误拒绝。20 轮、每轮四个 producer 的独立复现捕获了第 11 轮错误：root 为普通 `W:` 路径，目标 resolve 返回相同位置的 extended-length 路径，原比较误认为越界。`telemetry-path-probe-verified/11-1.json` 保留两端原值，不把此错误归因于本轮线程修改。

首批性能结果仍失败：模型五轮 P99 超限，小图两轮超限；标准和较早启动的 600 秒资源轮及正式停止检查通过。该批不包含上述外层修复，不能作为最终源码的认证。补充修复后使用 `outer-frozen-*` 重新组合回归、组装、冻结与执行，不覆盖首批失败证据。

补充后的组合结果为 Windows **751 passed、13 skipped**、WSL Ubuntu **335 passed、16 skipped**，对应 `combined-windows-outer.xml` 与 `combined-ubuntu-outer.xml`。WSL 符号链接越界实测通过，额外八项 Windows 路径前缀测试明确跳过。WSL 的两条 Starlette/AnyIO 弃用告警保留，不计为功能失败或掩盖为无告警。前端 HTTP 七项与 Vue 类型检查重新通过，新增 Python 代码 Ruff 与差异空白检查通过。

### 外层修复后的最终冻结结果

最终候选为 `outer-frozen-*`。三份清单的共用文件摘要没有差异，2,242 个后端 Python 源文件与发行副本逐个相同。验收使用 GPU1、同一工程 YOLO26 segmentation TensorRT FP32 产物、一个实际模型实例，默认 diagnostics 和 keep-warm 仍关闭。小图与 20MP 的四并发是四个独立无模型流程，不是四个模型请求；模型准入仍由实际部署实例数决定。GPU1 未安排其他计算任务，但保留 WDDM 桌面图形环境，未更改驱动、电源或时钟。
