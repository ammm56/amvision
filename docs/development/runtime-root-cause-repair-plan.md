# 运行时根因修复与验收计划

## 状态与目标

2026-10-15，状态：部分完成。最终 Windows 1051 项、WSL Ubuntu 640 项回归通过，独立 600 秒和一小时资源验收通过；最终模型五轮中两轮、小图五轮中一轮 P99 失败，整体仍为 `not_passed`。首次长稳发现 pinned 输出统计缺口后中止，补全统计及 Workflow manager 停止确认后重新组装、冻结并完成正式验收。当前证据见 [修复验收结果](runtime-repair-results-20261015.md)。本计划不表示已完成全部修复或验收。

目标是修复 EventRing 存活探测竞态，消除已验证的不必要热路径工作，查清并修复小图与默认模型 P99 失败，再验证停止、恢复、资源与模型输出均未回归。不重做已有跨平台进程框架。

## 固定边界

- Windows 优先，Ubuntu 以 WSL 实测为准；OS 差异只在现有进程与 IPC 基础设施适配层。
- 模型容量按实际 DeploymentInstance 数决定；无模型流程不加模型容量限制，不增加业务等待队列或常驻包装进程。
- 整组回收、停止超时保留依赖、关闭中的恢复拒绝、generation、fingerprint、worker epoch 和 Buffer receipt 校验继续保留。
- 默认 diagnostics、keep-warm 保持关闭。不改模型精度、输出、输入尺寸、算法或数值容差来取得性能通过。
- 不放宽既有门禁，不删除失败结果，不用诊断 profile 替代正式验收。运行时故障不回退到旧实现。
- 只修改源码并重新组装发行；不手改 release 副本。保留当前工作区其他修改，不自动提交 Git。

### 已实施与证据

- R1：owner 观测不再取得独占锁；Windows 仅把原生错误 33 识别为锁占用，Linux 查询 OFD 锁。探测前后校验文件身份与 epoch/session。遥测 receiver 遇到权限或身份不确定时关闭 reader，不删除文件。
- R1 真实进程验证：两个独立 observer 在打开 handle 后暂停，新 publisher 仍能启动；第二个 publisher 被拒绝；恢复 observer 后均看到真实 owner。覆盖零字节和一字节锁文件。
- R2 失败复现：外层 guard 阻塞 reject；两个不同 Runtime 的 hash 分段碰撞；模拟一秒 1,000 次节点唤醒产生 1,001 次恢复扫描。证据为 `data/acceptance/runtime-repair-20261015/admission-red.xml`。
- R2：沿用既有 manager，外层准入传递 wait/reject；锁改为按 Runtime 唯一、弱引用回收的注册表。monitor 保留即时节点 deadline 检查，将数据库扫描限制为原半秒周期或实际回收事件触发；扫描中到达的恢复标记不会丢失。
- 第一轮 R1/R2 组合：Windows 152 通过、6 跳过；WSL Ubuntu 153 通过、5 跳过。证据为同目录 `r1-r2-windows.xml` 和 `r1-r2-ubuntu.xml`。平台跳过不能替代另一平台验证。
- 以上结果只确认边界测试。小图及默认模型原 P99 门禁、最终冻结候选和一小时长稳尚不能据此标为通过。

## R1：修复 owner 探测竞态

### 实现设计

在既有 `mmap_primitives.py`/IPC 适配层提供不取得所有权的锁占用观测。publisher 仍是唯一可以 acquire owner lock 的角色；reader 不创建锁文件、不取得临时独占锁，也不以 PID 存活替代内核锁。

- Windows：通过独立只读句柄，对 owner 锁范围执行原生 `ReadFile`。仅 `ERROR_LOCK_VIOLATION` 表示该范围被独占；其他错误按真实含义上报。不能将 Python 的所有 `PermissionError` 或 `EACCES` 都当成 owner 存活。
- Ubuntu：使用独立打开的文件描述符和 `F_OFD_GETLK` 查询既有 OFD 锁，不能使用会取得锁的 SETLK，也不能换为进程级 lockf。
- 查询句柄不使用排斥 writer 的文件共享方式。它的存在不能阻止合法 publisher 取得 byte-range lock。
- 观测结果只是瞬时状态，不能授予执行权。reader 仍核对 channel、owner epoch、session、closed 状态及文件身份，拒绝路径替换和旧代快照；真正执行准入由原生命周期与 token 边界决定。
- 文件缺失、文件身份变化、权限不足与锁被持有分别处理，未知状态不能冒充 healthy 或确认退出。文件身份沿用既有 inode/设备或 Windows handle 身份机制。

设计预验证：本机对零字节和一字节文件的锁范围读取均得到 Windows 原生错误码 33，解锁后可读。该结果只验证单机基本原语，不替代跨进程、重启与 WSL 验收。现有零长度 owner 文件可先按原语验证保留，不为消除竞态无条件升级整个 EventRing 数据协议；若后续确需改变格式，必须显式版本化并整体更新读写双方。

依据：[Windows 字节锁](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files)、[Linux OFD 查询](https://man7.org/linux/man-pages/man2/fcntl_locking.2.html)。

### 必须覆盖

- 多个 reader 并行探测不能使新 publisher 启动失败，也不能互相误报 owner 存活。
- 两个真实 publisher 同时启动只能有一个成功；持锁进程强制退出后仍按正式恢复入口接替。
- 旧 reader 跨 owner 重启、文件删除/替换、同 PID 不同出生代次、权限失败与初始化中断均不能误报 ready。
- 状态采集、InferenceStatusPublisher、训练遥测共同使用 EventRing 的路径全部回归。
- 真实 Windows 与 WSL 进程复现，含零长度锁文件、不同 handle、旧 mapping 未关闭的情形；无休眠碰运气的单一测试。
- full 启动、故障恢复、正常停止、启动失败回滚以及中间进程退出后的孙进程回收重新通过。

## R2：准入与 monitor 热路径

### 准入边界

现有 `admit_sync_workflow_run()` 在到达 `acquire_execution_token(..., reject)` 前，先进入阻塞式 `runtime_lifecycle_guard()`。先补受控测试，固定停止/恢复持锁时的调用顺序，明确它是否等待以及是否影响另一个 Runtime。

修复在既有生命周期入口内完成：实时 reject 调用从最外层起即非等待准入；停止或恢复期间明确拒绝，不等锁释放后继续执行旧请求。控制操作本身的资源排空仍保留 deadline 和退出确认，这不是业务排队。

生命周期锁与执行 token 分工不变，不能去掉外层锁后形成检查与使用之间的竞态。当前 64 个分段锁的跨 Runtime 碰撞必须纳入测试，不能把无关 Runtime 的控制动作变成模型容量不足；若需调整锁存放方式，仅改造现有 manager 的锁归属与回收，不并行维护第二套锁表或无限增长的历史 ID 缓存。

覆盖 stop/start/restart/recovery 与 invoke 的交叉顺序、token 在异常和取消时的归还、同 Runtime 顺序保证、不同 Runtime 隔离、真实 Deployment 容量，以及无模型流程不被模型限流。

### monitor 扫描边界

现有节点开始/结束事件会唤醒 monitor，而 `_run_monitor_loop()` 每轮都执行 `_schedule_desired_runtime_recoveries()`；后者查询所有 desired=running Runtime，再逐个查询 revision。这使节点事件频率和数据库恢复扫描频率发生耦合。它是需要验证和消除的冗余工作，但尚不是历史 35.444 ms P99 的完整归因。

在同一个既有 monitor 中分离两种工作，不增线程或业务队列：

- 节点 deadline、取消和 force-kill 继续即时唤醒和检查，不延长原 timeout/grace。
- 全量 desired-state 对账使用独立 monotonic 到期条件；普通节点开始/结束不触发全量数据库扫描。
- 已确认 worker 缺失、组回收完成等事件触发及时恢复检查，不能把快速恢复推迟到任意长周期。
- 使用有界标记合并重复扫描请求，不累计待处理业务项；周期对账仍能发现持久状态变化。
- Repository 继续通过 ORM 读取，可合并 Runtime/revision 查询，消除 N+1；不让业务层直接写 SQL。

测试验证：大量节点唤醒不使扫描次数随请求数量增长；恢复事件不会丢失；stop 与清理失败时不会启动下一代；节点超时精度及现有恢复预算不退化。观测线程、对象分配和查询次数，但不能据此代替端到端验收。

### 其他每请求分配

先量化实际分配位置，再处理反复构造的 ORM 语句、重复元数据复制及不变 policy/snapshot 解析。可复用不可变语句和当前已加载版本的数据；不能建立按时间失效的可变运行状态缓存，不能跳过数据库中的停止/选版变化。若修改状态来源，须先证明所有写入口与跨进程失效均受现有生命周期边界控制，否则保留原校验。

## R3：小图与 GC 归因

此前逐慢调用 JSON 日志产生明显干扰，不再使用它的性能数值。诊断复用现有请求 identity 和阶段计时，增加诊断专用的关联记录，不另建常驻观测服务。

记录采用有界、预分配的定长缓冲，测量窗口结束后导出；满载计数并明确标记证据不完整。GC callback 只记录开始、结束、代次与进程时间，不在热路径枚举栈、序列化 JSON、同步落盘或增长列表。SDK、backend 和 worker 保留 request/trace 关联、单调时钟单位与时钟域；没有校准的不同进程时钟不能直接相减。

先做观测开/关对照，确认分配量、CPU 和延迟未被明显改变，才用于归因。正式性能验收关闭全部诊断。若内部观测仍产生明显干扰，停止使用该观察器，针对时间窗口使用平台调度观测；不以增加日志强行解释结果。

分别处理：

1. GC 同步尖峰：关联同进程 GC 区间与请求区间，结合 R2 的分配/扫描变化做对照，核对仍有无长暂停和内存滞留。
2. 连续慢窗口：定位 allocation、准入锁、Broker、worker 回复、ACK 回收及 OS 调度所占时间，针对真正重叠的因素修复。

不全局禁用 GC、不无边界 gc.freeze、不定时强制 GC 掩盖尖峰。不能在尚未证明因果时先新增进程或移动整个 TriggerSource 子系统。若现有进程边界确实不能满足原门禁，需形成明确的边界调整说明，再复用既有独立执行器实施，不能将此项提前写成已解决。

## R4：默认模型 P99

在 R1/R2 稳定后，继续使用 GPU1、同一工程 TensorRT FP32 产物、同输入和同实例数。先检查同 session 的连续及不同请求间隔，再检查完整 ZeroMQ/shared 链路；基线和候选采用交替运行顺序，保留全部轮次，避免将系统状态变化误当传输差异。

同请求分离 CPU enqueue、CUDA event、完成等待、H2D/D2H 与平台握手耗时。GPU 频率/利用率等观测仅作有时间关联的辅助证据，不把某个低频样本解释成全部尖峰原因，也不从未校准时间戳推导调度结论。

处理顺序：

1. 修复已经证明的不必要 CPU 往返、分配、串行化或锁竞争；保留 PREPARE、ownership handoff、ACK 和 receipt 回收语义。
2. 对仍落在 GPU 时间区间的尖峰，区分空闲频率、GPU 调度和引擎执行；不降低精度或换模型来回避。
3. 已授权的 keep-warm 只作独立配置对照，不能变成默认修复或占用真实请求容量。
4. 驱动电源/时钟策略需要额外明确授权与厂商支持核对；不假定 RTX 4070 支持 TCC，不自动改系统设置。

若原默认环境下 GPU 执行本身仍不满足门禁，保持 R4 未通过，提交清晰的环境限制和必要的部署决策。不能承诺纯软件一定消除所有 WDDM/电源状态波动，也不能把环境原因当成验收豁免。

输出一致性验证使用同产物、固定样本和既有容差，覆盖分类、框/分数、mask、keypoint 或旋转框中实际受到公共运行时修改影响的契约。没有修改模型 core 时不重写模型算法；若触及公共推理路径，扩大相应模型/任务回归，不只测一张图或一个类别。

## R5：最终冻结与交付

1. 执行 Windows 与 WSL 的相关组合回归，补齐 R1/R2 新用例；跳过项逐条说明，不只追求测试数量。
2. 执行 .NET SDK/启动器测试、前端 HTTP 与类型检查，并针对实际受影响的 busy、停止失败、恢复状态做页面 smoke；没有 UI 行为变化则不做无关重设计。
3. 从源码组装发行，冻结源码、依赖、SDK、模型和配置摘要；随后执行原模型、小图、20MP、sync/async 与 Workflow 矩阵，原有轮次、样本数和门禁不变。
4. 执行标准及较早启动两种资源窗口，保留 RSS/private、线程、句柄、pinned buffer、进程数、回收和日志观测；不能改变启动时间来绕过旧窗口增长问题。
5. 按最新确认的范围执行 **1 小时**冻结候选混合负载长稳验收，覆盖启停恢复，保留逐窗口门禁与累计趋势。本轮不安排 2 小时或 24 小时运行，更长周期由项目维护方另行验证；1 小时通过不等同于所有现场场景认证。
6. 检查运行前后摘要一致，正式停止全部本轮测试服务，独立检查 Windows/WSL 无残留，再清理 `.tmp`。

任何生产源码或默认配置在冻结后发生变化，废止该候选后续认证并重新冻结、重跑受影响组合和正式验收。诊断用的替代配置不混入默认配置结果。

交付清单包含各问题的根因、修复文件、反向边界测试、完整失败与通过证据、最终配置、平台覆盖和未覆盖范围。只有三类问题均达到相应完成条件，才可关闭本轮修复；不能将“执行结束”写成“全部通过”。
