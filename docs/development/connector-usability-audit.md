日期：2026-10-08。当前二维连接器功能已经具备工程闭环，能够在既有 Workflow 中配置、预览、发布并显示结果。本文保留首轮发现，并在末尾追加修复后的第二轮审计；首轮问题不能直接当作当前仍存在的缺陷。当前下一步以 [实施基线第 13 节](connector-inspection-2d.md#13-第二轮使用体验改进与交付步骤) 为准，第 12 节及下方首轮优先级用于追溯。

## 实际使用步骤

### 1 进入图编辑

状态：功能路径完整，信息层级需要优化。

![节点画布](../../data/development/connector-inspection/ux-audit-20261008/01-workflow.jpg)

六个节点组已经按输入、定位、PIN、测量、判定、显示排序，并附配方边界说明。当前窗口在 44% 缩放下才能显示多个步骤，参数和说明文字很小；单节点组留白较多。应用属性面板首先展示内部应用/执行 ID 和输入类型按钮，待检图片入口在较低位置，小地图与该入口重叠。

建议先调整工程模板布局和节点摘要，优先显示产品配方、当前资源名称和本次运行结果；原始 ID 留在详情。公开端口的稳定字段名保留，显示标签可简化。避免为了这一示例重做全局画布或改变旧流程尺寸。

### 2 选择定位模板

状态：版本引用和图形取点已实现，资源创建步骤仍偏技术化。

![定位模板资源](../../data/development/connector-inspection/ux-audit-20261008/02-template.jpg)

资源可按版本选择、查看原图、导入和导出；没有直接暴露任意服务器路径。创建区域同时呈现导入 ZIP、上传 PNG、参考坐标 ID、ROI 和锚点坐标，已选资源名称又重复显示。“清除资源引用”占据一整行，层级过高。

建议将“选择已有 / 新建模板 / 导入”作为明确操作；选中后展示缩略图、名称、版本、图像规格，主操作为框选区域和设置基准点。坐标数值作为精确调整，不要求普通使用者先理解资源摘要和内部 ID。资源版本保存与节点引用应用是两个动作，应清楚显示保存结果，避免取消节点编辑时误以为已创建资源也被删除。

### 3 配置 PIN 阵列和采样

状态：可配置且已有真实诊断，首屏重点和重新生成行为需要修复。

![PIN 布局](../../data/development/connector-inspection/ux-audit-20261008/03-pin-layout.jpg)

资源加载完成后正确恢复参考模板；初始短暂“未选择”不是模板丢失。稳定编号、设计留空、不同类型、候选带和逐线诊断都有实现。本次已有预览显示 R1P01 覆盖率 100%、最大拟合残差 0.3069 px；这是该样本的拟合信息，不是测量准确度。

问题在于剖面、梯度和逐线数据位于参考图片及 PIN 表之前，首屏看不到正在配置的工件。排列生成器仍显示初始值 Origin 100/100、Pitch 50，与已有 PIN 坐标及约 85.56 px 的节距不符。源码的生成动作直接替换草稿中的 pins，可能重置留空、类型或端点配置；虽然尚可取消整个弹窗，但缺少清楚的替换范围和局部恢复。

建议参考图与 PIN 表并排，采样参数与诊断围绕当前 PIN 展示；诊断不默认占满布局首屏。将“新建排列”与“编辑现有排列”区分，规则阵列可以可靠推导时才回填生成器；不规则布局不能假装是默认规则阵列。生成后先预览差异，不静默删除留空、端点和对应尺寸配置。

### 4 配置尺寸项

状态：图形方向与截面入口已实现，存在明确控件显示错误和防错缺口。

![尺寸项编辑](../../data/development/connector-inspection/ux-audit-20261008/04-measurements.jpg)

尺寸项与独立公差节点保持正确分工。已有参考图方向/截面编辑，无需重建这项能力。但表中的启用复选框显示为细线：实际 DOM 宽度约 1.33 px，高度 16 px，`appearance:none` 与局部 `width:auto; min-width:0` 组合使其只剩边框。列标题“启用”也换行。

PIN A/B 和具名特征目前是自由文本；前端主要验证字符串形状，并不证明选中的 PIN 实际存在。方向单位向量、截面投影、过长小数也增加学习成本。图像交互已能计算方向，用户不必在正常操作中先执行“归一化方向”。

建议使用统一固定尺寸复选框；PIN/特征从显式连接的上游配置选择，无法静态解析时明确提示并保留运行校验。支持按一排/选中 PIN 批量添加宽度、节距等尺寸，保留稳定 item_id。显示精度可简化，但打开、取消或不改动保存不能改变原始数值，更不能将显示舍入用于判定。

### 5 配置公差

状态：判定契约严格，当前编辑器有类型正确性问题，优先级 P1。

![公差规则](../../data/development/connector-inspection/ux-audit-20261008/05-limits.jpg)

51 条规则以长卡片排列，Item Id、Unit、Enabled、Required 和包含边界选项均为文本输入。源码 `WorkflowParameterRows.vue` 只对 integer 转为数值，其余普通输入原样写入字符串；而 `LimitRule.enabled/required/include_lower/include_upper` 使用 StrictBool。修改这些字段后，即使输入 `false`，也会产生错误类型。

本次在开发 Python 直接核对：`enabled=True` 验证通过，`enabled='false'` 被拒绝为 `bool_type`。这是有意构造的负例，不是生产运行失败记录。原来未编辑的布尔值不会仅因打开/取消而变成字符串；不能据此说现有全部规则已经损坏。

修复需同时覆盖类型正确性和易用性：通用表单支持 boolean、number、nullable number，空上/下限保持 null；公差使用紧凑的通用数值规则表，启用/必检为复选框，单位和条目有明确选择，边界用包含/不包含表达。上下限错误在行内定位。必检集合始终来自保存的配方，不能根据上次成功测出的项自动删减。

### 6 保存和选用平面标定

状态：资源版本化可用，标定输出到资源保存仍依赖手工交接。

![平面标定资源](../../data/development/connector-inspection/ux-audit-20261008/06-calibration-resource.jpg)

界面要求把 Planar Calibrate 的 Calibration 输出复制进文本框。虽然技术上能保存和验证，但现场人员容易选错输出、用旧结果或混淆相机内参与平面映射。当前选择界面也没有直接展示有效域、单位、图像规格及独立验证误差。

建议在成功标定的结果上提供“保存为标定资源”，显示本次参数和结果是否一致、有效域及独立验证结论；调用已有资源服务生成不可变版本，再由测量节点显式选择。手工 JSON 导入可作为高级入口。相机内参、去畸变图像空间和平面映射不能仅因图片尺寸相同而视为相容。

本次没有重新执行棋盘/平面拟合，也没有重新审计标定取点弹窗；其已有实现由代码和既有验证记录说明。

### 6 识别标定依据

状态：存在优先级 P1 的证据展示问题。

![第二轮：标定资源证据提示](../../data/development/connector-inspection/ux-review-followup-20261008/06-calibration.jpg)

本次合成比例资源没有独立验证点，却显示“独立验证最大误差 0”，未注明单位或缺少验证证据。代码中 `PlanarCalibration.evidence` 可为空，而资源选择器直接显示 `validation_max_error`；工程资源生成器把该值设为 0。这个显示不能支持“实际标定无误差”的结论，也不是已经证明测量计算发生错误。

建议：没有独立验证点时显示“未提供独立验证数据”；有证据时显示点数、最大误差和单位。即使存在验证点，也不能自动宣称实物验证完成。合成/实物/外部导入来源只能依据明确元数据，不从资源名称或 plane_id 推断。不可变资源内容不原地修写，旧结果原值仍可在工程详情查看。“清除资源引用”改为次要操作，去掉重复名称和主要流程中的大段内部字段。

## 第二轮代码与边界核对

- `WorkflowMeasurementResourcePicker.vue` 是上述证据展示问题的直接入口；`WorkflowCalibrationResourceSave.vue` 已有同次完成预览、参数快照及过期结果防护，不能把标定保存功能重新列为缺失。
- `PinLayoutEditor.vue`、`MeasurementEditor.vue` 已有草稿事务和批量预览，应调整组织方式，不重写已有几何、配对和公差定义。
- `WorkflowPreviewTable.vue` 与 `WorkflowResultTable.vue` 使用不同的状态/单位呈现规则，是显示不一致的实现来源。
- `parameters/static-numeric-items.ts` 直接导入连接器包描述函数，平台通用遍历与行业实现有静态耦合。建议在现有可信编辑器组合入口登记条目描述提供器，平台只调用通用接口；不建设另一套插件加载系统。这是维护边界改进，不是已复现的执行故障。
- Schema 允许的大量 PIN/规则不等于当前全部行渲染在大配方上已通过交互性能验证。大列表及双语、暗色、键盘、焦点和不同窗口尺寸需下一轮单独验收，本次不能外推。

## 第二轮优先级与判断

| 顺序 | 目标 | 判断依据 |
| --- | --- | --- |
| R01 | 标定证据提示正确、原应用与验证应用交接清楚 | 不把缺少证据显示成零误差，不把旧配方差异误报为新功能失效 |
| R02 | 静态配方引用检查及通用层边界 | 只使用显式连线/资源；已知错误定位到节点，不可靠解析明确标出 |
| R03 | PIN 与尺寸默认视图围绕现有对象 | 参考图可用，编辑已有项无需穿过新增表单；取消不改参数 |
| R04 | 公差与各结果入口统一呈现 | 单位、状态、原因一致；原始值和判定不受展示精度影响 |
| R05 | 两套工程应用和用户操作文档交付 | 更新目标草稿需显式操作，发布与 Runtime 切换分开 |
| R06 | 最终版本的交互、回归、节拍及一小时门禁 | 不复用修复前长测充当最终版本验收；实物计量另设证据门禁 |

结论：目前适合受指导的工程配置和合成资源验证，尚不宜表述为现场人员无需指导即可完成所有配方。主要优化是已有能力的顺序、证据和呈现，不是再增加节点数量。详细代码范围、依赖及逐步验收统一进入实施基线第 13 节。
