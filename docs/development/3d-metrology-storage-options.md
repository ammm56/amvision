# 三维运行存储与 5 GB 输入方案核对

日期：2026-11-16。源码核对基点：`eec8eb49`。本轮只修改前端控件，不修改后端存储、生产容量或输入协议。用户要求先比较方案；以下建议尚未获准实施。

**本轮确认结论：保持现有实现。** Preview 临时输入、Runtime 文件暂存、文件支撑的 LocalBuffer mmap、释放清理及显式 Save 均保持不变。更好的存储方案与 5 GB 点云支持另行详细讨论；本文后续步骤不是已批准的实施计划，不据此调整容量或切换纯内存。

## 1. 必须分开的概念

- **持久保存**：显式 Save 节点或资源管理操作创建可重读资产。普通测量不应自动归档完整原云。
- **运行暂存**：上传、跨进程访问期间的临时数据。即使结束即删除，仍可能产生磁盘写入。
- **内存映射**：访问方式，不等于磁盘保存，也不等于物理内存常驻。mmap 可映射已有文件，也可使用匿名内存。
- **算法数组**：解码后的坐标、属性、原始行号及中间计算结果。文件大小不等于数组大小。
- **显示数据**：有界概览和已保存资产的原始细节索引是不同路径。只返回数值不应隐含构建全云显示索引。

因此，“不永久保存”“应用不创建点云临时文件”“操作系统完全不写盘”是三种不同要求。Windows 的命名共享内存可由系统分页文件支持，不能把共享内存宣传为绝对不会触及磁盘。依据：[Python mmap](https://docs.python.org/3.12/library/mmap.html)、[Windows 命名共享内存](https://learn.microsoft.com/en-us/windows/win32/memory/creating-named-shared-memory)。本项目不应擅自关闭系统分页文件或锁定全部物理内存。

## 2. 已核实的现状

| 路径 | 当前实现 | 保存边界 |
| --- | --- | --- |
| Preview 文件上传 | `preview/buffers.py` 使用 `SharedTemporaryInput`；文件描述、pin 与执行生命周期绑定 | 会临时写盘；释放最后持有者后删除，不是资产归档 |
| Runtime HTTP 文件上传 | multipart 解析后，经 `workflow_runtime_support/uploads.py` 写运行输入对象，再传给执行端 | 不是纯内存路径；正常清理与异常中断必须分别验证 |
| 同机二进制数组 | `point_cloud/local_array.py` 借用 LocalBuffer 只读视图，沿现有预算和 Scope 释放 | 避免跨节点重新复制，但 Broker 的文件支撑 arena 仍有磁盘后备 |
| 文件解码与算法 | CloudRuntime 管理 NumPy 等数组与工作预算 | 不应统称为 mmap；不保证任意算法都可流式处理 |
| 原始细节索引 | `point_cloud/detail_index.py::prepare_index` 只接受 ready 的完整已保存资产，显式构建块文件 | 不对任意运行输入自动索引；新代次提交后清旧代次，删除源资产时回收 |
| Save Cloud / 导出 | 沿现有资源与保存节点执行 | 用户明确要求的持久保存，不在本轮取消范围 |

重要源码：`backend/service/infrastructure/filesystem/shared_temporary_input.py`、`backend/service/application/workflows/preview/buffers.py`、`backend/service/api/rest/v1/routes/workflow_runtime_support/uploads.py`、`backend/service/application/workflows/point_cloud/local_array.py`、`backend/service/application/workflows/point_cloud/detail_index.py`。

当前索引不是“每次执行自动留下完整点云”的证据。另一方面，“结束删除”也不能冒充“从未写盘”。本轮没有重跑后端异常退出、资源清理或长稳测试，不据静态路径宣称所有异常清理均已通过。

## 3. 当前容量不满足 5 GB

以下为本机配置文件和源码常量核对，不代表已经对正在运行进程逐项读取有效配置：

| 层次 | 当前值 | 位置 |
| --- | --- | --- |
| 公开点云输入上限 | 1,000,000,000 字节 | `backend/contracts/workflows/point_cloud.py::MAX_POINT_CLOUD_INPUT_BYTES` |
| Broker 总 arena / 单次分配 | 2 GiB / 1 GiB | `broker_settings.py` 与 `config/backend-service.json` |
| Preview 文件单会话 / 总暂存 | 500 MB / 1 GB | 本机 `backend-service.local.json` |
| 解码数组 | 400 MB | 同上 `io.max_decoded_bytes` |
| Run 活跃数组 / 算法工作区 | 1 GiB / 4 GiB | 同上三维策略 |
| 保存资产 / 资产包 / 导出 | 600 / 610 / 600 MB | 同上三维策略 |
| 概览 | 100 万点、二进制数据 32 MiB | 同上显示策略；不是原云可测点数上限 |

MB/GB 在本表表示十进制，MiB/GiB 表示二进制。用户所述“5G”尚未定为 5,000,000,000 或 5 GiB，实施前需统一字节定义。

现有 Buddy 分配器要求容量为二次幂，并将单次连续分配向上取整。若仍用单块承载 5 GB 或 5 GiB，块容量均需到 **8 GiB**，不是把单次上限直接填 5 GB 即可。8 GiB 是分配占用，不等于立即拥有 8 GiB 驻留物理内存；还须为其他调用和图像业务预留空间。实现证据：`backend/service/infrastructure/local_buffers/buddy_allocator.py::BuddyArenaGeometry/allocate`。

mmap 没有本项目这种固定 1 GB 技术上限；当前限制来自协议、策略和分配结构。仅调大 arena 仍会在上传、解码、活跃数组或保存路径被拒绝。

## 4. 方案比较

| 方案 | 优点 | 成本与风险 | 适用范围 |
| --- | --- | --- | --- |
| 直接只读已有本地文件 | 不再上传复制一份；可利用操作系统缓存；保留现有成熟解析器 | 首次读取仍有 I/O；ASCII/压缩格式仍需解码；须校验可访问范围、文件身份和执行期间变化 | 文件已在运行主机的复算；浏览器选文件不能自动当作服务端路径 |
| 受管临时文件 + 文件 mmap | 跨进程共享，不必各复制完整载荷；适合较小 RAM；可复用当前所有权机制 | 会写盘；缺页与磁盘竞争影响尾延迟；需磁盘准入、取消/崩溃回收；大连续块存在取整开销 | 明确允许运行暂存的离线/大文件场景 |
| 共享内存 + 内存解码 | 应用不生成原云临时文件；同机数组传递成本低，内存充足时延迟更可控 | 不能消除解析与算法成本；需同时容纳重叠生命周期的输入、输出及工作区；内存不足须明确拒绝；系统仍可换页 | 对运行写盘敏感、RAM 容量明确的生产调用 |
| 按输入方式显式选择 | 本地已有文件不复制，同机数组共享；保存仍只由 Save 完成；可复用 Broker、Scope、既有解析器 | 必须明确模式与预算，不能内存不足时偷偷落盘；不同模式需要各自验证 | 建议进一步收口的方向，不是本轮已决定的实现 |

“默认保存完整资产后再测量”不符合当前要求，不作为推荐方案。为了读取方便而自动 Save、每次为原云生成永久索引、每个节点重复写一份文件，也不应引入。

## 5. 5 GB 不等于只需要 5 GB 内存

容量核算应按同一时间仍存活的不同数据计费：

`输入载荷 + 解码属性 + 来源索引 + 派生结果 + 算法工作区 + 有界显示 + 其他进程余量`

- 同一共享块不能按多个进程 RSS 简单重复相加；同时也不能忽略复制、临时数组及系统缓存。
- ASCII PLY 的 5 GB 文本可能解码后更小；压缩 PCD 的 5 GB 文件可能解码后更大。应先读头部并估算，不能按扩展名推断容量。
- 纯 XYZ float32 二进制按每点 12 字节计算，5 GB 约有 4.17 亿点；若另需每点 uint64 来源索引，约再占 3.33 GB。全量 float64 XYZ 副本为约 10 GB，但当前设计不要求所有算法都创建这种副本。
- ROI 扫描可分块不等于全量三角剖分、空间索引、拟合等步骤全部天然分块。5 GB 输入可接收与整条配方可完成是不同验收。
- 本轮不填写新的最低 RAM、并发数、timeout 或默认算法预算，不承诺 5 GB 的十秒节拍。

## 6. 建议实施顺序，待存储边界确认

1. 固定“不自动归档”与“是否允许运行临时磁盘”两个独立政策；显示概览、原始细节缓存和 Save 分开声明。
2. 获取代表性 5 GB 文件的格式、点数、字段和实际大小；核对目标 Windows/Ubuntu RAM、磁盘与调用方式。样本不足时不以小文件结果宣称全容量完成。
3. 统一入口、描述符、SDK、解码、活跃数组、工作区、保存和导出容量；只调整已选定模式。无容量时直接报告不足，不加等待队列或隐藏落盘降级。
4. 复用 LocalBuffer/Scope 生命周期；评估单块 8 GiB 的取整代价。若需改变分配形态，先单独给出数据视图、借用与回收方案，不再造第二套资源系统。
5. 明确文件解析与算法的峰值，保持原始字段/精度/行号；显示预算独立，不为显示把全云复制进浏览器，不以显示采样替代测量。
6. 验证正常结束、取消、超时、客户端退出、worker 退出、重启、磁盘/内存不足；检查 Run owner、reader guard、文件/句柄/共享块以及索引的回收。
7. Windows 与 Ubuntu 原生文件系统同样本验收；统计实际分配、共享/私有内存与磁盘写入，最后再定可交付容量。不会因本轮前端测试通过就宣称存储方案完成。
