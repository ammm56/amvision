### 3.1 高度定义差异

手工 `plane_height_at_xy` 在同一**源坐标** `(x,y)` 分别求局部平面上的 `z_top`、`z_body`，再计算台面有符号距离。因此 `H_report = n_D.z * (z_top-z_body)`。两个点连线沿源 Z，不一定沿台面法向 `n_D`。

R4 方向测距则对 `q + t*a` 与两平面求交，返回 `t_target-t_reference`；`a` 是显式单位方向。R5 已确认正式高度取 `a=n_D`，查询点在同一已定义的台面 U/V 位置。倾斜或翘曲时两种算法不能标成同一量；报告仅作参考，验收使用同一定义的独立计算，不调参数追求旧数字。

- `H`：钢片目标面相对其邻近基体面的中心位置高度差；仅基准可有限延伸。
- `Z`：钢片目标面相对载物台面高度；另一个基准和独立延伸距离限制，不复用 H 的上限。
- `t`：报告中的六个邻近基体 ROI 到台面的点高度中位数，不是钢片中心处的基体面高。`t+H` 不必等于 Z。
- `H_local`：height-query 的有限圆柱局部拟面结果，只作另一个明确命名的量。整片核心区拟面和局部拟面不要求相等；如用相同拟面特征/同一评价线经 measure-step 计算，应一致且不重复拟面。
- 十二片分别记录，不用六处左右片合并拟合结果替代单片值。两片间高差或六个 t 若纳入交付，单列输出，不暗中扩充本轮验收范围。

### 5.1 节点主线

| 分支 | 复用节点与算法 | 前置条件/结果 |

| 共同输入 | read-cloud → normalize-units → filter-valid | 一次完整读取，共享只读引用；有效点过滤不是去噪 |
| 基准 | 五 ROI 并集 → fit-plane → build-frame | 联合支持已确认、并集扩展待实施；Open3D 候选＋原正交 QR/SVD，保留全部质量检查 |
| 坐标 | transform-cloud | 现有刚性变换和 Scope；一次共享或仅变换必要子集，不能给十四分支各复制一份全云 |
| H / Z | 目标 crop-roi → fit-plane；基体/台面 features → measure-step | 同一目标拟面用于 H/Z，基准各自显式延伸；特征多来源端口已支持，不新增合并系统 |
| 局部高度诊断 | height-query → 既有 features / evidence | 局部方法单独命名；需要交叉检查时把其输出面传给 measure-step，避免重复求面 |

| 输出 | core.value.numeric-tables-merge、cloud-preview、既有 App 输出 | 按稳定 item_id 合并，保留无效项及原因；不另建结果/发布服务 |

| 多 ROI 联合支持 | CropCloudParameters 的 rois 是目标及依赖，roi_mask 只求单个目标或截面带交集 | Q3 已确认，按 5.4 扩展同一裁剪实现；不串联五次 crop，那是交集 |
| 自适应截面高度 | ContourBoundary.height 是静态数值，Catalog 没有绑定对应动态值端口 | 若定义为每次 `h_B+0.5*(h_T-h_B)`，须复用平台参数绑定/数值节点补明确接线并验证无效传播；不能复制报告常量冒充自适应 |
| 基准到查询/评价坐标 | build-frame / transform-cloud 已有；测量方向、query_position 和 evaluation 当前仍是配置，transform-cloud 只输出云，不自动变换 features/ROI | 审核“统一到台面坐标”及必要参数来源；禁止源 frame 的平面接到目标 frame 的云、只改 frame_id、从屏幕方向猜轴。源 XY 表须完整刚性转换，而非照抄到台面 U/V |
| 顶面核心支持 | 现有 ROI 是有限 box/cylinder/section，不是手工栅格连通分量侵蚀掩码 | 先明确工程 ROI 是否接受；若必须复现原支持，再审核通用能力，不以全包围盒或更小窗口替代 |
| 单 ROI 的 t | measure-step(roi-statistic) 是两个 ROI 的统计差 | 不把邻近台面残差中位数当成精确 0；t 的“到指定平面距离统计”不是现成双 ROI 差，若加入必须单独收口 |
| 平面持久恢复 | save-cloud 的 features 扩展当前用于唯一 BoundaryFeature，非任意特征快照 | 保存顶面/基体支持后按配方重拟合；边界按已有 cloud+features 保存恢复；不声称旧 PlaneFeature 可跨运行直接复用 |

上述都是配方能否完整表达的核对结果，不代表都要新增能力。Q1–Q3 已确认，只对确实阻断的部分设计必要扩展，仍交付完整行为，不建空壳、不新增资源系统或通用脚本执行器。

台面平面只确定高度和倾斜，不会自动确定工件面内平移/转角。完整样本的固定位置复算不能声称实现任意来料定位；移动工件的定位来源、原点和方向须另有明确约束。独立刚体变换测试必须同时变换云、ROI、查询和方向，不能冒充自动定位验收。

### 5.3 质量与数值待定项

复用既有严格参数和 quality_policy：平面支持数/二维跨度/法向分离/RMS/最大残差；高度双方覆盖/最近点/三角边/残差/方向；边界支持及长度；线方向可辨识性/跨度/残差；圆角覆盖/最大缺口/Jacobian 条件/残差/半径约束。

待确认数值包括：三维 ROI 的 Z 范围、真实边段窗口、方向与评价点来源、各基准延伸上限、局部搜索/支持半径、表面 alpha/边长/高度跳变、求解参数和各项质量限值。报告已有值只能作为标注清楚的复现配置，不自动填进新定义。Open3D 与报告算法不同，不能承诺随机支持行完全一致；应比较合法支持、质量和数值范围，不强制逐位相同。

质量门禁不是产品公差，也不是算法数值容差。阈值敏感性、ROI 扰动和采样缺失分析用于说明方法适用性，不能从“刚好通过本工件”的值倒推生产限值。拟合失败不扩大残差、不切换算法重试，不把少点/歧义结果补零。

### 5.4 五 ROI 联合支持设计

设计位置是现有 `Roi3d → CropCloudParameters → roi_mask → crop_roi → CloudRuntime.register_subset`，不是新的点云合并节点。Q3 授权的是联合支持语义；以下为源码核对后的实施设计，尚未写代码。

| 部分 | 设计 |
| --- | --- |
| 参数形状 | 在同一 roi3d.v1 中增加 `kind=union`，`geometry.roi_ids` 显式引用成员；成员正文仍放同一 ROI 依赖集合。名称为设计字段，不表示当前 schema 已接受 |
| 有限性 | 并集非空、成员唯一、引用存在、同 frame/单位；沿用现有配置规模限制。统一检查 union 成员与 section-band 的 bounds 依赖，拒绝环及缺失引用，不增加无限 ROI |
| 数据选择 | 对同一父云块分别计算成员掩码并逻辑 OR，闭边界沿用现有定义；重叠窗不重复加权，成员顺序不改变选中父行。五个不同父云不在此自动合并 |
| 所有权 | 沿现有两遍扫描：计数、预留索引、填入递增父逻辑行，再 register_subset。保持 source_indices/source_point_count；不复制五份属性数组、不建立第二套 owner |
| 预算与取消 | 合并掩码、成员工作数组和依赖求值都计入现有 max_working_bytes；逐块且逐成员检查取消，不创建整云×ROI 数量的布尔矩阵。原生拟合另按原预算准入 |
| 来源和保存 | CropCloudMethod 记录完整已校验参数及摘要；资产重读走同一严格类型。成员顺序改变可改变参数摘要，不要求不同配置的摘要相同；输出支持集合须一致 |
| 前端 | 扩展原 RoiEditor 的形状选择及成员勾选，复用现有子 ROI 编辑/拾取。并集显示实际子区域，不显示一个虚假的大包围盒；删除被引用成员时阻止应用并指出引用 |
| 其他使用方 | 原边界 region/target、截面有限边界、资产方法读取和 geometry-overlay 同批支持或明确拒绝未支持输入，不能把 union 当 box。连续段选择仍按原规则，多个区域不意味着允许跨缺口连线 |

普通 crop 明确清除拓扑；R3 边界选择保持拓扑。联合裁剪不能替代 R3，不能把无序支持误当有序轮廓。实现时复用成员几何计算而不是复制三套 box/cylinder/section 算法；依赖检查也不能分成前端后端互不相同的规则。

三维数据契约继续使用当前开发期 v1，不新建 v2/v3 或旧算法兼容分支。实现时按既有规则递增受影响节点/包的实现版本，同批更新读取方和发布依赖身份；不改 Workflow 发布版本管理。原始数据不删除，生产 manifest 仍不创建。

验收必须覆盖：原始云与已有子集、同坐标不同采集行、重叠/相邻/分离窗、成员顺序、空结果、缺失成员和循环、frame/单位错误、参数/输入两种来源、分配/第二遍扫描取消、Scope 关闭、保存重读和前端取消/切节点。独立集合真值逐行比较，不只比点数。

五窗报告支持约 209 万点，不能把此前小窗口 RANSAC 的内存情况直接套用。当前 `_ransac_support` 按 `count*128 + iterations*(sample_size*8 + 64 + count*16)` 估算工作数据；正式验收先用确认参数核对预算，再执行原生调用。不能为通过预算静默抽成报告的 50,000 点、缩小五窗或取消原门禁。

### 5.5 测量参数来源的下一步核定

现有 `NodeParameterInputBinding` 和 `resolve_node_parameters` 只绑定参数 schema 的顶层属性；可以复用，但不能直接把 `settings.method.height` 这样的嵌套路径写进绑定。三维 Catalog 当前未声明此类动态参数端口。

下一步必须给每个量标明四类来源：固定配方、同次几何特征、同次有效数值、候选显示拾取。后两者不能混用；Preview 点坐标只是候选，不是正式拟合输入。

1. **高度方向/评价线**：采用已确认的台面法向；设计在同次台面坐标执行，或从同次有效 PlaneFeature 取得方向，不能拿手工报告法向固定冒充本次结果。坐标/单位/观测身份沿原契约，不给无效基准填默认 +Z。
2. **钢片等高值**：Q2 确认了严格边界，没有确定固定绝对高度还是随两面的相对高度；`0.5` 是报告方法，不自动成为新配方默认。确定此定义后才选择现有顶层对象绑定或明确的几何输入，不先重写通用绑定器支持任意路径。
3. **有效性**：Numeric Table To Value 保留 value/null 及有效性，但普通值本身不能代替几何证据。动态值无效/缺失不得回退静态旧值、补零或继续使用上次结果；设计中明确测量无效与坏配置错误的区别，不能仅依赖 JSON schema 把所有 null 变成输入错误。
4. **质量与证据**：当前运行的最终有效参数必须进入既有 method 参数和摘要；静态草稿不伪装为执行参数。质量规则不因参数来自输入而变成可跳过，也不能让外部输入改写已发布配方的限制。

此节列核定步骤，不宣称上述动态链已接通；没有增加通用脚本节点、表达式执行器或新的发布系统。剩余具体选择在配方接线设计时确认，Q1–Q3 不再重开讨论。

1. 图中按共同输入/基准、六组钢片、S1/S2、结果组织；节点标题和 item_id 对应表中稳定名称。参数不按返回序号绑定对象。

7. 现场仅使用已有已发布 App Mode：输入完整文件/数组、运行、查看数值和原因。未知公差下不输出 OK/NG；无原云的历史只读证据，不能点击历史图重新测量。

部分“按对象聚焦/分层”和完整十四对象结果可读性仍需真实页面验收，不写成已实现。图编排、发布版本和 Runtime 选择继续由现有平台负责。

### 7.1 独立真值与反例

- 高度：已知倾斜台面与两非平行面，在指定台面位置解析求交；与固定源 XY 的报告算法作明确非等价反例。高度搜索区含多层、目标有孔、参考有覆盖但质量失败、延伸等于/超过上限均覆盖。
- ROI：按已确认的并集验证重叠父行不重复、相邻闭边界、窗顺序不影响支持、空窗、跨 frame/单位拒绝、取消及保存恢复；保留同坐标不同采集行，不新增另一种原始行号语义。
- 长宽：已知矩形和圆角轮廓，固定 U/V 与最小矩形分别验证；极值附近缺测不能用残余跨度冒充完整尺寸。轴向跨度是有限所选支持的量，不自带完整性证明。
- 直边：两条有限平行/非平行边的指定方向交点；端点、缺口、外推、短段和错平面；明确方向宽与报告平均偏航修正宽的区别。
- 圆弧：已知半径的整段/多段/短弧；保留类似 S2 缺口的拓扑，检验角覆盖、整周 max_gap、半径碰界、非单调和退化。不得因 RMS 小就忽略角支持。
- 保存：原云/子集字段和 source_indices 不变；生成顶点保存源边/面及插值来源；边界 cloud+features 重读后沿同一选择拟合。最终数值证据持久化不含有效的旧运行租约。

### 7.2 真实样本逐项记录

每个量记录输入文件/数组摘要、提交和包版本、发布版本、稳定 item_id、测量定义、实际 ROI/评价线、算法参数和质量策略摘要、支持行/生成来源、量值或 null、失败阶段/原因、关键质量、延伸或圆弧缺口、有界显示证据。

对照分三层：相同支持/公式的独立数值验证；不同提取方法的敏感性分析；实体标准件/量具的准确度验证。只有第一层允许给“同定义差值”结论；手工估计与严格边界不同的项标记不可直接比较，不能改名后当通过。源样本只说明这一份数据，不代表重复性、相机标定或真实公差。

表面/轮廓失败按 `input → ROI → datum/target fit → surface → intersection → target selection → feature fit → measurement quality → display/output` 定位；先查中间数据再决定改实现。区分产品定义不适用、真实缺测、参数错误、资源/执行异常与代码缺陷，不统一叫“算法失败”。

### 7.3 真实运行与清理

Windows 优先，WSL Ubuntu 的数据库、LocalBuffer、资产和运行目录使用原生文件系统；源码/只读样本可位于 Windows 挂载盘。Windows .NET bytes/fill、Ubuntu 支持的同机协议分别验收，不把 Ubuntu 协议成功写成 Windows 专用 SDK 成功。

复用现有真实发布生命周期用例，覆盖运行中切版拒绝、停止后换版、旧路由、客户端异常退出、执行中停止、恢复、预算拒绝；确认资源归零而非只看停止返回 True。新增多分支重点核对共享云没有十四份全量副本、取消时全部借用/派生索引释放。仅开展与本次变更有关的资源检查，不重做无关压力循环。

测试采用单列显式配置，生产 timeout、kill grace、内存/预览容量、节拍、公差仍待确认。测试服务必须隔离于现有业务环境；收尾停止自己启动的 Runtime/worker/API/Vite、关闭自己的测试页、清理 `.tmp` 和本轮 WSL 目录，保留原始 PLY/BIN、手工报告、既有资产及用户服务。

## 8. 本轮审计结论

R4 可作为 R5 基点，无证据要求重复实现延伸/契约/资源/发布管理。**Q1–Q3 已确认，五 ROI 并集已有基于现有实现的扩展设计；R5 配方尚未完全收口或验收。** 三维支持窗口、等高值取法、参数来源和质量数值仍需核定；不能将本次定义确认写成所有节点已经可以接线执行。
