## 编辑可用性复核与优化方案

2026-11-14 对实际图编辑页面和当前源码进行只读复核。功能链路已运行不等于现场编辑体验已经合格。本节为待实施规格，不把设计记作已交付功能；未修改页面中未保存的草稿、发布版本或运行实例，未启停服务。

### 已核实的问题

| 问题 | 证据与判断 |
| --- | --- |
| Read Cloud 要求编辑 File Options JSON | `shared/parameters.py` 的 `source` 已声明 `cloud-source` 控件，但 `file_options` 没有专用编辑器；前端 `trusted-editors.ts` 未登记对应组件，复杂对象落入通用 JSON 编辑。这是交互缺失，不是现场人员需要学习内部协议。 |
| 画布不能表达工程层级 | 当前实际页面在 25% 缩放下大量跨区连线覆盖节点。仓库配方为 111 节点、317 条边、16 分组，其中 209 条跨组边；统计对象是仓库配方，不冒称当前未保存草稿完全相同。 |
| 显示和汇总线占据主画布 | 原配方 Preview 有 57 条入边，结果汇总有 38 条入边，合计 95 条。这些依赖不能直接认定为冗余，需逐项核对接口是否让调用者重复传递同一信息；不能通过隐藏连线冒充简化。 |
| 分组未形成清晰阅读顺序 | 现有连线已有单线悬停/选中高亮，仍需用现有节点组组织工程区域与数据流。图契约中的 `collapsed` 不作为本轮优化依据；不开发折叠、隐藏子图或视觉连线归并。 |
| 算法数量与编辑负担混为一谈 | 原配方有 25 个 Crop ROI、19 个 Fit Plane、24 个 Measure Step、14 个 Extract Boundary、12 个 Measure Extents。大量实例来自对象重复和共享基准，不是 111 种算法，也不能仅凭节点数判定算法拆分错误。 |

核心判断：首先修复参数表单，并审计真实的节点职责与数据接口，再用现有节点组组织完整可见的流程。分组排布改善可读性，不减少真实计算复杂度；不得将折叠、隐藏连线或自动排列当作功能简化。通用任务节点是否需要调整由职责与复用证据决定，不能预先认定所有现有拆分都合理，也不能改成一个工件专属大节点。

确认边界：节点和实际连接完整可见，仅使用现有节点组组织逻辑和区域；不增加折叠、嵌套隐藏流程或隐式数据总线。底层算法可保持模块化，但不要求每个内部步骤都必须成为一个由现场人员手动接线的节点。

### 固定实施顺序

#### U1：Read Cloud 可视化配置

- 复用已有文件/资源来源控件及可信参数编辑器注册机制，不创建第二套表单框架。
- 文件入口分为输入来源、文件格式、空间定义、字段对应四区。格式和编码用选择器；单位用 m/mm/um/未确认选择；坐标系及轴定义采用有标签的独立字段。协议版本等内部固定字段不要求人工填写。
- 字段对应采用表格：文件字段、用途、目标字段、类型、分量、单位。位置 X/Y/Z 明确显示，颜色、法向、强度及额外标量完整保留；不静默丢字段、不默认降精度。
- PLY/PCD 文件头信息只复用受控解析器。当前 `inspect_cloud_file` 仍要求完整 options，自动展示文件头需核对并复用其受限头读取边界，不能假定现有接口已能自动配置。仅声明明确的信息可预填；单位或坐标语义未知时明确要求选择，不能凭数值猜测。XYZ 无头输入继续显式指定列布局。
- 首次导入可选样本确认字段；运行时文件仍通过原文件端口输入，不把样本路径写死。选择已有点云资产时直接显示资产空间/字段摘要，不再配置文件解析选项。
- 逐字段校验重复映射、缺少坐标、错误类型和单位来源冲突。普通操作不依赖 JSON 文本，保存继续产生原严格契约，不做宽松解析或兼容降级。
- 验证文件/资产切换、已有配置无损回显、未知字段、异步检查晚返回、换节点和卸载取消；保存重开与后端校验一致。真实 ASCII PLY 保持原字段和精度。

#### U2：审计节点职责与真实接线负担

- 按完整图逐项列明各节点的任务、输入输出、共享使用者及重复参数。区分独立工程操作、可复用的中间特征、仅由内部算法需要的步骤和纯数据适配。
- 优先核对 Crop ROI 到 Fit Plane、H/Z 的重复配置、测量结果与显示证据的分别传递、结果转换与封装。这些是审计候选，不是已确认冗余；不能凭节点数直接合并。
- 若某组操作形成明确的通用工程任务、内部中间量没有独立用途，可设计职责完整的任务节点，内部调用现有算法模块，不复制算法、不隐藏一张子工作流。方法、ROI、质量条件及失败证据必须仍可编辑、可解释。
- 若特征供多个测量共享，保留独立节点及显式连接；不得为了减少连线而重复拟合、重复扫描或通过全局变量传递数据。已有契约携带的同一来源若又被重复要求输入，应先核实校验职责再调整接口。
- 每项建议列出修改前后的实际节点、端口、连接、运算次数与错误定位方式。质量条件、来源追溯、资源释放及取消行为不得损失。没有证据的合并不实施；不设任意节点数量目标。
- 涉及公共节点或接口调整时先明确所有读取方及既有配方影响，不借本轮修改应用列表、节点分类或发布系统。

#### U3：整理当前工件配方并完成现场编辑验收

- 按“输入与有效点 → 台面及共享基准 → 十二钢片/两半圆 → 五十项判定 → 显示与保存”组织完整展开的画布。复用现有节点组调整成员和布局，不增加嵌套或折叠分组；所有实际连线保持可见，不以视觉归并替代真实端口连接。
- 每个钢片组内明确基体/顶面支持、H/Z、可见包络 L/W；半圆组内明确边界、拟圆、直径。共享基准只算原有次数，不为了缩短连线重复计算。
- 节点主标题优先工程别名，如“左上钢片顶面”“台面五窗拟合”，同时保留算法名称。共享基准靠近共同使用区域、对象内路径方向一致、汇总区放在输出侧；必要时滚动查看，不强求全图缩到文字无法辨识的一屏。
- 高频操作沿现有应用模式进行文件输入、运行和结果查看；工程编辑在完整显示的组中直接修改 ROI、方法和限值。不能用“操作员只运行”掩盖工程配置不友好的问题。
- 本轮不新增工件专属多功能节点，不引入模板执行系统。仅根据 U2 核对结果实施必要的通用节点职责或接口调整；纯布局改动和真实功能简化分别报告。
- 验收采用原完整点云，检查所有 50 项数值、有效性、判定及输出字段与原冻结配方一致；核对原始行号、证据及保存行为不变。Windows 验证真实表单编辑到保存重开、发布运行；WSL 原生文件系统验证同配方发布及执行，不将其表述为 Ubuntu GUI 验收。
- 验收以能独立配置 Read Cloud、不写 JSON、能定位并修改指定对象的 ROI/限值、能沿线解释基准到结果为使用目标；不以节点总数下降作为唯一目标，不宣称画布简化会自动达到十秒节拍。
