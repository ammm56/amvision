# 默认推理与小图尾延迟核对

## 范围与结论

本轮承接 [修复验收结果](runtime-repair-results-20261015.md)。一小时零调用错误和资源门禁通过，不代表正式 P99 已通过，也不能证明不存在长期内存增长。原正式报告的模型 2/5 轮、小图 1/5 轮失败仍有效。

本轮只增加独立诊断、请求关联和证据分析，没有修改生产模型、IPC 协议、业务准入或进程框架，没有关闭 GC、增加业务等待队列或放宽门禁。证据位于 `data/acceptance/runtime-repair-20261015/`。诊断 profile 的退出码 0 不等于正式性能通过，必须读取内部性能报告。

2026-10-16 已按要求暂停后续 P99 调查，不再自动执行测试。实际修复、静态代码影响复核、适用边界及最新进程清理状态统一见 [收口审计](runtime-repair-results-20261015.md#收口审计)；本文保留诊断证据，不作为继续扩大排查范围的任务清单。

## 模型侧已证实的范围

同一 TensorRT 10.16.1 engine、真实预处理输入、GPU1、FP32，通过 NVIDIA `trtexec` 直接执行，不经过 Python 推理 session、Workflow、数据库或平台 IPC。使用 `--exposeDMA` 保持单流串行传输，并交替执行 0/18/0/18 ms 间隔，每组 1,000 次。**以下首组运行在工具隔离环境，不是正式发行验收的宿主环境，不能与管理员轮次直接作锁频因果比较。**

| 顺序 | 间隔 / ms | C++ latency P99 / ms | GPU compute 区间 P99 / ms |
| --- | --- | --- | --- |
| 1 | 0 | 7.350 | 4.835 |
| 2 | 18 | 37.886 | 26.427 |
| 3 | 0 | 8.256 | 5.388 |
| 4 | 18 | 37.805 | 27.138 |

证据：`remaining-native-floating-*-gap*.json`、对应日志及 `remaining-native-floating-commands.json`。首个命令因 Windows 盘符被 `--loadInputs` 解析为 tensor 名的一部分而失败，已改用相对输入路径；该失败保留在 `remaining-native-0-gap0.log`，不是产品推理失败。

这个对照证明：请求间隔退化可以在项目调用链之外复现，不能再把它唯一归因于平台生命周期锁、Python GIL 或 IPC。它不证明驱动存在缺陷，也不能单凭该对照区分 GPU 自动频率与 WDDM 调度。NVIDIA 文档明确区分[浮动时钟与 WDDM 对测量的影响](https://docs.nvidia.com/deeplearning/tensorrt/10.x.x/performance/hw-sw-environment.html)；文档说明不能替代本机实验。

### 授权锁频对照

只操作 GPU1 UUID `GPU-425ff429-ea08-1ef0-a68b-b02c85b7bfab`，目标 SM 时钟 2475 MHz；不修改 GPU0、显存时钟、驱动、Windows 电源方案或 200 W 功耗上限。脚本在 `finally` 中执行自动时钟恢复，设置和恢复均留存原始返回值。普通权限的第一次尝试被驱动拒绝，没有设置成功，保留在 `remaining-clock-control.json`。

管理员会话对照 `remaining-clock-control-admin.json` 确认锁频和恢复均成功，但没有消除 full-core 尾延迟。该轮自动时钟采样已经保持 2745 MHz，不能把它解释成“低频到高频”的单变量反事实。原生工具与该会话同进程组运行时还存在一个闲置 Python CUDA context，因此另设无额外 CUDA context 的原生三阶段对照，不合并两类样本。

纯原生三阶段对照 `remaining-native-clock.json` 中，控制进程不创建 CUDA context。每个阶段均按 0/18/0/18 ms 间隔执行：

| 同一管理员宿主环境 | 0 ms 两轮 latency P99 / ms | 18 ms 两轮 latency P99 / ms |
| --- | --- | --- |
| 自动时钟 | 16.015 / 16.576 | 7.874 / 9.489 |
| 锁定 2475 MHz | 16.204 / 15.881 | 8.765 / 6.948 |
| 恢复自动时钟 | 15.531 / 15.025 | 7.321 / 12.637 |

锁频阶段采样确认 2475 MHz；过渡后的恢复采样重新出现 2640/2220/2745 MHz，恢复命令成功，前后功耗上限均为 200 W。锁频不能消除连续调用的约 16 ms 尾部。

随后在与正式验收一致的普通权限宿主环境执行 `remaining-native-host-floating-*`，0 ms 两轮 P99 为 15.986/16.045 ms，18 ms 两轮为 18.869/15.585 ms。说明隔离环境中的 8→38 ms 变化不能直接代表宿主，也不能据此把默认性能失败统一归因于空闲降频。没有开启默认保温、修改系统电源方案或以锁频作为项目修复。

### CUDA 时间线

宿主环境使用已安装的 Nsight Systems，只采集测试进程 CUDA/NVTX，不采集系统级 WDDM/CPU 事件。`remaining-nsys-host-gap0/18.sqlite` 保留原始活动，`remaining-cuda-attribution.json` 将每次 enqueue 与 273 个顺序相同的 kernel、输入和输出 DMA 关联；每组最后 200 次为测量请求，前面的工具预热单独排除。第一轮隔离环境下 Nsight 启动超时的日志也保留，不计作产品错误。

- 连续组 kernel 实际执行总和 P99 1.128 ms，而首末 kernel 跨度 P99 13.758 ms。
- 连续组 25/200 次、18 ms 组 1/200 次存在超过 8 ms 的 kernel 间空档，范围约 9.226–10.040 ms。
- 这些空档之后的 kernel 提交 API 均在前一个 kernel 结束前已返回，且同一 compute stream 中没有覆盖空档的 memcpy/memset。已排除这批慢点是 Python/Workflow 迟交，或只是 kernel 算得更慢。
- 证据将这批慢点收窄到已提交 GPU 工作的执行/调度等待层，但没有系统级 WDDM 上下文切换证据，不能进一步指认某个桌面进程、驱动缺陷或某项系统调度设置。

Nsight 存在观测开销，以上用于定位，不替代原正式 P99。kernel 报表有工具输出编码警告，分析读取 SQLite 原始记录并校验 kernel 数量和顺序，没有使用报表缺失值。

### GPU1 实际运行环境

`remaining-host-hardware.json` 的宿主机只读检查发现：GPU1 当前 PCIe 链路为 **Gen3 ×1**，设备报告最大宽度 ×16；GPU0 当前宽度为 ×16。仅从这些值不能判断是插槽设计、主板 lane 分配还是链路协商问题，不能直接判定硬件损坏。

时间线中每次 1,179,648 B H2D 中位数约 1.453 ms，786,432 B D2H 约 0.951 ms，传输成本不能忽略。但窄链路不足以解释没有同流内存操作覆盖的约 10 ms 空档。

所有测试推理退出后，GPU1 仍承载桌面、浏览器、编辑器等图形上下文；10 秒只读采样利用率为 **19%–66%**。因此本机 GPU1 并非完全独占，不能把测试结果标成“独占 GPU 验收”。未关闭非测试应用，未迁移桌面、改 GPU0 或修改 BIOS。要将外部调度竞争与驱动内部等待进一步分离，需要真正隔离图形负载的对照或受控 WDDM 调度跟踪，而不是继续修改模型数学实现。

## 小图请求级证据

| --- | --- | --- | --- |
| 1 | 23.510 | 37.008 | 失败 |
| 2 | 31.654 | 30.632 | 通过 |

`remaining2-associated.json` 将 20,000 次模型和小图测量按 source、轮次、完整 event ID 与同 PID 观测关联，无丢记录。每轮序号会重用，不能只按 source/sequence 建字典，否则后轮覆盖前轮；独立 preflight 不计入测量。该问题仅在本轮离线分析脚本初次关联时发现，断言中止后修正，没有改变 SDK 计时或历史正式统计。

### 长 GC 是已捕获的一种原因

第 4 轮同一 backend 的 generation 2 GC 持续 186.264 ms。对应 shared 请求达到 206–221 ms，其中一个请求的准入 196.401 ms，另一个请求的 manager 调用 199.760 ms；同 PID 的完整区间交集直接证明长 GC 阻塞了这两个请求。其余两个请求的慢点落在发布等待或最终响应阶段，不能只靠准入/调用两个观察区间进一步作唯一归因。

第 1 轮的 P99 超限没有相同长 GC 证据。原正式失败轮 SDK GC 也不与尾部请求重合。因此不能以“都是 GC”解释全部小图失败，更不能通过禁用 GC 或改采样删除这些请求。

### 准入与 Broker 开销

第二次诊断 `remaining-detail-diagnostic` 细分相同生产方法，10,200 次测量请求关联完整、观察记录无溢出。准入仍执行当前 Runtime 与 active revision 的数据库读取；不是每次重新加载执行策略文件，也不是 token 获取长时间阻塞。

该轮全程观测：Runtime 读取 P99 4.232 ms、active revision 读取 P99 2.988 ms、执行策略加载 P99 0.004 ms、token 获取 P99 0.105 ms。shared 使用的 external allocate 与 publish/handoff 在同一 Broker client 的串行请求锁上，锁等待 P99 分别 2.406/2.167 ms；对应完整控制往返 P99 4.237/3.996 ms。release-owner 锁等待 P99 2.118 ms。

这些计时既有嵌套也来自不同请求，不能相加成一个请求的 P99。Windows `thread_time_ns` 在该运行环境显示 15.625 ms 粒度，不能用该字段精确分解毫秒级 CPU/GIL/调度占比。具体同请求记录保留在 `remaining-detail-associated.json`。

例如失败轮 worker-1 的第 207 个测量请求总耗时 32.960 ms：Runtime 读取 3.688 ms、revision 读取 2.715 ms、完整准入 6.673 ms；release-owner 控制请求 6.582 ms，其中同一 client 锁等待 3.525 ms。另一请求的 token 获取只有 0.030 ms。以上是同请求关联，不是用不同请求的 P99 拼接。

共享内存没有图像复制开销优势时，多阶段所有权交接和共享控制通道会成为可测成本。不能为消除这些成本删除 PREPARE、handoff、ACK、receipt 或停止恢复校验；也不能把正常控制协议成本直接等同于新发现的功能错误。尚需独立的等价实现反事实，才能证明这些成本各自导致了多少正式 P99 超限。

## 一小时内存趋势复核

`remaining-analysis.json` 对原 718 个测量样本按角色重新分组。inference-daemon **进程组**的 RSS 增长约 20.90 MiB、private 增长约 20.62 MiB，是总增长的主要部分；该组包含部署子进程，不能等同于 daemon 单进程泄漏。六个十分钟窗口的 RSS 中位数约为 2694.56、2700.65、2706.58、2708.98、2711.09、2713.56 MiB，尚未形成完全平台期。

backend 的增长大部分在前段阶跃后稳定；evaluation worker 也主要是前段阶跃。以上不推翻原资源门禁通过，但不能将 30.65 MiB 总增长全部解释为“已完成预热”，也不足以直接判定持续泄漏。

隔离环境与宿主环境分别执行同一 full-core 会话 8,000 次固定输入推理。宿主记录 `remaining-host-memory.json` 中，RSS/private 相对预热后的增长约 2.71/2.92 MiB，3,000→8,000 次期间 RSS 只增加约 0.145 MiB，private 略降；线程 30→27，pinned 输出固定 832,032 B。Python 记录总量约 0.306 MiB，诊断专用显式 GC 后约 0.100 MiB，包含观察器自己的快照数据。

prediction/proto 摘要仍分别为 `45f3c63e...cc30` 和 `52e61132...e8ef`，与此前固定工程样本一致。这只是该会话与该输入的资源/输出核对，不是所有模型准确率认证。独立会话没有复现进程组约 20.9 MiB 的持续增长，因此该进程组趋势仍需在 daemon、部署子进程和 IPC 各自采样后闭合，不能宣称已经证明无泄漏。
