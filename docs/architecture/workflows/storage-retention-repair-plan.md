# 文件保留清理修复与验收方案

## 状态和依据

状态：已实现并完成 Windows 功能回归与开发环境短时联调；长期及部署规模验收尚未完成。依据为 [2026-09-21 审计](../../operations/storage-retention-audit-20260921.md)，实施与测试结果见[验证记录](../../operations/storage-retention-repair-20260921.md)。

目标是在保持本地部署、同步 Runtime/Trigger、无新增队列和后台调度的前提下，修复文件清理与保存的生命周期问题。范围包括 Storage Retention Cleanup、其共用文件系统能力、明确启用缺图回退的图片读取节点及实际显示 Workflow。模型加载、推理算法、LocalBuffer、部署 IPC、生产计数及 .NET 调用协议不变。

## 必须保持的规则

1. 时间策略只删除文件修改时间严格早于截止点的文件。一个月表示自然月，月末与闰年按现有规则处理。
2. 候选按修改时间从旧到新处理，同一时间用规范路径确定顺序。达到单次上限后留下较新的过期文件供后续调用清理，不能随机删除，也不能优先删除最新文件。
3. 最新图片如果也已过期，仍可以被清理；不暗中保留最后一张图片。缺图由读取和显示边界处理。
4. 图片、结果 JSON 的保留与生产统计独立。当前九个固定目录不包含生产统计、JSONL 和汇总目录。
5. 清理调用不等待其他清理或写入者，不进行 Workflow 自动重放；正常推理满载不是故障。
6. 节点依然由 Workflow 明确调用。禁止增加隐式扫描线程、定时器、持久化扫描游标或清理队列。
7. 文件删除不可整批回滚。中途取消、进程退出或错误时，已删除文件保持已删除，未删除文件下次重新检查；不返回虚假的全批成功。

## 第一步：固定回归证据

在生产代码修改之前，增加可以确定性失败的隔离测试：

- junction 指向目标目录之外时，目标外空子目录不能被遍历删除；junction 自身也必须保留。
- `.amvision-*` 内部目录及其全部后代保持不变。
- Save 在创建日期目录与创建临时文件之间遇到清理，仍能正确保存，或在外部持续破坏路径时返回明确的有界错误，不能无限重试。
- 删除空目录期间发生新文件创建，必须保留新文件；目录非空是正常跳过。
- 单个节点取消和 Workflow 截止时间到达后停止继续选择、删除文件，释放句柄及锁。
- File missing 与权限不足、文件损坏、版本改变分别处理。

使用操作屏障或注入点控制并发顺序，不用依赖 sleep 的概率测试。Windows junction 测试是本平台必须执行的用例，不能因符号链接权限不足而一并跳过。所有删除测试仅使用明确创建的隔离目录。

完成门槛：旧实现能稳定复现审计问题；新的测试不会接触现场图片或 JSON。

## 第二步：统一安全遍历与条件删除

主要文件：`backend/service/infrastructure/filesystem/retention_files.py`。

- 普通文件扫描和空目录清理共享目录准入判断。必须在进入目录之前，以不跟随链接的方式检查类型、reparse 属性和控制名称。
- 用显式深度优先遍历替换当前不能提前裁剪的 bottom-up `os.walk`。目录在安全遍历完子树后才进入空目录删除阶段。
- 排除符号链接、junction、其他 reparse point、内部控制目录和临时文件；清理根目录永不删除。
- 候选保存目录身份；下降、重新打开及删除前检查根和相关祖先是否仍是原先允许的目录。发生目录替换或新增链接时跳过/失败关闭，不能沿解析后的新位置继续删除。
- Windows 文件系统适配层应通过句柄验证和必要的删除/重命名保护，缩小检查与操作之间的竞争窗口；不能宣称一次 `resolve()` 或重复 `stat()` 可以完全消除路径替换竞争。无法建立安全边界时拒绝该操作，不退化成无条件删除。
- 不保留全部目录列表或候选文件列表。内存目标为 `O(delete_limit + page_size + directory_depth)`；异常退出时关闭遍历句柄。
- 权限错误必须显式报告；目录消失、变成非空、被写入保护则按预期并发分类处理。

完成门槛：junction/control 后代测试通过；外部目录、非匹配文件、根目录和期限内文件零误删；嵌套目录和路径变更用例通过。

## 第三步：修复保存与空目录删除竞争

主要文件：`backend/nodes/save_locations.py`、`backend/service/application/runtime/io/atomic_files.py`、`backend/service/infrastructure/object_store/local_dataset_storage.py` 及文件系统公共 helper。

采用公共的“确保父目录并安全创建临时文件”能力，避免每种 Save 节点各自打补丁。

### Windows 主实现

1. 创建/确认父目录，打开短生命周期的目录保护句柄；在创建临时文件的窗口内防止该目录被删除或重命名。并行保存使用可共存的保护，不用独占大目录锁串行化全部文件写入。
2. 目录在建立保护前已经消失时，仅重做目录准备，最多三次立即恢复。并发实测证明三次忙循环不足以覆盖 Windows 删除句柄关闭窗口：仅遇到 WinError 32/33/303 时改为最多 100 ms、每次 1 ms 的有界目录准备重试；正常路径没有等待，权限错误不按占用重试。该步骤不重放文件写入、推理、生产记录或整个 Workflow；短暂系统调用仍受操作系统调度影响。
3. 临时文件成功创建后，非空目录本身已能防止普通 `rmdir`；保护资源在明确的 finally 边界释放。原子发布顺序必须确保临时文件到最终文件之间不出现无文件窗口。
4. 清理尝试删除受保护的目录时立即跳过。权限不足不能被误分类为“正在写入”。
5. 外部持续删除或改写目录、无法建立保护等情况达到尝试上限后返回包含阶段的明确错误。不能通过重跑推理、重复追加生产记录或重新执行整个 Save 节点恢复。

当前未提供已验证的 POSIX 空目录删除实现。在任何删除前，POSIX 配置 `delete_empty_directories=true` 且非 dry-run 时明确报错，要求关闭该可选项；不把 advisory flock 宣称为与 Windows 目录共享模式等价的外部路径保护。

覆盖 bytes、文件复制、覆盖保存、自动编号保存、ObjectStore 本地写入和通用 atomic write；视频等先暂存后发布路径同样检查。保留现有文件级版本重检与写协调，不引入全局写锁。异常清理不得覆盖原始错误。

完成门槛：确定性 Save/清理交错通过；同目录并行保存成功且文件内容完整；不同目录互不等待；进程退出后无遗留占用。测量正常保存额外耗时，未达到性能要求前不能扩散到生产配置。

## 第四步：锁、取消和错误诊断

主要文件：`path_write_coordinator.py`、`storage_retention.py`、清理节点 handler。

- 只有可确认的非阻塞锁竞争返回 `target_locked`/`locked`。锁文件权限、无效句柄、系统 I/O 异常原样进入结构化失败。若当前 Windows CRT 错误映射不能可靠区分原因，在基础设施层保留原生错误码，不靠错误文本猜测。
- 复用 `ExecutionControl`：每页扫描、每个目录阶段及每次删除前检查取消和 deadline。检查回调通过应用层传入基础设施，保持依赖方向。
- 大目录没有匹配文件、大量空目录时也能响应取消；检查不能只放在发现可删除文件时。
- 操作系统单次阻塞调用不保证可立即中断；沿用现有 Worker 恢复边界，不新建每节点线程/进程。协作式取消与强制终止应分别验证。
- 错误提供稳定 `error_code`、操作阶段、节点、目标目录、必要的单个相对路径、errno/winerror，以及有界的本次扫描/已删除计数。不得返回无界文件清单或吞掉异常。
- `has_more` 表示当前观察范围还有剩余候选或被占用/改变的候选，不表示已自动安排后续执行。`partial` 的文档需要覆盖跳过文件的情况，不仅是删除上限。
- 时间参数超出有效日历范围、无效枚举、布尔代替整数、空路径、目标为文件等，应在产生删除副作用前拒绝。

完成门槛：注入真实锁竞争、非竞争错误、取消、超时和中途退出，均得到对应结果；没有后台继续删除或锁表持续增长。

## 第五步：缺图回退，保留数据真实性

主要文件：`core_nodes/io/local/image_load_local.py`、节点 schema、读取测试和前端占位显示。

- 增加显式 `missing_file_policy: error | blank`，默认 `error`，保持已有流程严格读取行为。
- 当前显示 Workflow 的六个业务图片读取节点配置为 `blank`。其他检测输入节点不自动放宽。
- 直接捕获实际读取返回的 `local_file_missing`，不能仅用先 exists 再 read 的检查；清理可能发生在两者之间。
- File 观察记录的版本校验仍然有效；明确绑定观察版本的输入不因该选项接受新版本。回退仅处理真实不存在，版本变化、权限不足、损坏、超过资源上限继续报错。
- 复用已有有界空白图尺寸，summary 标明 `generated_blank`、`blank_reason=missing-file` 和来源路径，不伪造文件观察记录。
- 界面显示“图片不可用”，不把所有缺失都宣称为已过期；也不继续展示前一轮残留图片。图内预览、应用模式、双击大图使用同一明确状态。
- 继续显示当前文件汇总中的计数与最后一次业务结论；不能因为图片缺失把 OK/NG 改为另一种检测结论或重置数量。
- 页面展示保持 JPEG 通道，新增占位图不引入 PNG 大图传输；现有真实图片内容不在读取节点改码。

无需添加大量 Exists/Compare/Conditional 节点。对磁盘不存在的处理放在实际读取处，既简洁又覆盖检查后的竞争。

完成门槛：图片先存在后被删除、启动时就缺图、全部历史图过期，以及新图片重新出现均正确；无残留旧图，统计准确，严格模式仍然报错。

## 第六步：扫描性能与运行编排

- `age` 模式只把已过期文件加入有界候选 heap，避免为大量期限内文件维护最旧候选；仍完整流式扫描，保持全局最旧顺序。
- count/age-and-count 继续按完整扫描结果决定稳定最旧候选，不改为“枚举到谁就删谁”。
- 不通过忽略目录尾部、按目录名猜日期、减少校验或隐藏异步删除制造低耗时结果。
- 修复期间当前九个节点可临时关闭 `delete_empty_directories`。重新启用必须通过第三步并发门槛；此配置变更及恢复需在实施报告中明确记录。
- 本轮不擅自迁移用户已编排的九个清理节点。保留在显示 Workflow 时明确接受每次完整扫描的耗时和清理错误对本次调用的影响。
- 对十万/百万文件生产规模，推荐将同样九个节点放入独立维护 Workflow，由上位机或已有外部调度低频调用。该迁移是显式编排调整，不能在节点内部私加调度，也不能悄悄改变当前应用。
- 不承诺任意规模全扫描或批量删除小于一秒。即使采用独立维护 Workflow，共享磁盘/CPU 仍需做并发压测。

完成门槛：给出固定目录规模、磁盘、文件分布和删除数量下的扫描/删除耗时，分别报告存储节点与整条 Workflow 的端到端耗时。

## 第七步：实际配置、兼容性和发布

1. 操作前读取最新 draft 与已发布版本，保存可恢复快照；核对未保存草稿，不覆盖用户新增节点、组位置、连接或颜色。
2. 保持九个目标目录、匹配模式、一个月和删除上限正确。只调整明确需要的缺图参数与空目录清理开关。
3. 后端新可选参数默认保持旧行为，继续使用 v1 API 和现有 payload；增加字段必须同步 node schema、目录、前端类型和文档。不增加数据库表或磁盘状态文件。
4. 保存草稿后校验并真实预览；发布新版本和切换 Runtime 是独立步骤，记录哪些 Runtime 已采用新版本，不能以页面“已保存”代替上线。
5. 修改源目录，按项目发布流程重新组装发行包；不得手改 release 中源码。验证 conda 开发环境和同目录发行 Python。
6. 配置可回滚到原版本；已经清理的文件不可因回滚代码恢复，测试和发布记录必须明确这一点。

## 验收矩阵

| 范围 | 必须验证的情况 | 通过条件 |
| --- | --- | --- |
| 时间和顺序 | 月末/闰年、恰好截止、未来时间、同 mtime、超过 1000 候选 | 新文件零误删，稳定最旧优先 |
| 文件策略 | age/count/组合、多个扩展名、大小写、子目录 | 计数、结果与保留范围一致 |
| 路径边界 | 根目录、junction、链接、控制目录及后代、扫描后路径替换 | 目标范围外零删除 |
| 并发 | Save/cleanup、两个 cleanup、文件修改/消失/占用、目录新建 | 无误删，无死锁，无重复业务执行 |
| 异常 | ACL/锁服务异常、磁盘 I/O、取消、进程退出、重启 | 原因可诊断，资源释放，后续可正常调用 |
| 显示 | 缺图、恢复、损坏图、权限错误、应用模式及大图 | 明确占位，错误不混淆，计数保持正确 |
| 资源 | 多轮扫描与删除、异常路径、多进程退出 | 锁/句柄/线程/Private Memory 无持续增长趋势 |
| 性能 | 1 千、1 万、10 万；部署规模涉及百万时加百万 | 分别记录 P50/P95/P99、删除吞吐和共享磁盘影响 |
| 核心链路 | Preview 与 Runtime/Trigger/.NET 同时调用 | 不引入队列，正确结果不变，既有门禁通过 |

开发联调先完成不超过约三分钟的真实数据功能冒烟，使用已有结果图片和统计。过期删除、损坏及异常注入在隔离目录完成，不修改现场图片时间戳制造过期。更大规模和长时间测试作为独立阶段明确记录，不把短测称为长期验收。

长期验收至少覆盖跨日期目录、重复创建/删除、保存与清理并发、Worker 重启和错误恢复。资源趋势需连续采样，不能只比较开始与结束两个点。性能比较使用同机、同磁盘、同数据、同并发条件，并沿用已有项目门禁；测试门槛不能在失败后临时放宽。

## 交付检查顺序

每一步执行“最小改动 → 对应用例 → 差异审查 → 记录结果”，通过后再进入下一步。最终交付包含源代码、失败用例回归、节点契约和说明、实际 Workflow 配置差异、开发/发行验证结果、Runtime 版本状态，以及仍未验收的边界。不得将已发现但未修复的问题写为已完成。
